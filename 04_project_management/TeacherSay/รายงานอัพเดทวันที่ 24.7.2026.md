
###  รายงานความคืบหน้าโปรเจค MyNetMate (Network Configuration Automation)
![[Screenshot 2026-07-24 150626.png]]

**1. ด้านการออกแบบสถาปัตยกรรมและฟีเจอร์ (อ้างอิงจากแผนภาพ MyNetMate)**
*   **ฟีเจอร์หลัก (Core Features) ที่จะดำเนินการพัฒนา:**
    *   **Authentication & Dashboard:** ระบบยืนยันตัวตน และหน้ากระดานสรุปผลการทำงาน พร้อมระบบ Audit Trails สำหรับบันทึกประวัติการเปลี่ยนแปลงทั้งหมด
    *   **Device Inventory:** ระบบบริหารจัดการคลังอุปกรณ์ รองรับสภาพแวดล้อมแบบ Multi-vendor (Cisco, MikroTik, Huawei) โดยรองรับทั้งการเพิ่มข้อมูลด้วยตนเอง (Manual) และการค้นหาอัตโนมัติ (Network Auto-Discovery)
    *   **Network Topology:** แผนผังเครือข่ายเชิงโต้ตอบ (Interactive) ที่อนุญาตให้ผู้ดูแลระบบจัดเรียง Node (Drag & Drop) และระบุพอร์ตการเชื่อมต่อได้ด้วยตนเอง
    *   **Configuration Management (ระบบบริหารจัดการคอนฟิก):**
        *   *Config Generation:* ระบบสร้างชุดคำสั่งโดยใช้ Rulebase (Jinja2 Template) เป็นแกนหลัก ผสานการทำงานร่วมกับ AI (LLM) และมีกระบวนการ PII Masking เพื่อรักษาความปลอดภัยของข้อมูล
        *   *Config Deployment & Security Validation:* กระบวนการตรวจสอบความสอดคล้องด้านความปลอดภัย (Compliance) ก่อนดำเนินการผลักดันคำสั่ง (Push) ลงสู่อุปกรณ์จริง
        *   *Version Control:* ระบบจัดเก็บประวัติและควบคุมเวอร์ชันของการตั้งค่า
    *   **Settings:** ส่วนการตั้งค่าระบบ AI, การบันทึก Credential อัตโนมัติ และการสำรองข้อมูล (Auto Backup)
    *   **Security Mode (กระบวนการป้องกันความผิดพลาด):** 
        *   *Protect Mode (Commit Confirmed):* ทุกครั้งที่มีการปรับใช้การตั้งค่าใหม่ ระบบจะดำเนินการหน่วงเวลาเพื่อตรวจสอบสถานะการเชื่อมต่อ (SSH Reconnect) อย่างต่อเนื่อง เพื่อป้องกันข้อผิดพลาดที่อาจส่งผลให้ผู้ดูแลระบบสูญเสียการควบคุม (Management Disconnect)
        *   *Recovery Mode:* หากเข้าสู่ Protect Mode และระบบตรวจพบว่าสูญเสียการเชื่อมต่อ จะดำเนินการย้อนกลับ (Auto-Rollback) ไปสู่การตั้งค่าเวอร์ชันก่อนหน้าโดยอัตโนมัติทันที
*   **ส่วนที่พิจารณาชะลอการพัฒนาหรือตัดออก (Deferred/Excluded Features):**
    *   *Auto-Generated Report (PDF):* พิจารณาตัดออก เนื่องจากผู้ใช้งานสามารถตรวจสอบข้อมูลและสถานะเชิงลึกผ่านระบบ Dashboard  จึงมุ่งเน้นทรัพยากรไปที่ระบบ Automation เป็นหลัก
    *   *การประเมินความจำเป็นของ RAG (Retrieval-Augmented Generation):* ขณะนี้อยู่ระหว่างการพิจารณาลดบทบาทของ RAG ลง เนื่องจากประเมินว่าโมเดลภาษา (LLM) ในปัจจุบันมีขีดความสามารถด้านไวยากรณ์เครือข่ายที่ครอบคลุมเพียงพอ การอาศัย Template เป็นหลักร่วมกับการปรับแต่ง Prompt จะช่วยลดความซับซ้อนของระบบ (System Complexity) และประหยัดทรัพยากรได้มากกว่า

**2. การรักษาความปลอดภัยข้อมูลส่วนบุคคลและความลับ (PII Masking)**
*   **ความท้าทาย:** จากการศึกษาพบว่า หากใช้ Regex ในการเซ็นเซอร์ IP Address ทั้งหมด AI อาจสูญเสียบริบทด้าน Subnet และการทำ Routing 
*   **แนวทางแก้ไข:** ทางทีมผู้พัฒนาได้นำเสนอการใช้ไลบรารี **`yacryptopan`** ซึ่งใช้กระบวนการเข้ารหัสแบบ **Prefix-preserving IP address anonymization** เข้ามาแก้ปัญหา โดยกระบวนการนี้จะทำการสุ่มแปลง IP Address แต่ยังคงรักษาโครงสร้างของ Network Prefix ไว้ ทำให้ AI สามารถคำนวณความสัมพันธ์ของเครือข่ายได้อย่างถูกต้อง โดยที่ข้อมูล IP จริงขององค์กรไม่ถูกส่งออกไปยัง External API

**3. การออกแบบสถาปัตยกรรมแบบขยายได้ (Plugin / Driver Architecture)**
*   **Extensible Architecture:** ออกแบบระบบให้มีความยืดหยุ่นและรองรับการขยายตัวในอนาคต 
*   **Separation of Concerns:** มีการแยกตรรกะการทำงานหลักของระบบ (Core Logic) ออกจากคำสั่งเฉพาะของแต่ละอุปกรณ์ (Vendor Logic) โดยจัดทำตัวกลาง (Abstract Base Interface) เพื่อให้การเพิ่มการรองรับอุปกรณ์ยี่ห้อใหม่ในอนาคต สามารถทำได้ผ่านการติดตั้ง Plugin Driver โดยไม่กระทบต่อซอร์สโค้ดหลักของระบบ

**4. การดำเนินการทดสอบระบบ Network Auto-discovery**
*   **รูปแบบการทำงาน:** พัฒนาในรูปแบบ CLI Application / Background Task โดยรับคำสั่งเริ่มต้นในการสแกนเครือข่ายผ่านอาร์กิวเมนต์ เช่น การระบุช่วง `IP หรือ CIDR (192.168.1.0/24)`
*   **กระบวนการวิเคราะห์:** ระบบจะส่ง Probe (SSH/SNMP) ไปยังเป้าหมาย เมื่อพบการตอบสนอง จะทำการดึงข้อมูล `sysDescr` (System Description) เพื่อจำแนกผู้ผลิตและรุ่นของอุปกรณ์ และแสดงผลให้ผู้ดูแลระบบยืนยัน (Confirm) ก่อนจัดเก็บลงฐานข้อมูล Inventory
*   **การจำลองสภาพแวดล้อม (Mocking):** ระหว่างการพัฒนา จะประยุกต์ใช้โปรแกรม **SNMPSIM** เพื่อจำลองพฤติกรรมของอุปกรณ์เครือข่าย ทำให้สามารถจำลองการทดสอบในสเกลขนาดใหญ่ได้โดยไม่ต้องพึ่งพา Hardware จริงทั้งหมด

**5. การประยุกต์ใช้โครงสร้างการจัดเก็บข้อมูลแบบ Nornir Inventory**
*   โครงงานได้นำรูปแบบการจัดเก็บข้อมูลของแพลตฟอร์ม Nornir มาประยุกต์ใช้ เพื่อรองรับการสเกลและการจัดการที่ซับซ้อน โดยแบ่งความสัมพันธ์ของฐานข้อมูลออกเป็น 3 ระดับ:
    *   **Hosts (รายอุปกรณ์):** จัดเก็บพารามิเตอร์เฉพาะเจาะจงของเครื่อง เช่น Hostname, IP Address, OS Version
    *   **Groups (กลุ่มอุปกรณ์):** จัดกลุ่มอุปกรณ์ตามความสัมพันธ์ (เช่น `Group: Core-Switches`, `Floor-1`) เพื่อรองรับการสั่งรันชุดคำสั่งแบบกลุ่ม (Bulk Execution)
    *   **Defaults (ค่าพื้นฐานส่วนกลาง):** จัดเก็บค่าตัวแปรระดับระบบหรือ Credential Profiles ทำให้ Hosts ต่างๆ สามารถสืบทอด (Inherit) ค่าพารามิเตอร์ไปใช้งานได้ ช่วยลดความซ้ำซ้อนในการจัดเก็บข้อมูลรหัสผ่าน
