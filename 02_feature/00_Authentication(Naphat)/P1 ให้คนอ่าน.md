## 2. P1 ที่ควรทำ Full-stack

|ส่วน|P1 ขั้นต่ำ|
|---|---|
|Frontend|Login ด้วย username/email, logout, session-expired state, route guard, หน้าเปลี่ยนรหัสผ่านตนเอง, และหน้า Admin จัดการ user แบบ create/list/deactivate/change-role|
|Backend/API|Login, `me`, logout, self-change password, admin user APIs, Opaque Server-side Session Cookie, Argon2id และ RBAC guard|
|Data/contract|Migration ของ `users` และ `auth_sessions`; Cookie ถือ Token สุ่ม 256-bit, DB เก็บเฉพาะ SHA-256 Hash; ตรวจ session/role/is_active จาก DB ทุก Protected Request|
|Permission/security|Admin/Operator/Viewer, CORS Origin allowlist, CSRF Origin check, rate limit, last-admin protection|
|Test|Pytest ครอบคลุม login fail, revoke, role change, deactivate, permission denied, privacy, rate limit และ test-user seed|
|Audit integration|Auth เขียนเฉพาะ canonical Auth events ผ่าน writer; ไม่สร้าง Full Audit API หรือ Audit UI ซ้ำ|

สเปกที่รองรับชุดนี้อยู่ใน [MVP scope (line 5)](/E:/CEPP Project/หลักศูตร/KMITL_Knowledge/Project/02_feature/00_Authentication(Naphat\)/01_MVP - Authentication & RBAC.md:5), [API contract (line 5)](/E:/CEPP Project/หลักศูตร/KMITL_Knowledge/Project/02_feature/00_Authentication(Naphat\)/04_API Contracts.md:5) และ [Acceptance tests (line 7)](/E:/CEPP Project/หลักศูตร/KMITL_Knowledge/Project/02_feature/00_Authentication(Naphat\)/05_Acceptance Tests.md:7)

Demo ที่ทำได้จริง:

1. Login ด้วย `demo_operator` แล้วเข้าถึงเฉพาะสิทธิ์ Operator
2. Admin เปลี่ยน role หรือ deactivate Operator แล้ว session เดิมถูกปฏิเสธทันที
3. ผู้ใช้เปลี่ยนรหัสผ่าน แล้ว session เดิมทั้งหมดใช้ไม่ได้และ login ใหม่ด้วยรหัสผ่านใหม่ได้

## 5. ความเสี่ยงถ้ารับ Full-stack ทั้ง feature ตอนนี้

- ไม่มี commitment เจ้าของ Full-stack ที่ได้รับการยืนยัน จึงเสี่ยงชนกับ responsibility matrix
- Backend มีโครง FastAPI อยู่ แต่ยังไม่มี auth module, SQLAlchemy, Alembic, Argon2/session dependencies หรือ test stack ใน requirements  
    [backend README (line 1)](/E:/CEPP Project/หลักศูตร/KMITL_Knowledge/Project/mynetmate/backend/README.md:1), [requirements.txt (line 1)](/E:/CEPP Project/หลักศูตร/KMITL_Knowledge/Project/mynetmate/backend/requirements.txt:1)
- ต้องตกลงก่อนว่าใครทำ migration/schema, Audit writer และ rate-limit store; หากทำคนละส่วนโดยไม่มี test fixture ร่วม จะทดสอบ atomic revoke/audit ไม่ได้
- ค่า production origin, cookie domain และ deployment secret ยังไม่มีค่า environment จริงในเอกสาร จึงทำได้ระดับ dev/demo ก่อน

## 6. Recommendation

**Commitment ที่แนะนำ:** “เมื่อทีมตั้งชื่อ owner ชัดเจน ให้รับทำ Auth P1 เป็น vertical slice ที่มี Login, Database-backed Opaque Session, RBAC, minimal user management และ automated tests ครบ โดยไม่รับ Audit UI, NTV หรือ P2 identity features เพิ่ม”

- **สถานะที่แนะนำสำหรับนภัทรในฐานะ Full-stack owner:** `undecided` — รอการยืนยันจากทีม เพราะหลักฐานปัจจุบันไม่ระบุ commitment นี้
- **สถานะของ Authentication ในฐานะ project feature:** `committed` สำหรับ P1

Open questions ที่ต้องยืนยัน:

1. ใครเป็น owner ของ Auth Frontend, Auth Backend และ Alembic migration
2. ใครส่งมอบ Audit writer/test fixture ก่อน Auth integration test
3. P1 rate limiter จะใช้ in-memory สำหรับ single-instance demo หรือ service กลาง
4. Network Management group ยืนยันรับ Auth Shared Core อย่างเป็นทางการหรือไม่
5. จะใช้ API prefix `/api` ตาม Auth Contract หรือ `/api/v1` ตาม Backend Skeleton (`api_v1_prefix`) ต้องเลือกค่าเดียวก่อนเริ่มเชื่อม Frontend
