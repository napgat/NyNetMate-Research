# การออกแบบแผนภาพองค์ประกอบของระบบ (Component Diagram)

การออกแบบแผนภาพองค์ประกอบของระบบ MyNetMate ในส่วนการจัดการเครือข่าย (Network Management) แสดงการแบ่งหน้าที่ของโมดูลซอฟต์แวร์และความสัมพันธ์ระหว่างโมดูล เพื่ออธิบายว่าบริการแต่ละส่วนมีหน้าที่ใด และต้องเรียกใช้บริการจากส่วนใดของระบบ โดยไม่รวมความสามารถด้าน Configuration Management และการเปลี่ยนแปลงค่าของอุปกรณ์เครือข่าย

ระบบแบ่งส่วนติดต่อผู้ใช้งานออกจากส่วนประมวลผลและฐานข้อมูล ส่วน Backend ใช้ FastAPI และจัดกลุ่มโค้ดตามหน้าที่ เช่น Authentication, Audit Trail, Device Management และ Network Discovery โมดูลเหล่านี้ประกอบเป็นแอปพลิเคชัน Backend เดียวกัน ไม่ใช่บริการ Microservices ที่แยกติดตั้งแต่ละโมดูล แผนภาพต่อไปนี้สรุปความสัมพันธ์จากโครงสร้างโค้ดปัจจุบัน โดยแสดง PostgreSQL และอุปกรณ์เครือข่ายเป็นระบบภายนอกที่เกี่ยวข้อง

![Component Diagram ของ MyNetMate เฉพาะ Network Management](D:/KMITL-Repo/KMITL_Knowledge/Project/outputs/thesis/component-diagram/network-management-components.png)

*รูป: แผนภาพองค์ประกอบของระบบ MyNetMate ในส่วนการจัดการเครือข่าย*

จากรูป สามารถอธิบายองค์ประกอบหลักและหน้าที่ได้ดังนี้

1. **Web User Interface:** พัฒนาด้วย React และ TypeScript สำหรับแสดงหน้าจอ รับข้อมูลจากผู้ใช้งาน และเรียกบริการ HTTP API เช่น การเข้าสู่ระบบ การดูรายการอุปกรณ์ การดู Topology การจัดการผู้ใช้ และการดูประวัติเหตุการณ์ โดยไม่ติดต่อฐานข้อมูลโดยตรง
2. **API Routers:** เป็นส่วนรับคำขอของ Backend และส่งต่อไปยังโมดูลที่รับผิดชอบ เช่น Auth API, User Management API, Audit API, Device API และ Discovery API วงกลม HTTP API ในภาพแทนจุดให้บริการที่ส่วนติดต่อผู้ใช้งานเรียกใช้ ไม่ได้หมายถึง Endpoint เดียว
3. **Authentication / RBAC และ User Management:** จัดการการเข้าสู่ระบบ Session ฝั่งเซิร์ฟเวอร์ และการตรวจสิทธิ์ตามบทบาท รวมถึงการสร้างบัญชี เปลี่ยนบทบาท และเปิดหรือปิดใช้งานบัญชี โดยใช้บริการ Audit Trail สำหรับบันทึกเหตุการณ์ที่เกี่ยวข้อง
4. **Audit Trail:** แยกส่วนบันทึกเหตุการณ์ (Writer) ออกจากส่วนอ่านประวัติ (Reader) โดยส่วนอ่านเรียกตรวจสิทธิ์จาก Authentication ก่อนให้ข้อมูล การบันทึกครอบคลุมเหตุการณ์ที่ระบบกำหนด ไม่ใช่ทุกการคลิกของผู้ใช้งาน และ API สำหรับอ่านประวัติไม่เปิดให้แก้ไขหรือลบประวัติ
5. **Device Management:** จัดการข้อมูลอุปกรณ์ รายละเอียด Interface การตรวจสถานะการติดต่อ และข้อมูลที่ใช้แสดง Topology โดยเรียกใช้ SNMP Client สำหรับอ่านข้อมูลที่เกี่ยวข้อง การเปลี่ยนข้อมูลการจัดการใน MyNetMate ไม่ใช่การเปลี่ยน Configuration ของอุปกรณ์จริง
6. **Network Discovery and Collection:** จัดการคำขอค้นหาเครือข่ายและการรวบรวมข้อมูล เรียกใช้ Network Discovery Library และบริการจัดการอุปกรณ์ เพื่อนำข้อมูลอุปกรณ์และหลักฐานเพื่อนบ้านมาใช้ใน Inventory และ Topology โดยจำกัดการใช้งานกับสภาพแวดล้อมทดสอบที่ได้รับอนุญาต
7. **Network Discovery Library:** เป็นไลบรารี Python ที่ทำงานภายใน Backend ไม่ใช่แอปพลิเคชันหรือบริการแยก ใช้สนับสนุนการค้นหาและการอ่านข้อมูลผ่าน SNMP ชื่อในภาพใช้ชื่อหน้าที่ของไลบรารี โดยชื่อแพ็กเกจที่เรียกใช้ในโค้ดคือ `oxian_py`
8. **Database Session:** เป็นองค์ประกอบเชิงตรรกะที่แทนส่วนสร้าง Engine และ Session ของ SQLAlchemy ซึ่งโมดูลต่าง ๆ ใช้เข้าถึง PostgreSQL ไม่ได้หมายความว่าระบบมี Repository กลางสำหรับทุก Feature หรือว่าทุกคำขอใช้ Transaction เดียวกัน

PostgreSQL จัดเก็บข้อมูลผู้ใช้งาน Session ประวัติเหตุการณ์ อุปกรณ์ และข้อมูลการค้นหา ส่วนอุปกรณ์เครือข่ายใน Lab เป็นแหล่งข้อมูลที่ระบบอ่านผ่าน SNMP ทั้งสองส่วนแสดงเป็นบริบทภายนอก ไม่ใช่โมดูล Python ภายใน Backend

## การเชื่อมต่อระหว่างองค์ประกอบ

ส่วนติดต่อผู้ใช้งานเป็นผู้เรียกใช้ HTTP API ขณะที่ API Routers เป็นผู้ให้บริการและส่งต่อคำขอไปยังโมดูลที่เกี่ยวข้อง เส้นทึบที่เชื่อมกับวงกลมแสดงการให้บริการ Interface ส่วนลูกศรเส้นประแสดงการเรียกใช้หรือการพึ่งพาองค์ประกอบอื่น โดยลูกศรชี้จากผู้เรียกใช้ไปยังส่วนที่ถูกเรียกใช้ ไม่ใช่ลำดับการทำงานตามเวลา

ความสัมพันธ์สำคัญคือ Authentication เรียก Audit Writer เพื่อบันทึกเหตุการณ์ ขณะที่ Audit Reader เรียก Authentication เพื่อตรวจสิทธิ์การอ่านประวัติ ความสัมพันธ์สองทิศทางนี้เกิดจากหน้าที่ที่แตกต่างกัน ไม่ใช่การส่งคำขอวนซ้ำ ส่วน Network Discovery ใช้บริการ Device Management ร่วมกับ Network Discovery Library และใช้ Database Session สำหรับจัดเก็บข้อมูลที่เกี่ยวข้อง

## ประโยชน์ของแผนภาพต่อการออกแบบระบบ

แผนภาพนี้ช่วยขยายรายละเอียดจาก System Architecture ซึ่งแสดงส่วนหลักและเทคโนโลยีที่ใช้ ให้เห็นการแบ่งหน้าที่ภายใน Backend และจุดเชื่อมต่อระหว่างงานแต่ละส่วน จึงช่วยให้ทีมเข้าใจบริการที่ต้องใช้ร่วมกัน เช่น การตรวจสิทธิ์ การบันทึก Audit และการเข้าถึงฐานข้อมูล รวมถึงใช้เป็นแนวทางอธิบายองค์ประกอบที่ปรากฏใน Sequence Diagram โดยไม่ซ้ำกับแผนภาพลำดับการทำงาน

แผนภาพสรุปโครงสร้างที่ตรวจพบในโค้ด ไม่ใช่หลักฐานว่าทุกความสามารถผ่านการทดสอบครบวงจร และไม่สื่อว่าทุก API ผูกกับการตรวจสิทธิ์หรือบันทึก Audit แล้วทั้งหมด การรับรองผลการทำงานต้องพิจารณาหลักฐานการทดสอบแยกจากแผนภาพ
