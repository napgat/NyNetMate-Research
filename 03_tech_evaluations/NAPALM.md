**NAPALM (Network Automation and Programmability Abstraction Layer with Multivendor support)**
ลิงค์ : https://github.com/napalm-automation/napalm
document : https://napalm.readthedocs.io/en/latest/
**ประเภท:** ไลบรารีระดับการจำลองโครงสร้างข้อมูล (Abstraction Layer Library)

**หน้าที่หลัก:** ทำหน้าที่เป็นหน้าต่างส่วนกลาง (Unified API) ครอบสับซ้อนของแต่ละยี่ห้อเอาไว้ เพื่อให้ผู้พัฒนาสามารถใช้คำสั่งเดียวกันในการจัดการอุปกรณ์ต่างค่าย

**จุดเด่น:** * มีฟังก์ชันดึงข้อมูลมาตรฐานที่เรียกว่า **Getters** (เช่น `get_facts`, `get_interfaces`) ซึ่งจะส่งผลลัพธ์กลับมาเป็นโครงสร้างข้อมูล JSON ที่เหมือนกันเสมอไม่ว่าจะใช้กับอุปกรณ์ยี่ห้อใด
    - รองรับกระบวนการจัดการคอนฟิกขั้นสูง เช่น การเปรียบเทียบและแทนที่คอนฟิกทั้งหมด (Compare and Replace) หรือการรวมคอนฟิกเฉพาะส่วน (Merge) พร้อมระบบ Rollback
    
**ข้อจำกัด:** รองรับฟังก์ชันและคำสั่งเฉพาะทางได้จำกัด หากอุปกรณ์มีความสามารถพิเศษที่อยู่นอกเหนือฟังก์ชันมาตรฐานของ NAPALM จะไม่สามารถเรียกใช้งานผ่านภาษากลางนี้ได้

การเปลี่ยนผ่านจาก Netmiko ไปสู่ **NAPALM** จำเป็นต้องปรับเปลี่ยนวิธีคิดจากการควบคุมเซสชันการทำงานของอุปกรณ์ในระดับดิบ (Low-level CLI Session) ไปสู่แนวคิด **"ชั้นข้อมูลจำลอง (Abstraction Layer)"** โดยคอนเซปต์สำคัญที่คุณต้องทำความเข้าใจและจดบันทึกเพิ่มเติม มีดังนี้ครับ
## 3 คอนเซปต์หลักที่ต้องศึกษาต่อจาก Netmiko

### 1.Unified API และระบบ Driver

- **การนำไปใช้:** วิศวกรเครือข่ายสามารถเขียนโค้ดชุดเดียวเพื่อสั่งงานอุปกรณ์ต่างค่ายได้ทันที โดยคำสั่งระดับบนจะเหมือนกันทั้งหมด แล้วระบบ Driver เบื้องหลังจะทำหน้าที่แปลภาษากลางนั้นให้เป็นคำสั่งที่อุปกรณ์ค่ายนั้นๆ เข้าใจเอง อ้างอิงรายการอุปกรณ์ที่รองรับได้จากคลังโค้ดบน [NAPALM GitHub Repository](https://github.com/napalm-automation/napalm)

### 2. Getters และข้อมูลแบบมีโครงสร้าง (Structured Data)

คอนเซปต์นี้ขจัดปัญหาข้อจำกัดของ Netmiko ที่ส่งคืนค่ากลับมาเป็นข้อความดิบ (Unstructured String)

- **แนวคิด:** NAPALM มีฟังก์ชันสำเร็จรูปที่เรียกว่า **Getters** ทำหน้าที่ดึงข้อมูลสถานะเครือข่ายและแปลงเป็น Python Dictionary หรือ JSON ให้โดยอัตโนมัติ
* https://napalm.readthedocs.io/en/latest/support/index.html#getters-support-matrix
- **ฟังก์ชันสำคัญที่ต้องจดจำ:**
    
    - `get_facts()`: ดึงข้อมูลพื้นฐานของอุปกรณ์ (เช่น Hostname, Serial Number, Model, Uptime)
        
    - `get_interfaces()`: ดึงสถานะและพารามิเตอร์ของพอร์ตเชื่อมต่อทั้งหมด
        
    - `get_bgp_neighbors()`: ดึงข้อมูลการจับคู่และสถานะของโปรโตคอล BGP
        
- **ประโยชน์:** ไม่ต้องเสียเวลาเขียน Regular Expression หรือใช้ TextFSM Parser ภายนอกเพื่อตัดคำ ข้อมูลที่ได้พร้อมนำไปเข้าเงื่อนไขของระบบ Backend หรือส่งต่อให้ API ตัวอื่นได้ทันที
### 3. Configuration Management Workflow (ความปลอดภัยในการจัดการคอนฟิก)

ตำรา[[Network Programmability and Automation (Second Edition).pdf]] ได้เน้นย้ำถึงกระบวนการจัดส่งคอนฟิกอย่างปลอดภัย ซึ่ง NAPALM ได้เปลี่ยนรูปแบบจากการส่งคำสั่งทีละบรรทัดแบบเรียงลำดับ มาเป็นกระบวนการ 4 ขั้นตอน (Pipeline) เพื่อป้องกันความผิดพลาด:

- **Load Config:** การนำไฟล์คอนฟิกใหม่ไปพักไว้ในหน่วยความจำชั่วคราวของอุปกรณ์ รองรับ 2 รูปแบบคือ **Merge** (เขียนทับเฉพาะส่วน) และ **Replace** (เปลี่ยนคอนฟิกทั้งหมด)
    
- **Compare Config (Diff):** การสั่งเปรียบเทียบความแตกต่างระหว่างคอนฟิกปัจจุบัน (Running) กับคอนฟิกใหม่ที่โหลดเข้าไป เพื่อให้ผู้ดูแลระบบตรวจสอบความถูกต้องก่อนสั่งงานจริง
    
- **Commit Config:** การยืนยันเพื่อบันทึกและเปิดใช้งานคอนฟิกใหม่พร้อมกันในคราวเดียวแบบเป็นกลุ่ม (Atomic Operation) ป้องกันการเกิดปัญหาคอนฟิกค้างครึ่งๆ กลางๆ
    
- **Discard Config / Rollback:** หากพบข้อผิดพลาดระหว่างทาง สามารถสั่งยกเลิก (Discard) ก่อน Commit หรือสั่งย้อนคืนค่า (Rollback) คอนฟิกดั้งเดิมกลับมาได้อย่างรวดเร็ว


### 4. โครงสร้างโค้ดพื้นฐานของ NAPALM

```Python
import json
from napalm import get_network_driver

# 1. เลือก Driver ให้ตรงกับยี่ห้อ/ระบบปฏิบัติการของอุปกรณ์
driver_name = 'ios' # สำหรับ Cisco IOS (หากเป็นยี่ห้ออื่น เช่น 'eos', 'junos', 'nxos')
driver_class = get_network_driver(driver_name)

# 2. กำหนดข้อมูลการเชื่อมต่อและสร้าง Object ของอุปกรณ์
# optional_args ใช้สำหรับกำหนดพารามิเตอร์เพิ่มเติม เช่น พอร์ต หรือการตั้งค่า SSH เฉพาะทาง
device = driver_class(
    hostname='192.168.1.1',
    username='admin',
    password='password123',
    optional_args={'port': 22} 
)

# 3. เปิดการเชื่อมต่อ
device.open()

# 4. เรียกใช้งาน Getters (ข้อมูลที่ได้จะเป็น Python Dictionary ทันที)
print("--- อธิบายข้อมูลพื้นฐานของอุปกรณ์ (get_facts) ---")
facts = device.get_facts()
print(json.dumps(facts, indent=4)) # ใช้ json.dumps เพื่อจัดฟอร์แมตให้อ่านง่าย

print("\n--- ดึงข้อมูลสถานะของอินเตอร์เฟสทั้งหมด (get_interfaces) ---")
interfaces = device.get_interfaces()
print(json.dumps(interfaces, indent=4))

# 5. ปิดการเชื่อมต่อ
device.close()
```

### 5. จุดเปรียบเทียบที่สำคัญ: Netmiko vs. NAPALM ในระดับโค้ด

1. **การระบุประเภทอุปกรณ์ (Driver Selection):**
	- **Netmiko:** ระบุผ่าน Key `device_type` (เช่น `'cisco_ios'`) ภายใน Dictionary ของข้อมูลอุปกรณ์
	- **NAPALM:** ใช้ฟังก์ชัน `get_network_driver('ios')` เพื่อดึงคลาสของ Driver มาสร้างเป็น Object ก่อนใส่ข้อมูลเชื่อมต่อ
	
2. **รูปแบบการสั่งงาน (Execution):**
	- **Netmiko:** ต้องพิมพ์คำสั่ง CLI ลงไปตรงๆ เช่น `device.send_command("show ip interface brief")`
	- **NAPALM:** เรียกใช้เมธอดที่เป็นมาตรฐานของไลบรารี เช่น `device.get_facts()` หรือ `device.get_interfaces()` โดยไม่ต้องสนใจว่าคำสั่ง CLI ของค่ายนั้นคืออะไร
3. ผลลัพธ์ที่ได้ (Output Format):
	* **Netmiko:** คืนค่ากลับมาเป็นข้อความดิบ (Raw String) ที่ต้องนำไปเขียนสคริปต์แยกคำ (Parsing) ต่อเอง
	- **NAPALM:** คืนค่ากลับมาเป็น Python Dictionary พร้อมใช้งาน สามารถนำไปเรียกใช้คีย์ที่ต้องการได้เลย เช่น `facts['uptime']` หรือแปลงเป็น JSON เพื่อส่งต่อให้ระบบอื่นได้ทันที
4. **การจัดการเซสชัน (Session Management):**
	- **Netmiko:** เชื่อมต่อทันทีที่สร้าง Object ด้วย `ConnectHandler`
	- **NAPALM:** ต้องสั่ง `device.open()` เพื่อเริ่มเซสชัน และ `device.close()` เมื่อเสร็จสิ้นอย่างชัดเจน


### 6. **ข้อจำกัด (Caveats) ที่ต้องตระหนัก**

1. การรองรับอุปกรณ์แบบ Native มีจำกัด (Limited Core Support)
NAPALM รองรับอุปกรณ์หลักอย่างเป็นทางการ (Core Drivers) เพียง 5 ระบบปฏิบัติการเท่านั้น ได้แก่:
	- Arista EOS
	- Cisco IOS
	- Cisco IOS-XR
	- Cisco NX-OS
	- Juniper JunOS
	หากในเครือข่ายมีอุปกรณ์ค่ายอื่น (เช่น MikroTik, Huawei หรือ Fortinet) คุณจะต้องพึ่งพา **Community Drivers** ซึ่งอาจได้รับการอัปเดตช้ากว่า มีฟังก์ชัน Getters ให้ใช้ไม่ครบถ้วน หรืออาจเกิดบั๊กที่ยังไม่ได้รับการแก้ไขจากผู้พัฒนาอิสร

2. ต้องเปิดใช้งานฟีเจอร์เฉพาะบนอุปกรณ์ (Device Pre-requisites)
	Netmiko ต้องการเพียงแค่เปิด SSH ก็สามารถทำงานได้ทันที แต่ NAPALM จำเป็นต้องใช้โปรโตคอลอื่นเบื้องหลังเพื่อให้ได้ข้อมูลแบบมีโครงสร้าง คุณจึงต้องตั้งค่าอุปกรณ์ให้พร้อมก่อนการเชื่อมต่อ เช่น:
	- **Cisco NX-OS:** ต้องเปิดใช้งานฟีเจอร์ `NX-API`
	- **Cisco IOS-XR:** ต้องเปิดใช้งาน `XML agent`
	- **Cisco IOS:** ต้องเปิดใช้งาน `SCP server` และฟีเจอร์ `Archive` เพื่อให้รองรับการทำ Config Replace และการย้อนคืนค่า (Rollback)

3. ปัญหา "ตัวหารร่วมน้อย" (Lowest Common Denominator)
	เนื่องจาก NAPALM พยายามสร้าง "ภาษากลาง" (Unified API) ให้ใช้ได้กับทุกยี่ห้อ ฟังก์ชันที่มีให้เรียกใช้จึงถูกจำกัดอยู่แค่ **ฟีเจอร์พื้นฐานที่ทุกยี่ห้อมีร่วมกัน**
	- หากอุปกรณ์ของคุณมีฟีเจอร์พิเศษเฉพาะตัว หรือต้องการดึงค่าพารามิเตอร์เชิงลึก NAPALM จะไม่มี Getter มาตรฐานสำหรับดึงข้อมูลนั้น คุณจะต้องถอยกลับไปใช้ฟังก์ชัน `cli()` เพื่อส่งคำสั่งดิบ (ซึ่งทำให้กลับไปเจอปัญหาการต้องเขียนสคริปต์ตัดคำเองแบบเดียวกับ Netmiko)

 4. ความเสถียรของการจัดการคอนฟิก (Configuration Management Quirks)
	กระบวนการ Load, Compare, Commit และ Rollback จะทำงานได้สมบูรณ์แค่ไหน ขึ้นอยู่กับสถาปัตยกรรมของระบบปฏิบัติการปลายทาง:
	- อุปกรณ์อย่าง Juniper (JunOS) หรือ Arista (EOS) มีระบบจัดการคอนฟิกแบบ Transactional ที่ดีเยี่ยมในตัว การทำ Commit/Rollback ผ่าน NAPALM จึงรวดเร็วและปลอดภัยมาก
	- แต่สำหรับ OS รุ่นเก่าอย่าง Cisco IOS ที่เป็นการเขียนทับคำสั่งลงไปตรงๆ NAPALM ต้องใช้วิธีจำลองกระบวนการเหล่านี้ขึ้นมา (Workaround) ทำให้การทำงานช้ากว่า และมีโอกาสเกิดข้อผิดพลาดค้างในระบบได้หากการส่งไฟล์ไม่สมบูรณ์
5. ข้อกำหนดด้านสภาพแวดล้อม (Environment Requirements)
	ตัวแพ็กเกจของ [NAPALM](https://github.com/napalm-automation/napalm) มีการบังคับใช้เวอร์ชันของภาษา Python ที่ค่อนข้างใหม่ (เช่น ตั้งแต่เวอร์ชัน 5.1.0 ขึ้นไป จะรองรับเฉพาะ Python 3.9+) หากระบบเซิร์ฟเวอร์กลางที่คุณใช้รัน Automation Script ยังใช้สภาพแวดล้อมเก่า จะต้องจัดการอัปเกรดระบบก่อนติดตั้ง

สรุปคือ NAPALM เป็นเครื่องมือที่ทรงพลังมากหากโครงสร้างเครือข่ายของคุณใช้อุปกรณ์ในกลุ่ม Core Support และเน้นการจัดการข้อมูลพื้นฐานเป็นหลัก แต่ถ้าเครือข่ายมีความซับซ้อนและมีอุปกรณ์ยี่ห้อเฉพาะทางผสมอยู่มาก การใช้เครื่องมืออื่นอาจตอบโจทย์กว่าครับ


### 7. ความเพียงพอของเนื้อหาในการเปลี่ยนไป Nornir
เนื้อหาและแนวคิดพื้นฐานที่คุณได้ศึกษาจาก Netmiko และ NAPALM ถือเป็น **"รากฐานที่สมบูรณ์และจำเป็นอย่างยิ่ง"** ในการก้าวเข้าสู่ Nornir ครับ

เหตุผลสำคัญคือ Nornir ไม่ได้ถูกสร้างขึ้นมาเพื่อ "แทนที่" ไลบรารีทั้งสองตัวนั้น แต่ถูกสร้างขึ้นมาเพื่อเป็น **"กรอบการทำงาน (Framework)"** ที่คอยควบคุมและสั่งการ Netmiko หรือ NAPALM อีกชั้นหนึ่ง (ผ่านระบบ Plugin) หากคุณไม่เข้าใจวิธีการทำงานและข้อจำกัดของไลบรารีระดับล่างมาก่อน การแก้ไขปัญหา (Troubleshoot) เมื่อ Nornir เกิดข้อผิดพลาดจะทำได้ยากมาก

### สิ่งที่นำจาก Netmiko/NAPALM ไปใช้ใน Nornir ได้ทันที
- ความเข้าใจเรื่องความแตกต่างของระบบปฏิบัติการ (OS) และการกำหนด `device_type` หรือ `driver`
- โครงสร้างข้อมูลแบบ Dictionary และ JSON ที่ใช้จัดการคอนฟิก
- วิธีการส่งคำสั่ง (Command) และการใช้ฟังก์ชัน Getters ดึงข้อมูล

### 8. 4 จุดเปลี่ยนสำคัญที่ต้องเรียนรู้เพิ่มเมื่อเข้าสู่ [[Nornir]] (Conceptual Shift)

การเปลี่ยนผ่านสู่ Nornir คือการเปลี่ยนวิธีคิดจาก **"การสั่งงานอุปกรณ์ทีละตัว (Sequential Execution)"** ไปสู่ **"การบริหารจัดการภาพรวมระดับเครือข่าย (Orchestration & Concurrency)"** โดยมีคอนเซปต์ที่คุณต้องทำความเข้าใจและจดบันทึกเพิ่มเติมดังนี้:

### 1. Inventory Management (ระบบบริหารจัดการฐานข้อมูลอุปกรณ์)

ใน Netmiko หรือ NAPALM คุณอาจสร้างตัวแปรเก็บ IP และรหัสผ่านไว้ในไฟล์โค้ดตรงๆ แต่สำหรับเครือข่ายขนาดใหญ่ วิธีนี้จะดูแลรักษายาก Nornir บังคับให้คุณจัดระเบียบข้อมูลใหม่ทั้งหมด

- **แนวคิด:** Nornir แยกข้อมูลอุปกรณ์ออกจากลอจิกของโค้ด โดยใช้โครงสร้างไฟล์มาตรฐาน (ส่วนใหญ่นิยมใช้ YAML) แบ่งเป็น 3 ส่วนหลักคือ:
    
    - `hosts.yaml`: เก็บรายชื่อ IP และข้อมูลเฉพาะของอุปกรณ์แต่ละตัว
        
    - `groups.yaml`: กำหนดกลุ่มของอุปกรณ์ (เช่น เลเยอร์ Core, กลุ่ม Access, ยี่ห้อ Cisco)
        
    - `defaults.yaml`: เก็บตัวแปรส่วนกลางที่ใช้ร่วมกันทั้งหมด (เช่น Username/Password กลาง)
        
- **ประโยชน์:** คุณสามารถใช้ฟังก์ชัน `filter()` ของ Nornir กรองเฉพาะกลุ่มเป้าหมาย (เช่น เลือกเฉพาะอุปกรณ์ที่เป็น cisco_ios และอยู่สาขาเชียงใหม่) เพื่อรันสคริปต์ได้อย่างแม่นยำ
    
### 2. Concurrency & Parallel Execution (การประมวลผลแบบขนาน)

นี่คือฟีเจอร์ที่เป็นหัวใจหลักและเหตุผลอันดับหนึ่งที่วิศวกรเครือข่ายเปลี่ยนมาใช้ Nornir

- **แนวคิด:** ในการทำงานด้วย Netmiko ทั่วไป หากคุณมีอุปกรณ์ 100 ตัว คุณต้องใช้ `for loop` วนเชื่อมต่อทีละตัว ซึ่งอาจใช้เวลาหลายสิบนาที แต่ Nornir ใช้ระบบ Threads
    
- **การนำไปใช้:** เมื่อคุณสั่งรันโค้ด Nornir จะสร้าง Worker ตามจำนวนที่กำหนด (เช่น 20 Threads) แล้ววิ่งไปรันคำสั่งกับอุปกรณ์หลายตัวพร้อมๆ กัน ทำให้เวลาในการทำงานลดลงจากชั่วโมงเหลือเพียงไม่กี่นาที
    
### 3. Tasks และ Aggregated Results (กลไกการสั่งงานและรับผลลัพธ์)

เมื่ออุปกรณ์ถูกรันสคริปต์พร้อมกันจำนวนมาก ระบบจะต้องมีกลไกจัดการผลลัพธ์ไม่ให้ตีกัน

- **แนวคิด:** Nornir มองทุกชุดคำสั่งเป็น **ภารกิจ (Task)** คุณจะต้องฝึกเขียนฟังก์ชันในรูปแบบที่รับออบเจกต์ `Task` เข้าไปประมวลผล
    
- **ผลลัพธ์:** ข้อมูลที่ตอบกลับมาจะไม่ได้เป็น String หรือ Dictionary ธรรมดาอีกต่อไป แต่จะถูกห่อหุ้มด้วยโครงสร้างข้อมูลเฉพาะของ Nornir ที่เรียกว่า `AggregatedResult` ซึ่งจะรวบรวมผลลัพธ์จากทุกอุปกรณ์ (ทั้งตัวที่ทำงานสำเร็จและตัวที่เชื่อมต่อล้มเหลว) มารวมไว้ที่เดียวกัน ทำให้คุณเขียนโค้ดเพื่อตรวจสอบข้อผิดพลาด (Error handling) แบบรวมศูนย์ได้ง่าย
    

### 4. ระบบ Plugins (ปลั๊กอินส่วนขยาย)

- **แนวคิด:** ตัว Nornir เปล่าๆ ไม่สามารถเชื่อมต่อกับ Router ได้ด้วยตัวเอง มันทำหน้าที่เพียงจัดคิว ประมวลผลแบบขนาน และจัดการ Inventory
    
- **การนำไปใช้:** คุณจะต้องเรียนรู้วิธีการติดตั้งและเรียกใช้งาน Plugins เช่น `nornir_netmiko`, `nornir_napalm`, หรือ `nornir_scrapli` เพื่อบอกให้ Nornir รู้ว่า "สำหรับ Task นี้ ให้ลงไปใช้ Netmiko ในการส่งคำสั่งนะ

## ตารางเปรียบเทียบการเปลี่ยนผ่าน (Conceptual Shift)

| **หัวข้อความแตกต่าง**     | **Netmiko / NAPALM**                               | **Nornir**                                      |
| ------------------------- | -------------------------------------------------- | ----------------------------------------------- |
| **สโคปการทำงาน**          | สั่งงานอุปกรณ์ **1 ตัว** ต่อ 1 เซสชัน              | บริหารจัดการอุปกรณ์ **ทั้งเครือข่าย** พร้อมกัน  |
| **การจัดเก็บ Inventory**  | เก็บในตัวแปร Python หรือวนลูปอ่านไฟล์ CSV          | ใช้โครงสร้างไฟล์ YAML (Hosts, Groups, Defaults) |
| **ความเร็วในการประมวลผล** | ช้า (เรียงลำดับคิวทีละตัวด้วย For loop)            | เร็วมาก (ทำแบบขนานด้วย Threads)                 |
| **กลไกการส่งคำสั่ง**      | เรียกใช้เมธอดตรงๆ (เช่น `send_command`)            | ห่อลอจิกไว้ใน `Task` แล้วสั่ง `nornir.run()`    |
| **สถานะของเครื่องมือ**    | เป็นไลบรารีสำหรับ "เชื่อมต่อ" (Connection Library) | เป็น "เฟรมเวิร์ก" (Automation Framework)        |
