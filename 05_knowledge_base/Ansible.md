- **ประเภท:** เครื่องมือจัดการการตั้งค่าระบบ (Configuration Management Tool) แบบ Agentless)

- **หน้าที่หลัก:** ควบคุมสถานะการทำงานและการตั้งค่าของอุปกรณ์เครือข่ายผ่านไฟล์รูปแบบ YAML (เรียกว่า Playbooks)
    
- **จุดเด่น:** ใช้แนวคิดแบบ **Declarative** คือผู้เขียนสคริปต์ระบุเพียงแค่ "สถานะปลายทางที่ต้องการ" แล้วปล่อยให้ระบบจัดการส่วนที่เหลือเอง เรียนรู้ง่าย ไม่จำเป็นต้องมีทักษะการเขียนโปรแกรมระดับสูง มีโมดูลสำเร็จรูปสำหรับอุปกรณ์เครือข่ายให้เลือกใช้จำนวนมาก
    
- **ข้อจำกัด:** การทำงานเป็นแบบลำดับขั้น (Step-by-step) บนระบบโครงสร้างพื้นฐานขนาดใหญ่อาจทำรอบได้ช้ากว่า Nornir และการควบคุมตรรกะที่ซับซ้อนผ่านโครงสร้าง YAML ทำได้ยากกว่าการเขียนโค้ดโปรแกรมโดยตรง
ลิงค์ : https://docs.ansible.com/


จุดเชื่อมโยงสำคัญที่ทำให้องค์กรหรือวิศวกรเครือข่ายขยับจากการใช้ Nornir (หรือ Python Scripts) ไปสู่ **Ansible** คือเรื่องของ **"ความซับซ้อนในการดูแลรักษาโค้ด (Maintainability)"** และ **"แนวคิดการจัดการสถานะ (State Management)"** ครับ

หากคุณใช้ Nornir คุณจะพบว่ามันทำงานได้รวดเร็วมาก แต่เมื่อระบบใหญ่ขึ้น ตรรกะเงื่อนไขต่างๆ (if/else) จะเริ่มซับซ้อน และไม่ใช่ทุกคนในทีม Network จะเขียน Python ได้คล่องแคล่ว นี่คือจุดที่ Ansible เข้ามาตอบโจทย์ โดยมีคอนเซปต์ที่เป็นจุดเชื่อมโยงดังนี้:

### 1. การเปลี่ยนจาก Imperative สู่ Declarative

- **ฝั่ง Nornir (Imperative):** คุณต้องเขียนโค้ดบอกระบบว่า **"ต้องทำอย่างไร (How)"** ทีละขั้นตอน เช่น 1. ล็อกอิน 2. เช็คว่ามี VLAN 10 ไหม 3. ถ้าไม่มีให้สร้าง 4. บันทึกผล
    
- **ฝั่ง Ansible (Declarative):** คุณเปลี่ยนมาบอกระบบแค่ว่า **"ต้องการผลลัพธ์อะไร (What)"** เช่น ประกาศในไฟล์ YAML ว่า "อุปกรณ์ตัวนี้ต้องมี VLAN 10" จากนั้น Ansible จะไปจัดการหาวิธีลงมือทำ (ขั้นตอนที่ 1-4) เบื้องหลังให้เอง คุณไม่ต้องเขียนลอจิกการทำงานเหล่านั้นเลย

### 2. แนวคิด Idempotency (ทำซ้ำกี่ครั้งก็ได้ผลลัพธ์เดิม)

- นี่คือฟีเจอร์ที่สำคัญที่สุดของ Ansible หากคุณรันสคริปต์ Netmiko เพื่อสร้าง VLAN 10 ซ้ำ 2 รอบ ระบบอาจจะฟ้อง Error หรือเกิดความซ้ำซ้อน เพราะมันจะพยายามสร้างใหม่ทุกครั้ง (หากคุณไม่เขียนโค้ดดักไว้)
    
- แต่ใน Ansible โมดูลเครือข่ายถูกออกแบบมาให้เป็น **Idempotent** มันจะเข้าไป "ตรวจสอบสถานะปัจจุบัน" ของ Router ก่อนเสมอ ถ้าระบบมี VLAN 10 อยู่แล้ว มันจะไม่ทำอะไรและแจ้งสถานะเป็น `OK` แต่ถ้ายังไม่มี มันถึงจะสร้างให้และแจ้งเป็น `Changed` ช่วยลดความเสี่ยงที่สคริปต์จะทำให้เครือข่ายพังจากการรันซ้ำ
    
### 3. เปลี่ยนจาก Developer สู่ Operator (YAML Playbooks)

- Nornir บังคับให้คุณเป็นโปรแกรมเมอร์ (เขียน Python) แต่ Ansible ออกแบบมาให้คุณเป็นผู้ควบคุมระบบ (Operator) โดยใช้ภาษา **YAML** ซึ่งอ่านง่ายเหมือนภาษาคน (Human-readable)
    
- การส่งต่อสคริปต์ (Playbooks) ให้เพื่อนร่วมทีมที่ไม่ได้จบสาย Software Engineer มาสามารถทำได้ง่ายกว่ามาก การแก้ไขค่าต่างๆ ก็แค่แก้ในไฟล์ Text ธรรมดา

### 4. โมดูลสำเร็จรูป (Built-in Modules / Collections)

- แทนที่คุณจะต้องเขียน Plugin เพื่อไปสั่งงานอุปกรณ์แต่ละค่ายเอง Ansible มี Community และ Vendors (เช่น Cisco, Arista, Juniper) พัฒนาโมดูลสำเร็จรูปมาให้พร้อมใช้ คุณแค่เรียกชื่อโมดูลและใส่ตัวแปร ระบบก็พร้อมทำงานทันที
    
### ตารางสรุปจุดเปลี่ยนจาก Nornir สู่ Ansible

|**หัวข้อ**|**Nornir (Python Framework)**|**Ansible (Automation Platform)**|
|---|---|---|
|**แนวคิดการทำงาน**|Imperative (สั่งให้ทำทีละก้าว)|Declarative (ประกาศสถานะปลายทางที่ต้องการ)|
|**ภาษาที่ใช้เขียน**|Python 100%|YAML (Playbooks)|
|**ความยืดหยุ่นในการเขียนลอจิก**|สูงสุด (ทำได้ทุกอย่างที่ Python ทำได้)|ปานกลาง (ถูกตีกรอบด้วยโครงสร้าง YAML)|
|**การจัดการสถานะ (Idempotency)**|ต้องเขียนลอจิกตรวจสอบสถานะเอาเอง|จัดการให้โดยอัตโนมัติผ่าน Modules|
|**การเรียนรู้สำหรับทีม Network**|ต้องใช้เวลาเรียนรู้การเขียนโปรแกรม|เรียนรู้ง่าย เข้าใจโครงสร้างได้เร็วกว่า|

**สรุปจุดเชื่อมโยง:** คุณจะขยับไปหา Ansible เมื่อคุณต้องการ **"แพลตฟอร์มที่เป็นมาตรฐานกลางสำหรับทีม"** ที่ไม่ต้องพึ่งพาคนเขียน Python เก่งๆ เพียงคนเดียว และต้องการระบบที่จัดการสถานะของคอนฟิกอุปกรณ์ได้อย่างปลอดภัย รันซ้ำได้โดยไม่เกิดข้อผิดพลาดครับ


### คอนเซปต์หลักที่ต้องศึกษาเมื่อเข้าสู่ Ansible

การเปลี่ยนมาใช้ Ansible ในระบบเครือข่ายคือการเปลี่ยนกระบวนทัศน์ (Paradigm) จากการเขียนโปรแกรมเพื่อสั่งงานทีละขั้นตอน (Imperative) มาเป็นการประกาศสถานะปลายทางที่ต้องการ (Declarative) หัวข้อแกนกลางที่ต้องทำความเข้าใจมี 5 เรื่องหลัก ดังนี้:

**1. สถาปัตยกรรมแบบ Agentless (การทำงานโดยไม่ต้องติดตั้งโปรแกรมที่ปลายทาง)**

- **Concept:** Ansible ไม่จำเป็นต้องติดตั้งซอฟต์แวร์หรือ Agent ใดๆ ลงบนอุปกรณ์เครือข่าย โดยจะอาศัยโปรโตคอลมาตรฐานที่มีอยู่แล้วในระบบ เช่น SSH, NETCONF, หรือ REST API เป็นช่องทางในการเชื่อมต่อ
    
- **สิ่งที่ต้องโฟกัส:** วิธีการตั้งค่าพารามิเตอร์ `ansible_connection` (เช่น ใช้ `network_cli` สำหรับ CLI ทั่วไป หรือใช้ `netconf`) เพื่อให้เหมาะสมกับช่องทางการสื่อสารของอุปกรณ์แต่ละค่าย (เช่น Cisco, MikroTik, Huawei)

**2. Idempotency และแนวคิดแบบ Declarative (ผลลัพธ์คงที่และการกำหนดเป้าหมาย)**

- **Concept:** นี่คือหัวใจสำคัญที่สุดของการใช้เครื่องมือประเภท Configuration Management
    
    - **Declarative:** ผู้ใช้งานกำหนดเพียงแค่ "สิ่งที่ต้องการให้เป็น" (เช่น อุปกรณ์ตัวนี้ต้องมี VLAN 10) ระบบจะหาวิธีดำเนินการเองโดยไม่ต้องเขียนลอจิก if/else
        
    - **Idempotency:** การรัน Playbook ซ้ำ 10 ครั้ง หรือ 100 ครั้ง จะต้องได้สถานะเครือข่ายแบบเดิมเสมอ ระบบจะทำการ "ตรวจสอบสถานะปัจจุบัน" ก่อนดำเนินการ หากสถานะตรงกับเป้าหมายแล้ว ระบบจะข้ามการทำงานนั้นไป (แสดงผลเป็น `OK` แทนที่จะเป็น `Changed`)
        
- **สิ่งที่ต้องโฟกัส:** การทำความเข้าใจพฤติกรรมของ Network Modules ต่างๆ ว่ามีการจัดการสถานะ Idempotent ได้สมบูรณ์หรือไม่เมื่อเทียบกับการส่งคำสั่งแบบเดิม

**3. โครงสร้าง Playbooks, Plays และ Tasks (การเขียน YAML)**

- **Concept:** ชุดคำสั่งของ Ansible จะถูกเขียนขึ้นด้วยภาษา YAML ซึ่งอ่านเข้าใจง่ายเหมือนภาษามนุษย์ โครงสร้างจะเริ่มจาก Playbook (ไฟล์หลัก) $\rightarrow$ Plays (กำหนดกลุ่มเป้าหมายที่จะรัน) $\rightarrow$ Tasks (งานที่ต้องทำตามลำดับ)
    
- **สิ่งที่ต้องโฟกัส:** กฎการเว้นวรรค (Indentation) และโครงสร้าง Data Model ของ YAML รวมถึงข้อควรระวังอย่างยิ่งยวดในการเขียนไฟล์ YAML คือห้ามมีอักขระแปลกปลอมหรือรูปแบบ Citation tags หลุดเข้าไปในโค้ดอย่างเด็ดขาด เพราะจะทำให้ระบบเกิด Runtime error ระหว่างการประมวลผล

**4. ระบบ Inventory และตัวแปร (การบริหารจัดการกลุ่มอุปกรณ์)**

- **Concept:** การแยกเป้าหมายและข้อมูลเฉพาะออกจากตัวโค้ด โดยจัดเก็บรายชื่ออุปกรณ์ IP Address และรหัสผ่านไว้ในไฟล์ Inventory (รองรับทั้งรูปแบบ INI และ YAML)
    
- **สิ่งที่ต้องโฟกัส:** การจัดกลุ่มอุปกรณ์แบบมีลำดับชั้น (Hierarchical grouping) และวิธีการกำหนดค่าตัวแปรระดับกลุ่ม (`group_vars`) และระดับอุปกรณ์ (`host_vars`) เพื่อใช้เป็นฐานข้อมูล (Source of Truth) ของเครือข่าย

**5. Modules และ Collections (การใช้เครื่องมือสำเร็จรูป)**

- **Concept:** Ansible ขับเคลื่อนด้วย Modules สำเร็จรูปที่พัฒนาโดยชุมชนและผู้ผลิตอุปกรณ์โดยตรง องค์กรสามารถเรียกใช้ Collections เฉพาะค่าย (เช่น `cisco.ios`, `community.network.routeros`) เพื่อจัดการการตั้งค่าอุปกรณ์โดยไม่ต้องเขียน Parser ดึงข้อมูลเอง
    
- **สิ่งที่ต้องโฟกัส:** โครงสร้างการทำงานของ Network Modules ที่มักจะแยกเป็นหมวดหมู่ย่อย (เช่น `_command`, `_config`, `_facts`) และวิธีการดึงตัวแปรที่คืนค่ากลับมา (Registered variables) ไปใช้ใน Task ถัดไป

### เจาะลึกข้อจำกัด (Limitations) ของแต่ละเทคโนโลยี

ในการพัฒนาระบบจัดการและตั้งค่าเครือข่ายแบบอัตโนมัติที่ต้องรองรับการทำงานร่วมกับอุปกรณ์ที่หลากหลาย (เช่น Cisco, MikroTik, หรือ Huawei) ข้อจำกัดของแต่ละเครื่องมือจะส่งผลต่อการออกแบบสถาปัตยกรรมซอฟต์แวร์โดยตรง ดังนี้:

#### 1. ข้อจำกัดของ Netmiko (ยุคเริ่มต้นของการเขียนสคริปต์)

- **การจัดการข้อความดิบ:** ข้อมูลที่ได้กลับมาเป็น String การนำไปใช้งานต่อต้องเขียนตัวตัดคำ (Parser) เช่น TextFSM ซึ่งหากอุปกรณ์มีการอัปเดตเวอร์ชันและเว้นวรรคเปลี่ยนไป สคริปต์จะทำงานผิดพลาดทันที
    
- **ขาดความยืดหยุ่นข้ามผู้ผลิต:** ต้องเขียนโค้ดแยกกันชัดเจนตามยี่ห้อ (เช่น ชุดคำสั่งดึงค่า Interface ของ Cisco จะต่างจาก MikroTik โดยสิ้นเชิง) ทำให้โค้ดมีความซับซ้อนและยาวขึ้นเมื่อระบบขยายตัว
    
- **ทำงานแบบ Sequential:** โดยพื้นฐานจะเชื่อมต่ออุปกรณ์แบบเรียงลำดับทีละตัว หากเครือข่ายมีขนาดใหญ่จะใช้เวลาประมวลผลนานมาก
    

#### 2. ข้อจำกัดของ NAPALM (ยุคของการทำ Data Abstraction)

- **การรองรับอุปกรณ์ (Core Support) จำกัด:** รองรับระบบปฏิบัติการหลักเพียงไม่กี่ค่าย (ส่วนใหญ่เป็นกลุ่ม Data Center เช่น Cisco IOS-XR/NX-OS, Arista, Juniper) หากต้องการใช้กับอุปกรณ์ค่ายอื่น ต้องพึ่งพา Community Drivers ซึ่งอาจเสถียรน้อยกว่าหรือมีฟังก์ชันให้ใช้น้อยกว่า
    
- **ข้อจำกัดเรื่อง "ตัวหารร่วมน้อย" (Lowest Common Denominator):** NAPALM จะมีฟังก์ชัน Getters ให้ใช้เฉพาะฟีเจอร์ที่ทุกยี่ห้อมีตรงกันเท่านั้น หากอุปกรณ์ตัวใดตัวหนึ่งมีฟีเจอร์พิเศษเฉพาะค่าย จะไม่สามารถจัดการผ่าน API มาตรฐานของ NAPALM ได้
    
- **กระบวนการ Configuration ที่ซับซ้อนในบาง OS:** การทำ Compare หรือ Rollback บนอุปกรณ์รุ่นเก่าที่ไม่มีระบบ Transaction (เช่น Cisco IOS รุ่นเก่า) อาจทำได้ช้าและมีความเสี่ยงที่คอนฟิกจะไม่สมบูรณ์
    

#### 3. ข้อจำกัดของ Nornir (ยุคของ Framework และ Concurrency)

- **Learning Curve ด้านโปรแกรมมิ่งสูง:** ผู้ใช้งานต้องมีความเข้าใจภาษา Python อย่างลึกซึ้ง (เช่น การจัดการ Object, Error Handling, Threading) ซึ่งอาจเป็นอุปสรรคสำหรับทีมดูแลเครือข่ายที่คุ้นเคยกับ CLI มากกว่า
    
- **ไม่มี Idempotency ในตัว:** Nornir ทำตามคำสั่งแบบตรงไปตรงมา หากสั่งเพิ่ม VLAN 10 ซ้ำไป 5 รอบ มันก็จะพยายามยิงคำสั่งเข้าไป 5 รอบ การจะทำให้ระบบรู้ว่า "ถ้ามีอยู่แล้วไม่ต้องทำ" ผู้พัฒนาต้องเขียนตรรกะ (Logic) ตรวจสอบสถานะก่อนทำงานขึ้นมาเองทั้งหมด
    
- **ต้องพึ่งพาระบบนิเวศ (Ecosystem):** Nornir ทำงานเดี่ยวๆ ไม่ได้ ต้องเรียกใช้ Plugin (เช่น `nornir_netmiko`, `nornir_napalm`) ทำให้เมื่อเกิด Error ต้องวิเคราะห์ว่าปัญหามาจากตัว Nornir เอง หรือมาจาก Plugin
    

#### 4. ข้อจำกัดของ Ansible (ยุคของ Declarative Platform)

- **ประสิทธิภาพและความเร็ว (Performance):** แม้จะทำงานแบบคู่ขนานได้ แต่โครงสร้างเบื้องหลังของ Ansible ที่ต้องแปลง YAML ส่งผ่าน Python Modules ทำให้ความเร็วในการทำงาน (Execution time) ช้ากว่า Nornir อย่างมีนัยสำคัญเมื่อใช้กับอุปกรณ์จำนวนหลักร้อยหรือหลักพันตัว
    
- **ความซับซ้อนในการเขียน Logic:** ภาษา YAML ออกแบบมาให้อ่านง่าย แต่ไม่ได้ออกแบบมาให้เขียนตรรกะซับซ้อน (เช่น การทำ Nested Loops, การเช็คเงื่อนไข If/Else ซ้อนกันหลายชั้น) การฝืนทำลอจิกซับซ้อนใน YAML Playbook จะทำให้อ่านและแก้บั๊กได้ยากมาก
    
- **ข้อกำหนดด้านโครงสร้างไฟล์:** ต้องปฏิบัติตามโครงสร้างของ Inventory และ Role อย่างเคร่งครัด หากเว้นวรรค (Indentation) ในไฟล์ YAML ผิดพลาดแม้แต่ตัวเดียว ระบบจะแสดง Runtime Error และหยุดทำงานทันที
    

มื่อเข้าสู่เรื่อง [Ansible](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_intro.html#playbook-syntax) อย่างที่เราได้คุยกันไปว่านี่คือการเปลี่ยนผ่านจาก "การเขียนโค้ดเพื่อสั่งงาน (Imperative)" มาเป็น "การประกาศสถานะที่ต้องการ (Declarative)"

การทำงานกับ Ansible จะไม่ได้เขียนตรรกะโปรแกรมมิ่ง (If/Else, For Loop) ด้วย Python แบบ Nornir แต่จะเปลี่ยนมาใช้การเขียนไฟล์ตั้งค่าด้วยภาษา YAML แทน เพื่อให้ระบบอ่านแล้วนำไปจัดการเครือข่ายให้อัตโนมัติ โดยมีองค์ประกอบพื้นฐาน 4 ส่วนที่ต้องทำความเข้าใจเพื่อเริ่มต้นใช้งานครับ:

### 1. องค์ประกอบพื้นฐานของ Ansible

- **Inventory:** ระบบฐานข้อมูลอุปกรณ์ สามารถเขียนเป็นไฟล์ INI หรือ YAML ก็ได้ ใช้เพื่อจัดกลุ่มอุปกรณ์ตามประเภท (เช่น แยกกลุ่ม Cisco, MikroTik, Huawei) และกำหนดตัวแปรของแต่ละกลุ่ม
    
- **Modules / Collections:** เครื่องมือสำเร็จรูปที่ Ansible เตรียมไว้ให้ หากต้องการไปตั้งค่าอุปกรณ์ยี่ห้อไหน ก็เพียงแค่เรียกใช้ Module ของยี่ห้อนั้น เช่น `cisco.ios.ios_config` หรือ `community.network.routeros_command` โดยไม่ต้องมานั่งเขียนโค้ดตัดคำเอง
    
- **Playbook:** แผนการทำงานหลัก เขียนด้วยภาษา YAML ภายในหนึ่ง Playbook จะทำงานจากบนลงล่างตามลำดับเสมอ
    
- **Tasks:** ภารกิจย่อยที่บรรจุอยู่ใน Playbook โดยแต่ละ Task จะเป็นการเรียกใช้ 1 Module เพื่อทำงาน 1 อย่างให้เสร็จสมบูรณ์
    

---

### 2. โครงสร้างไฟล์ Playbook พื้นฐาน

อ้างอิงจากหลักการทำงาน อย่างน้อยที่สุดในหนึ่ง Playbook จะต้องระบุ 2 อย่างคือ **เป้าหมาย (hosts)** และ **งานที่ต้องทำ (tasks)** ข้อควรระวังที่สำคัญมากในการเขียนไฟล์นี้คือ โครงสร้าง YAML จะต้องสะอาด เคาะเว้นวรรคให้ถูกต้อง และต้องไม่มีอักขระแปลกปลอมหรือแท็กอ้างอิงใดๆ หลุดเข้าไปเด็ดขาด เพราะจะทำให้เกิด Runtime Error ทันที 
```yaml
---
- name: Configure and Backup Network Devices
  hosts: cisco_routers # ระบุกลุ่มเป้าหมายจาก Inventory
  gather_facts: false  # ปิดการดึงข้อมูลพื้นฐานของ Server (เพราะนี่คืออุปกรณ์ Network)

  tasks:
    - name: Ensure VLAN 10 exists
      cisco.ios.ios_vlans:
        config:
          - vlan_id: 10
            name: WEB_VLAN
        state: merged

    - name: Save running configuration to startup
      cisco.ios.ios_config:
        save_when: modified
```

_สังเกตว่าเราไม่ต้องเขียนโค้ดบอกว่า "ให้เชื่อมต่อ SSH -> พิมพ์ conf t -> พิมพ์ vlan 10" แต่เราแค่บอก Ansible ว่า "VLAN 10 ต้องมีชื่อว่า WEB_VLAN" (Declarative) ถ้าระบบมีอยู่แล้วมันจะไม่ทำอะไรซ้ำให้เกิด Error แต่ถ้าไม่มี มันจะสร้างให้เอง (Idempotency)_

---

### 3. คำสั่งพื้นฐานที่ใช้ในการทำงาน

เมื่อเราเขียนไฟล์ Inventory และ Playbook เสร็จแล้ว การสั่งรันจะทำผ่าน Command Line เป็นหลัก:

- **`ansible-playbook -i inventory.yaml playbook.yaml`** คำสั่งหลักที่ใช้รัน Playbook โดย `-i` คือการระบุไฟล์ Inventory
    
- **`ansible-playbook --check playbook.yaml`** (Check Mode) ใช้สำหรับทดสอบรันแบบจำลอง (Dry-run) เพื่อดูว่า ถ้ารันจริงๆ จะมีคอนฟิกอะไรบนอุปกรณ์เปลี่ยนไปบ้าง โดยที่ยังไม่มีการแก้ไขค่าจริงๆ บนอุปกรณ์ เหมาะมากสำหรับการทำ Pre-validation
    

### 4. ข้อพิจารณาเมื่อนำมาต่อยอดในสถาปัตยกรรมซอฟต์แวร์

หากคุณกำลังพัฒนาระบบที่มี Backend เป็น FastAPI และมี Frontend Dashboard รอรับข้อมูล การเลือกใช้เครื่องมือจะมีผลต่อสถาปัตยกรรมโดยตรง:

- **การทำงานกับ Nornir:** เนื่องจากเป็น Python 100% จึงสามารถ Import เข้าไปเป็นส่วนหนึ่งของ Route/Endpoint ใน FastAPI ได้เลย การทำงานร่วมกับ Database (เช่น SQLAlchemy) จึงทำได้แนบเนียนและลื่นไหล
    
- **การทำงานกับ Ansible:** ตัวมันเองเป็น Command Line Tool ที่แยกส่วนออกมา หากต้องการให้ Backend สั่งงาน Ansible จะต้องใช้วิธีเรียกผ่าน `subprocess` ของ Python หรือใช้ไลบรารีอย่าง `ansible-runner` ซึ่งอาจจะเพิ่มความซับซ้อนในการจัดการผลลัพธ์ที่เป็น JSON เล็กน้อย แต่แลกมากับการรองรับการทำงานข้ามค่ายได้ง่ายโดยไม่ต้องเขียน Data Models (YANG/Parsers) เองเยอะ
    

เพื่อนำไปใช้ตัดสินใจในการออกแบบระบบ คุณต้องการดูตัวอย่างการเปรียบเทียบโค้ดแบบ Side-by-Side ระหว่าง "การสร้าง VLAN ด้วย Nornir" เทียบกับ "การสร้าง VLAN ด้วย Ansible" เพื่อให้เห็นโครงสร้างความแตกต่างชัดเจนขึ้นไหมครับ?
