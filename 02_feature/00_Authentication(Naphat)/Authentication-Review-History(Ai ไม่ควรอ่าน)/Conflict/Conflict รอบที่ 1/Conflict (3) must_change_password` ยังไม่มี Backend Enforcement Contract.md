**ไม่ต้องสนใจเลยครับ ตัดทิ้งตามกันไปได้เลย!"

เรื่องนี้มันเป็นโดมิโน่ที่ล้มตามกันครับ:
1. **ตัด** ฟีเจอร์ "Admin กดรีเซ็ตรหัสผ่านให้ลูกน้องบนหน้าเว็บ" ทิ้ง (ใช้วิธี Seed User ทดสอบลงฐานข้อมูลตอนรันโปรเจกต์แทน)
2. 👉 **ส่งผลให้:** ไม่มีระบบ "รหัสผ่านชั่วคราว (Temporary Password)"
3. 👉 **ส่งผลให้:** ไม่จำเป็นต้องมีคอลัมน์ `must_change_password` ใน Database
4. 👉 **ส่งผลให้:** ไม่ต้องไปเสียเวลาเขียนโค้ด Backend Enforcement ดัก API (ประหยัดเวลาทำ Middleware ไปได้อีกเยอะ)
5. 👉 **ส่งผลให้:** ไม่ต้องเขียนโค้ดหน้าเว็บ Frontend เพื่อทำหน้าบังคับเปลี่ยนรหัสผ่าน

**สรุปคือ:** ถ้าเราตกลงกันว่า MVP P1 จะไม่มีฟีเจอร์ Admin Reset Password เราก็ปัดตกรีวิวของ GPT เรื่อง Backend Enforcement ข้อนี้ทิ้งไปได้เลยครับ เพราะฟีเจอร์นี้ไม่ได้อยู่ในระบบเราตั้งแต่แรก

**เพื่อให้เอกสารของเราตอนนี้ตรงกับภาพความเป็นจริงที่สุด (Lean MVP)** 
คุณต้องการให้ผมใช้เครื่องมือ **เข้าไปลบ** กฎข้อบังคับเกี่ยวกับ `must_change_password`, เรื่อง Temporary Password และแก้เคส Acceptance Tests ที่เกี่ยวกับเรื่องนี้ออกจากเอกสารทั้ง 6 ไฟล์เลยไหมครับ? (เอกสารของทีมจะได้คลีนๆ ไม่มีฟีเจอร์ขยะที่ไม่ได้ทำค้างอยู่ครับ)

### 3. `must_change_password` ยังไม่มี Backend Enforcement Contract

Flow บอกว่า “บังคับก่อนเข้า feature อื่น” แต่ยังไม่ระบุว่า backend ต้องอนุญาตเฉพาะ:

- `/api/auth/me`
- `/api/auth/change-password`
- `/api/auth/logout`

หากอาศัย frontend redirect อย่างเดียว ผู้ใช้ยังเรียก Feature API โดยตรงได้

ประเด็นนี้ GPT กำลังเตือนเรื่องความแตกต่างระหว่าง **"ความปลอดภัยหลอกๆ (Frontend)"** กับ **"ความปลอดภัยที่แท้จริง (Backend)"** ครับ

ผมขอเปรียบเทียบให้เห็นภาพชัดๆ แบบนี้ครับ:

สมมติว่าแอดมินสร้างรหัสผ่านชั่วคราวให้คุณ และตั้งค่าว่า "คุณต้องเปลี่ยนรหัสผ่านก่อนเข้าใช้งานนะ"
*   **ถ้าเราป้องกันแค่ฝั่งหน้าเว็บ (Frontend Redirect):** 
    พอคุณล็อกอินปุ๊บ หน้าเว็บจะเด้งพาคุณไปที่หน้า "กรุณาเปลี่ยนรหัสผ่าน" ทันที... ดูเหมือนจะปลอดภัยใช่ไหมครับ?
    แต่มันเหมือนการเอาป้าย **"ห้ามเข้า"** ไปวางไว้หน้าประตูครับ คนทั่วไปเห็นป้ายก็คงเดินไปเปลี่ยนรหัสผ่าน แต่ถ้าเป็นโปรแกรมเมอร์หัวหมอ หรือแฮกเกอร์ เขาจะไม่ใช้หน้าเว็บครับ เขาจะใช้โปรแกรมอย่าง Postman (เครื่องมือยิง API โดยตรง) ยิงคำสั่งทะลุป้ายห้ามเข้านี้ไปสั่งงานสวิตช์เครือข่ายได้เลย เพราะเซิร์ฟเวอร์ (Backend) ไม่ได้ล็อกประตูไว้!
*   **สิ่งที่ GPT แนะนำ (Backend Enforcement):** 
    คือการเอา **"แม่กุญแจ"** ไปล็อกที่ตัวเซิร์ฟเวอร์เลยครับ โดยตั้งกฎที่ Backend ว่า ถ้าไอดีนี้มีสถานะ `must_change_password = true` เมื่อไหร่ **ระบบ Backend จะดักตบทุกๆ คำขอ (API) ให้ร่วงหมด** (ตอบ `403 Forbidden` แจ้งว่าไม่มีสิทธิ์) 

เซิร์ฟเวอร์จะ **อนุญาตให้วิ่งผ่านได้แค่ 3 เส้นทาง (API) เท่านั้น** คือ:
1.  `/api/auth/me` (เพื่อให้หน้าเว็บโหลดข้อมูลได้ว่า คนนี้ชื่ออะไร และติดล็อกรหัสผ่านอยู่ไหม)
2.  `/api/auth/change-password` (เพื่อให้เขาส่งรหัสผ่านใหม่มาปลดล็อกตัวเอง)
3.  `/api/auth/logout` (เผื่อเขาเปลี่ยนใจไม่อยากใช้ระบบแล้ว ก็กดล็อกเอาต์ออกไป)

ถ้าเขาพยายามจะเรียก API ฟีเจอร์อื่น เช่น `/api/admin/users` หรือ `/api/devices` ระบบ Backend จะดีดออกทันที แม้ว่าเขาจะเป็น Admin ก็ตามครับ

### เราต้องปรับเอกสารอย่างไร?

นี่เป็นเรื่องที่ขาดหายไปในเอกสารจริงๆ ครับ และเป็นจุดที่อาจารย์ที่ปรึกษาที่เชี่ยวชาญด้าน Security มักจะถามจี้ตอนตรวจโปรเจกต์ (Defend) 

เพื่อให้เอกสารแน่นปึ้ก เราควร:
1.  **ไปแก้ไฟล์ `04_API Contracts.md`**: เพิ่มกฎข้อนี้ลงไปในส่วน Security Considerations ว่า Backend ต้อง Block API อื่นๆ ทั้งหมด และคืนค่า Error Code ชัดเจน เช่น `403 PASSWORD_CHANGE_REQUIRED` 
2.  **ไปแก้ไฟล์ `05_Acceptance Tests.md`**: เพิ่มเคสทดสอบว่า *"ถ้าบัญชีติดสถานะนี้ แล้วพยายามใช้ Postman ยิงไปที่ API จัดการอุปกรณ์ ระบบต้องปฏิเสธ"*

ถ้าคุณอยากให้ผมจัดการอุดช่องโหว่ทั้งเรื่อง **"Case-insensitive + ห้ามใช้ @"** (จากข้อที่แล้ว) และเรื่อง **"Backend Enforcement"** (จากข้อนี้) ลงในเอกสารให้สมบูรณ์เลย สั่งผมได้เลยนะครับ!
