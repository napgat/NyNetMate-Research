# สรุปคำแนะนำของอาจารย์ที่ปรึกษา ครั้งที่ 4 ปี 3 เทอม 1

**วันที่ประชุม:** 7 สิงหาคม 2026

**ที่มา:** เรียบเรียงจากบันทึกย่อหลังการพูดคุย เนื่องจากไม่มี Transcript ฉบับเต็ม จึงเก็บประเด็นที่ยังไม่ชัดเจนไว้เป็นเรื่องรอยืนยันและไม่ขยายความเกินข้อมูลต้นฉบับ

> เอกสารนี้เป็นบันทึกคำแนะนำ ณ วันที่ประชุม ไม่ใช่ข้อสรุปขอบเขตโครงงานฉบับล่าสุด การตัดสินใจเรื่องฟีเจอร์และลำดับการพัฒนาในปัจจุบันให้อ้างอิง [MyNetMate Weight Feature List](../../02_feature/MyNetMate%20Weight%20Feature%20List.md)

## 1. ข้อมูลที่ควรพิจารณาแสดงบนแดชบอร์ด (Dashboard)

จากบันทึก อาจารย์เสนอให้พิจารณาว่าแดชบอร์ดควรแสดงข้อมูลต่อไปนี้หรือไม่:

- เครือข่ายเสมือน (VLAN)
- ข้อมูลคอนฟิก (Configuration)
- โหมดของพอร์ต เช่น Access Mode และ Trunk Mode
- สถานะพอร์ต (Port Status)
- สถานะลิงก์ (Link Status)

ยังต้องกำหนดต่อว่าข้อมูลใดจำเป็นต่อผลิตภัณฑ์ขั้นต่ำที่ใช้งานได้ (Minimum Viable Product: MVP) และข้อมูลใดควรอยู่ในหน้ารายละเอียดแทนหน้าสรุป

## 2. ความสัมพันธ์ระหว่างฟีเจอร์ (Dependency)

ต้องระบุว่าแต่ละฟีเจอร์ขอใช้ข้อมูลหรือความสามารถจากส่วนใด และส่วนใดต้องเสร็จก่อนจึงจะเริ่มอีกส่วนได้

- มีคำว่า **LLCP** อยู่ในบันทึกเดิม แต่ยังไม่ทราบความหมายที่แน่นอน
- ต้องยืนยันว่าเป็นชื่อระบบภายใน หรือหมายถึงโพรโทคอล **LLDP**
- หากหมายถึง LLDP ต้องระบุว่าฟีเจอร์ใดเป็นผู้เก็บข้อมูล และฟีเจอร์ใดนำข้อมูลเพื่อนบ้านไปใช้

## 3. ขอบเขตของ Group Management Service

ต้องอธิบายให้ชัดเจนว่า Group Management Service จะทำอะไรได้บ้าง โดยบันทึกเดิมระบุหัวข้อที่ต้องพิจารณาไว้ดังนี้:

- VLAN
- Spanning Tree
- OSPF

รายการนี้ยังเป็นเพียงหัวข้อสำหรับกำหนดขอบเขต ไม่ได้หมายความว่าทั้งหมดได้รับการยืนยันให้อยู่ใน MVP แล้ว ทีมต้องพิจารณาความจำเป็น ความเสี่ยง และเวลาในการพัฒนาก่อน

## 4. การออกแบบและเลือกวิธีจัดเก็บข้อมูล

ข้อมูลแต่ละชนิดอาจเหมาะกับวิธีจัดเก็บต่างกัน จึงไม่ควรเลือกฐานข้อมูลเชิงสัมพันธ์ (Relational Database) หรือฐานข้อมูล NoSQL สำหรับทุกข้อมูลโดยยังไม่วิเคราะห์ลักษณะการใช้งาน

สิ่งที่ต้องระบุสำหรับข้อมูลแต่ละกลุ่ม ได้แก่:

- ข้อมูลนั้นคืออะไรและฟีเจอร์ใดเป็นเจ้าของ
- ฟีเจอร์ใดต้องอ่านหรือแก้ไขข้อมูลนั้น
- ข้อมูลมีความสัมพันธ์กับข้อมูลอื่นอย่างไร
- ต้องค้นหา เปรียบเทียบ หรืออ้างอิงย้อนหลังหรือไม่
- จะจัดเก็บในฐานข้อมูลเชิงสัมพันธ์ หรือ NoSQL พร้อมเหตุผล

ผลลัพธ์ที่ต้องการคือ Schema การจัดเก็บข้อมูลและเหตุผลประกอบการเลือกวิธีจัดเก็บ ไม่ใช่เพียงรายชื่อเทคโนโลยี

## 5. ขอบเขตอุปกรณ์ที่กล่าวถึง

บันทึกเดิมกล่าวถึงอุปกรณ์ต่อไปนี้:

- อุปกรณ์สวิตช์ (Switch): MikroTik และ Cisco
- อุปกรณ์กำหนดเส้นทาง (Router): Huawei

รายการนี้ควรถือเป็นอุปกรณ์เป้าหมายสำหรับการศึกษาและทดสอบ ณ เวลานั้น ยังไม่ใช่การยืนยันว่าระบบรองรับทุกฟังก์ชันของทุกยี่ห้อ ต้องยืนยันรุ่น ระบบปฏิบัติการ ชุดคำสั่ง และผลการทดสอบจริงอีกครั้ง

## 6. งานที่ทีมต้องดำเนินการ

1. แบ่งหน้าที่และระบุว่าใครรับผิดชอบฟีเจอร์ใด
2. หา MVP ของฟีเจอร์ที่แต่ละคนรับผิดชอบ
3. อัปเดตความคืบหน้าและข้อสรุปให้สมาชิกคนอื่นทราบ
4. ออกแบบ Schema สำหรับจัดเก็บข้อมูลของแต่ละฟีเจอร์
5. ระบุว่าข้อมูลแต่ละชนิดจะเก็บใน Relational Database หรือ NoSQL พร้อมเหตุผล
6. ระบุ Dependency และข้อตกลงการแลกเปลี่ยนข้อมูลระหว่างฟีเจอร์

## 7. แหล่งข้อมูลหรือผู้ที่ควรสอบถามเพิ่มเติม

บันทึกเดิมระบุให้สอบถามบุคคลหรือหน่วยงานต่อไปนี้เมื่อจำเป็นต้องยืนยันความต้องการของผู้ใช้:

- พี่นัท
- อาจารย์จิ
- KDMC — ยังต้องยืนยันว่าหมายถึงบุคคล หน่วยงาน หรือระบบใด

ก่อนสอบถามควรเตรียมคำถามให้เจาะจง เช่น ผู้ใช้อยากเห็นข้อมูลใดบน Dashboard งานใดทำเป็นกลุ่มบ่อย และข้อมูลใดจำเป็นต่อการตัดสินใจจริง

## 8. ประเด็นที่ยังรอยืนยัน

- คำว่า LLCP ในบันทึกหมายถึง LLDP หรือสิ่งอื่น
- Dashboard ต้องแสดง Config ระดับใด เช่น สรุปสถานะหรือคอนฟิกฉบับเต็ม
- Group Management Service ต้องรองรับ VLAN, Spanning Tree และ OSPF ทั้งหมดหรือไม่
- ฟีเจอร์ใดเป็น MVP และฟีเจอร์ใดควรเลื่อนไปภายหลัง
- ข้อมูลใดมีเหตุผลเพียงพอที่จะใช้ NoSQL แทน Relational Database
- KDMC หมายถึงใครหรือหน่วยงานใด และต้องสอบถามเรื่องใด

## สรุปสั้น

คำแนะนำหลักของการประชุมครั้งนี้คือ ให้แต่ละคนกำหนด MVP ของฟีเจอร์ที่รับผิดชอบ อธิบาย Dependency และออกแบบ Schema โดยระบุเหตุผลในการเลือกวิธีจัดเก็บข้อมูล พร้อมทั้งตรวจสอบว่าข้อมูลบน Dashboard และความสามารถแบบกลุ่มเป็นสิ่งที่ผู้ใช้ต้องการจริงหรือไม่
