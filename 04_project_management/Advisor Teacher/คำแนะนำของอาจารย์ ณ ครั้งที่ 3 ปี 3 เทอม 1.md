# สรุปคำแนะนำของอาจารย์ที่ปรึกษา ครั้งที่ 3 ปี 3 เทอม 1

**วันที่ประชุม:** 31 กรกฎาคม 2026

**ระยะเวลาการสนทนา:** ประมาณ 41 นาที

**ที่มา:** สรุปจากข้อความถอดเสียงการประชุม โดยปรับคำที่ถอดคลาดเคลื่อนให้ตรงกับบริบท เช่น Network Discovery, SNMP, SSH, Device Inventory และ Jinja2

> เอกสารนี้เป็นบันทึกคำแนะนำ ณ วันที่ประชุม ไม่ใช่ข้อสรุปขอบเขตโครงงานฉบับล่าสุด การตัดสินใจเรื่องฟีเจอร์และลำดับการพัฒนาในปัจจุบันให้อ้างอิง [MyNetMate Weight Feature List](../../02_feature/MyNetMate%20Weight%20Feature%20List.md)



## 1. ภาพรวมการประชุม

อาจารย์และทีมทบทวนว่าฟีเจอร์ที่เสนอ เช่น Dashboard, Device Inventory, Network Topology และ Configuration Management ยังตอบโจทย์ผู้ดูแลระบบเครือข่ายหรือไม่ โดยเห็นว่าทิศทางโดยรวมยังสอดคล้องกับกลุ่มผู้ใช้เป้าหมาย แต่ทีมไม่สามารถพัฒนาทุกฟีเจอร์พร้อมกันได้ จึงต้องลงรายละเอียด ประเมินความสำคัญ จัดลำดับ และแบ่งความรับผิดชอบให้ชัดเจนก่อนเริ่มพัฒนา

## 2. การกำหนดขอบเขตและลำดับฟีเจอร์

อาจารย์แนะนำให้ทีมดำเนินการดังนี้:

1. ขยายรายละเอียดว่าฟีเจอร์แต่ละส่วนทำอะไรได้บ้าง
2. ประเมินแต่ละฟีเจอร์จากข้อจำกัดจริง ได้แก่ เวลา จำนวนสมาชิก อุปกรณ์ และความยากทางเทคนิค
3. เลือกว่าส่วนใดต้องทำก่อน ส่วนใดทำภายหลัง และส่วนใดอาจไม่ทำ
4. ระบุความสัมพันธ์และสิ่งที่แต่ละฟีเจอร์ต้องขอใช้จากกัน เพื่อให้เห็นลำดับการพัฒนา
5. แบ่งงานเป็นระบบย่อยที่สามารถพัฒนาคู่ขนานกันได้

ประเด็นสำคัญคือ ทีมไม่ควรรอให้ Network Discovery เสร็จก่อนจึงเริ่มฟีเจอร์อื่น หากกำหนดโครงสร้างข้อมูลกลางและข้อตกลงการเชื่อมต่อระหว่างส่วนต่าง ๆ ไว้ก่อน แต่ละคนสามารถใช้ข้อมูลจำลองในการพัฒนาส่วนของตนได้

## 3. Device Inventory ควรเป็นข้อมูลกลางของระบบ

อาจารย์เสนอให้มอง Device Inventory ฝั่งหลังบ้านเป็นศูนย์กลางของระบบ และออกแบบโครงสร้างข้อมูลให้ตกลงร่วมกันก่อนเริ่มพัฒนา โดยต้องพิจารณาว่าจะเก็บข้อมูลใด เช่น ชื่ออุปกรณ์ ที่อยู่ IP รุ่น ระบบปฏิบัติการ และข้อมูลที่ฟีเจอร์อื่นต้องใช้

ความสัมพันธ์ที่อาจารย์อธิบายไว้คือ:

```text
Network Discovery ──นำข้อมูลอุปกรณ์เข้า──> Device Inventory
Device Inventory  ──ส่งข้อมูลให้─────────> Network Topology
Device Inventory  ──ส่งข้อมูลให้─────────> Configuration Management
```

- Network Discovery มีหน้าที่ค้นหาอุปกรณ์และเพิ่มข้อมูลลง Inventory
- Network Topology อ่านข้อมูลจาก Inventory เพื่อนำไปสร้างแผนผัง
- Configuration Management อ่านข้อมูลอุปกรณ์จาก Inventory เพื่อนำไปสร้างหรือจัดการคอนฟิก

อาจารย์แนะนำให้เริ่มจากฐานข้อมูลเชิงสัมพันธ์ (Relational Database) หากยังไม่มีเหตุผลชัดเจนว่าต้องใช้ฐานข้อมูลแบบอื่น และให้กำหนด Schema กลางก่อน เพื่อให้ทุกฟีเจอร์ใช้โครงสร้างเดียวกัน

## 4. แนวทาง Network Discovery และการใช้ SNMP

ทีมเสนอให้ใช้ SNMP แบบอ่านอย่างเดียว (Read-only) สำหรับค้นหาและอ่านข้อมูลอุปกรณ์ อาจารย์เห็นว่าเป็นแนวทางที่ทำได้ แต่ต้องระบุเป็นข้อจำกัดว่าอุปกรณ์เป้าหมายต้องเปิดใช้งาน SNMP

ควรมีวิธีเพิ่มอุปกรณ์ด้วยตนเอง (Manual Entry) สำหรับกรณีที่อุปกรณ์ไม่เปิด SNMP แต่ผู้ดูแลระบบทราบข้อมูลและช่องทางเชื่อมต่ออยู่แล้ว หลังจากเพิ่มอุปกรณ์แล้ว การติดตามสถานะอาจต้องใช้วิธีอื่น เช่น อ่านข้อมูลผ่าน SSH เป็นระยะ หรือรับ Syslog ทั้งนี้ต้องเลือกตามขอบเขตที่จะพัฒนาจริง

อาจารย์ไม่แนะนำให้ใช้ SNMP เป็นวิธีหลักสำหรับแก้ไขคอนฟิก เนื่องจากการเปลี่ยนหลายค่าต่อเนื่องอาจสำเร็จเพียงบางส่วน และไม่มีคุณสมบัติแบบ Transaction ที่ยกเลิกการเปลี่ยนทั้งหมดเมื่อขั้นตอนหนึ่งล้มเหลว งานแก้ไขคอนฟิกจึงควรศึกษาการใช้ CLI ผ่าน SSH และต้องมีกลไกตรวจสอบผลลัพธ์

## 5. การจำลองและการทดสอบกับอุปกรณ์จริง

ตัวจำลอง SNMP สามารถใช้ทดสอบ Discovery และสถานะพื้นฐานบางอย่าง เช่น พอร์ตทำงานหรือไม่ทำงาน แต่ไม่ใช่การจำลองอุปกรณ์เต็มรูปแบบ ข้อมูลอย่างการใช้ CPU หรือพฤติกรรมจริงของอุปกรณ์อาจไม่สมจริง

ระบบที่ออกแบบดีควรทำงานได้ทั้งกับสภาพแวดล้อมจำลองและอุปกรณ์จริง ทีมควรวางแผนเวลาให้มีโอกาสทดสอบกับอุปกรณ์จริง เพราะยิ่งทดสอบจริงมากเท่าใด ความมั่นใจว่าระบบใช้งานได้จริงก็ยิ่งเพิ่มขึ้น

## 6. สถาปัตยกรรมระบบและการแบ่งความรับผิดชอบ

อาจารย์ต้องการเห็นภาพสถาปัตยกรรมระบบแบบคร่าว ๆ ในการพูดคุยครั้งถัดไป โดยสามารถใช้ Component Diagram หรือภาพกล่องและลูกศรที่ตอบคำถามต่อไปนี้:

- ระบบประกอบด้วยส่วนย่อยใดบ้าง
- แต่ละส่วนรับผิดชอบอะไร
- แต่ละส่วนเชื่อมต่อหรือแลกเปลี่ยนข้อมูลกับส่วนใด
- ส่วนใดต้องทำก่อนหรือเป็นเงื่อนไขของส่วนอื่น
- สมาชิกคนใดรับผิดชอบส่วนใด

อาจารย์แนะนำให้แบ่งงานตามระบบหรือฟีเจอร์ เช่น Inventory, Discovery หรือ Topology มากกว่าการแบ่งเป็นคนทำ Frontend และคนทำ Backend เพราะเจ้าของแต่ละระบบจะสามารถดูแลการทำงานตั้งแต่ต้นจนจบได้ อย่างไรก็ตาม ทีมยังต้องตกลงมาตรฐานร่วมกัน เช่น Framework, สี รูปแบบหน้าจอ และส่วนที่ทุกระบบต้องใช้ร่วมกัน

## 7. การใช้ AI ช่วยสร้างคอนฟิก

ทีมทดลองให้ AI ช่วยสร้าง Jinja2 Template สำหรับคอนฟิกพื้นฐาน และพบว่าสามารถช่วยลดเวลาได้ โดยเฉพาะคำสั่งที่ใช้ทั่วไปของ Cisco แต่อาจารย์แนะนำให้ทดลองเพิ่มเพื่อประเมินความแม่นยำกับผู้ผลิตและรุ่นอื่นก่อนกำหนดขอบเขตการรองรับ

ผลจากการศึกษา Template และคำสั่งคอนฟิกควรถูกเรียบเรียงแยกเป็นหัวข้อ แม้ยังไม่ต้องเขียนเป็นภาษาทางการ เพื่อให้ทีมค้นหาได้ง่าย ใช้ร่วมกันได้ และนำไปพัฒนาเป็นเนื้อหาในรายงาน Project 1 ภายหลัง

## 8. วิธีทำงานและการจัดเก็บเอกสารร่วมกัน

อาจารย์แนะนำให้ทีมตกลงวิธีทำงานร่วมกันและตำแหน่งจัดเก็บข้อมูลให้ชัดเจน เช่น:

- เอกสารการศึกษาและข้อสรุป
- Source Code
- Template และตัวอย่างคอนฟิก
- Database Schema และข้อตกลงข้อมูลกลาง
- งานและผู้รับผิดชอบ

ควรจัดโฟลเดอร์ตามหัวข้อ เพื่อให้สมาชิกสามารถตรวจสอบความคืบหน้าของกันและกันได้โดยไม่ต้องรอถามเจ้าของงานทุกครั้ง เรื่องที่หลายฟีเจอร์ต้องใช้ร่วมกัน เช่น Inventory Schema ควรรีบตกลงตั้งแต่ต้น

## 9. ประเด็นด้านความปลอดภัย

อาจารย์เห็นว่าความปลอดภัยเป็นสิ่งที่ต้องพิจารณา แต่ปัญหาหลักของโครงงานยังเป็นการช่วยจัดการคอนฟิกเครือข่าย ทีมควรพัฒนาฟีเจอร์หลักพร้อมประเมินความเสี่ยงของแต่ละความสามารถ หากความสามารถใดเพิ่มความสะดวกแต่มีความเสี่ยงสูง ทีมสามารถเลือกไม่ทำได้ แต่ต้องอธิบายเหตุผลต่อกรรมการอย่างชัดเจน

## 10. สิ่งที่อาจารย์ต้องการเห็นในการประชุมครั้งถัดไป

1. รายละเอียดและลำดับความสำคัญของฟีเจอร์หลังประเมินตามข้อจำกัด
2. ภาพสถาปัตยกรรมระบบหรือ Component Diagram แบบคร่าว ๆ
3. หน้าที่ ความสัมพันธ์ และ Dependency ของแต่ละระบบย่อย
4. ผู้รับผิดชอบแต่ละส่วน
5. โครงสร้างข้อมูลและ Schema เบื้องต้นของ Device Inventory
6. ข้อตกลงเรื่องวิธีทำงานและตำแหน่งจัดเก็บเอกสารร่วมกัน
7. รายละเอียดเพิ่มเติมของฟีเจอร์ที่ทีมเลือกเริ่มทำ

## 11. ความเกี่ยวข้องกับรายงานความคืบหน้าครั้งที่ 1

อาจารย์ระบุว่ารายงานความคืบหน้าครั้งแรกยังไม่มีหัวข้อบังคับที่ชัดเจน เนื้อหาที่สามารถนำไปใช้ได้ ได้แก่ การเข้าพบอาจารย์ที่ปรึกษา การกำหนดแนวทางการทำงาน การจัดลำดับฟีเจอร์ การวางสถาปัตยกรรมระบบ การออกแบบ Inventory Schema และการแบ่งหน้าที่ของสมาชิก

## สรุปสั้น

คำแนะนำหลักของการประชุมครั้งนี้คือ **ให้ทีมเปลี่ยนจากการมีเพียงรายการฟีเจอร์ ไปสู่การออกแบบระบบที่แบ่งเป็นส่วนย่อยและทำงานร่วมกันได้จริง** โดยเริ่มจากการตกลงข้อมูลกลางของ Device Inventory แล้วระบุความสัมพันธ์ ความรับผิดชอบ Dependency และเจ้าของของแต่ละส่วน เพื่อให้สมาชิกสามารถพัฒนางานคู่ขนานกันได้และนำผลไปเขียนรายงานความคืบหน้าได้อย่างเป็นระบบ
