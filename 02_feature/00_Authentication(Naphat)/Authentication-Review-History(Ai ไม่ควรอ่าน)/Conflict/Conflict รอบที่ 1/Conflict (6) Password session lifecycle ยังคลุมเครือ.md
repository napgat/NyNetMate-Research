 Password/session lifecycle ยังคลุมเครือ

ควรแยกให้ชัด:

- Self change password: revoke session อื่นทั้งหมด และ rotate current token/session หรือบังคับ login ใหม่
- Admin reset password: revoke session ของ target user ทั้งหมดทันที
- Admin reset ต้องไม่กระทบ session ของ Admin ผู้สั่ง
- Temporary password ต้องไม่ถูกส่งกลับใน response แต่ Admin สามารถส่งค่าใหม่ใน request ผ่าน HTTPS


ข้อนี้ GPT กำลังอุดช่องโหว่เรื่อง **"วงจรชีวิตของ Session" (Session Lifecycle)** ซึ่งเป็นจุดที่โปรแกรมเมอร์มักจะเขียนบั๊กหรือเผลอมองข้ามบ่อยมากครับ 

ขออธิบายขยายความแต่ละข้อเพื่อให้เห็นภาพตรงกันครับ (ยังไม่แก้ไฟล์นะครับ คุยกันก่อน):

### 1. เปลี่ยนรหัสผ่านตัวเอง (Self change password)
*   **ปัญหา:** สมมติคุณล็อกอินไว้ 2 เครื่อง (คอมพิวเตอร์ กับ มือถือ) ถ้าคุณเปลี่ยนรหัสผ่านในคอมพิวเตอร์ แล้วมือถือยังใช้งานต่อได้ ถือว่าผิดหลัก Security (เพราะถ้ารหัสมือถือโดนขโมยไป คนร้ายก็ยังอยู่ในระบบ)
*   **แนวทางที่ควรระบุ:** ทันทีที่เปลี่ยนรหัสผ่านสำเร็จ ระบบต้องไปเชือด (Revoke) Session ในมือถือทิ้ง ส่วนในคอมพิวเตอร์ (เครื่องที่กำลังใช้อยู่) **วิธีที่เขียนโค้ดง่ายและปลอดภัยที่สุดสำหรับ MVP คือ "บังคับให้ล็อกอินใหม่" ครับ** (Revoke ตัวเองด้วยไปเลย แล้วเตะกลับไปหน้า Login)

### 2. แอดมินรีเซ็ตรหัสผ่านให้คนอื่น (Admin reset password)
*   **แนวทางที่ควรระบุ:** สมมติ Operator ทำตัวน่าสงสัย Admin เลยกดปุ่มรีเซ็ตรหัสผ่านของ Operator คนนั้น ระบบจะต้องวิ่งไป **Revoke Session ทุกอันของ Operator คนนั้นทิ้งทันที 100%** เพื่อเตะเขาออกจากระบบเดี๋ยวนั้น

### 3. แอดมินต้องไม่โดนเตะออกซะเอง
*   **ปัญหา:** อันนี้เป็นตลกร้ายที่เจอบ่อยตอนตรวจงานนักศึกษาครับ คือเขียนโค้ดสั่ง Revoke Session แต่เขียนเงื่อนไข Query ฐานข้อมูลผิด กลายเป็นว่าพอ Admin กดรีเซ็ตรหัสให้ลูกน้อง Admin ดันโดนเด้งออกจากระบบซะเอง 
*   **แนวทางที่ควรระบุ:** ต้องเขียนเป็น Acceptance Test ดักไว้เลยว่า "Session ของ Admin ที่เป็นคนกดสั่ง ต้องยังคงใช้งานได้ตามปกติ"

### 4. ห้าม Backend ส่งรหัสผ่านชั่วคราวกลับมา (Temporary password)
*   **ปัญหา:** สมมติเราให้ Backend สุ่มรหัสผ่านให้ แล้วส่งกลับมาทาง API Response (เช่น `{"new_password": "ABC"}`) รหัสผ่านนี้จะถูกบันทึกค้างไว้ใน Network Log ของ Web Browser ซึ่งไม่ปลอดภัยเลย
*   **แนวทางที่ควรระบุ:** 
    1. Admin จะเป็นคน **"คิดและพิมพ์"** รหัสผ่านชั่วคราวเองจากหน้าเว็บ
    2. หน้าเว็บส่งค่านี้ไปให้ Backend ทางช่องทางที่เข้ารหัส (HTTPS)
    3. Backend รับค่าไป Hash ลง DB แล้วเซ็ต `must_change_password = true`
    4. Backend ตอบกลับแค่ `{"status": "success"}` **ห้ามตอบรหัสผ่านกลับมาเด็ดขาด**

# แล้วที่หัวข้อที่เรากันคุยไปก่อนหน้านี้ เรื่อง must_change_password ไม่ทำ ตามไฟล์ 02_feature/00_Authentication(Naphat)/Conflict (1) - (5) จะอธิบาย (6)ว่าอย่างไร

คุณมองขาดมากครับ! การที่เราตกลงกันว่าจะ **"ไม่ทำระบบ Admin Reset Password และตัด `must_change_password` ทิ้งใน MVP"** มันช่วยแก้ปัญหาข้อ 6 ของ GPT ไปได้เกินครึ่งเลยครับ!

ถ้าเราอิงตามข้อตกลงที่เราจะตัดฟีเจอร์นี้ทิ้ง เราจะอธิบายและจัดการข้อ (6) ได้แบบง่ายๆ ดังนี้ครับ:

### สิ่งที่ "ถูกตัดทิ้งไปเลย" (ไม่ต้องสนใจแล้ว)
1. ❌ **Admin reset password (เตะเป้าหมายออก):** ไม่ต้องทำ เพราะ Admin ไม่มีปุ่มให้กดรีเซ็ตรหัสผ่านลูกน้องแล้ว
2. ❌ **Admin สั่งรีเซ็ตแล้วต้องไม่โดนเตะออกเอง:** ไม่ต้องกังวลเรื่องบักนี้ เพราะฟีเจอร์ถูกตัดทิ้งไปแล้ว
3. ❌ **ไม่ส่ง Temporary Password กลับมา:** ไม่ต้องทำ เพราะเราไม่มีระบบรหัสผ่านชั่วคราวอีกต่อไป (ใช้วิธี Seed User จากไฟล์ตั้งต้นแทน)

### สิ่งที่ "ยังคงต้องทำอยู่" (เหลือแค่อย่างเดียว)
✅ **Self change password (ผู้ใช้เปลี่ยนรหัสผ่านตัวเอง)**
แม้เราจะตัดระบบ Admin Reset ทิ้ง แต่ผู้ใช้งาน (เช่น Operator) ก็ยังควรจะมีหน้าจอให้ **"เปลี่ยนรหัสผ่านของตัวเอง"** ได้อยู่ดีครับ (เพื่อความปลอดภัยเบื้องต้น)

ดังนั้น ในข้อ (6) เราจะเหลือ Contract ที่ต้องเขียนลงในเอกสารเพียงข้อเดียวคือ:
> **"เมื่อผู้ใช้ทำการเปลี่ยนรหัสผ่านของตนเองสำเร็จ ระบบจะต้อง Revoke (ยกเลิก) Session ของผู้ใช้คนนั้นในทุกๆ อุปกรณ์ทันที และบังคับให้ผู้ใช้ต้องล็อกอินใหม่ด้วยรหัสผ่านใหม่"**

**สรุปการอธิบาย:**
ถ้าต้องอธิบายเรื่องนี้ (หรือตอบคอมเมนต์ GPT) เราจะอธิบายว่า:
*"สำหรับ MVP P1 เราได้ตัดสินใจตัด Flow การทำ Admin Reset Password ออกทั้งหมดเพื่อลดความซับซ้อน ดังนั้นเรื่อง Temporary Password และ Session Lifecycle กรณี Admin สั่งรีเซ็ต จึงอยู่นอกขอบเขต (Out of Scope) โดยระบบจะรองรับเพียง Lifecycle ของการเปลี่ยนรหัสผ่านตัวเอง (Self-change) เท่านั้น ซึ่งจะบังคับเตะ Session เก่าออกทั้งหมดและให้ล็อกอินใหม่"*

การตัด Scope แบบนี้ประหยัดเวลาเขียนโค้ด Backend ไปได้เป็นวันเลยครับ! มีหัวข้อข้อที่ 7 ต่อไหมครับ หรืออยากจะให้ผมลุยสรุปและอัปเดตไฟล์ให้ตรงตามนี้เลย?
