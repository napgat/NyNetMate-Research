# ร่างหัวข้อ 3.7–3.8 การออกแบบส่วนติดต่อผู้ใช้งาน MyNetMate

ขอบเขต: Network Management ไม่รวม Configuration Management

## ควรเริ่มเขียนส่วนนี้หรือยัง?

ควรเริ่มเขียนได้แล้ว เพราะมีโครงสร้างหน้าจอ Theme เมนู และองค์ประกอบ UI ในโค้ดปัจจุบัน ใช้สิ่งเหล่านี้อธิบายแนวทางออกแบบได้โดยไม่ต้องออกแบบหน้าจอใหม่ทั้งหมด แต่ยังไม่ควรสรุปว่าทุกหน้าทำงานสมบูรณ์หรือผ่านการทดสอบแล้ว

- **3.7 อธิบายหลักการออกแบบ:** ใช้สี ตัวอักษร และสัญลักษณ์อย่างไร และเลือกแนวทางนั้นเพื่ออะไร
- **3.8 แสดงผลของการออกแบบ:** ผู้ใช้ไปจากหน้าหนึ่งสู่อีกหน้าหนึ่งอย่างไร แต่ละหน้ามีองค์ประกอบและหน้าที่อะไร พร้อมภาพหน้าจอหรือ Mockup
- หากเป็นหน้าที่มีแล้ว ใช้ภาพหน้าจอจริงจากข้อมูลทดสอบ หากยังไม่เสร็จ ใช้ Mockup และระบุว่าเป็นแบบร่าง ไม่เขียนว่าเป็นผลการทำงานจริง

ไฟล์นี้เป็นร่างข้อความและรายการภาพที่ควรเตรียม ไม่ได้สร้างภาพหน้าจอใหม่ ไม่ได้แก้ Google Docs และไม่ได้รันทดสอบระบบในรอบนี้ เหตุผลในการเลือกแนวทาง UI ด้านล่างเป็นข้อเสนอสำหรับอธิบายในเล่ม โดยอ้างอิงองค์ประกอบที่ตรวจพบในโค้ด ไม่ใช่ผลการประเมินความพึงพอใจของผู้ใช้

## 3.7 การออกแบบส่วนติดต่อผู้ใช้งาน (User Interface Design)

การออกแบบส่วนติดต่อผู้ใช้งานของระบบ MyNetMate ในส่วนการจัดการเครือข่าย มีเป้าหมายให้ผู้ใช้งานเข้าถึงข้อมูลอุปกรณ์ แผนผังเครือข่าย และความสามารถที่เกี่ยวข้องได้อย่างเป็นระบบ โดยจัดวางเมนูหลักแยกจากพื้นที่แสดงข้อมูล และใช้รูปแบบของสี ตัวอักษร และสัญลักษณ์ร่วมกันในแต่ละหน้า เพื่อให้ผู้ใช้งานแยกแยะหน้าที่ขององค์ประกอบต่าง ๆ ได้ชัดเจน

ระบบใช้เมนูด้านซ้ายสำหรับเปลี่ยนหน้าการใช้งาน และแสดงเนื้อหาของหน้าที่เลือกในพื้นที่หลัก เมื่อใช้งานบนหน้าจอขนาดเล็ก เมนูจะเปลี่ยนเป็นแถบที่เปิด–ปิดได้ ส่วนการจัดการผู้ใช้งานและการดูประวัติเหตุการณ์กำหนดให้เป็นความสามารถของ Admin โดยมีแนวทางการออกแบบดังนี้

### 3.7.1 แนวทางการเลือกใช้สีในส่วนติดต่อผู้ใช้งาน

ระบบใช้สีฟ้าเป็นสีหลักร่วมกับพื้นหลังสีอ่อนและพื้นที่เนื้อหาสีขาว เพื่อแยกองค์ประกอบที่ผู้ใช้งานสามารถดำเนินการได้ออกจากพื้นที่แสดงข้อมูล สีหลักและสีพื้นหลังกำหนดไว้ใน Theme กลาง เพื่อให้หน้าจอใช้แนวทางเดียวกันและลดการกำหนดสีที่แตกต่างกันโดยไม่จำเป็น

| กลุ่มสี | รหัสสีใน Theme | แนวทางการใช้ |
|---|---|---|
| สีหลัก | `#0284C7` | ปุ่มหลักและองค์ประกอบที่ใช้สี Primary |
| สีหลักแบบเข้ม | `#0369A1` | สี Primary แบบเข้มตามรูปแบบขององค์ประกอบ |
| สีรอง | `#F97316` | กำหนดเป็นสี Secondary สำหรับองค์ประกอบรองเมื่อมีการใช้งาน |
| สีพื้นหลัง | `#F8FAFC` | พื้นหลังโดยรวมของระบบ |
| สีพื้นที่เนื้อหา | `#FFFFFF` | พื้นที่แบบฟอร์ม ตาราง และกล่องเนื้อหา |

การแสดงผลสำเร็จ ข้อผิดพลาด และสถานะบัญชีใช้สีขององค์ประกอบแจ้งเตือนหรือป้ายสถานะร่วมกับข้อความ เช่น Success, Failed, Active และ Inactive เพื่อให้ผู้ใช้เข้าใจความหมายโดยไม่ต้องพิจารณาจากสีเพียงอย่างเดียว

> หมายเหตุสำหรับผู้เขียน: สีรองถูกกำหนดไว้ใน Theme แต่ไม่ได้หมายความว่าทุกหน้าใช้สีส้ม และไม่ควรเขียนว่าสีส้มเป็นสีแจ้งเตือนทั้งหมด เพราะองค์ประกอบแจ้งเตือนใช้สีตามประเภทของ Material UI ไม่ได้ตรวจอัตราส่วนความเปรียบต่างของทุกองค์ประกอบในรอบนี้ จึงยังไม่ควรอ้างว่าผ่านมาตรฐานการเข้าถึง

### 3.7.2 แนวทางการใช้ตัวอักษรในส่วนติดต่อผู้ใช้งาน

ระบบกำหนด Roboto เป็นแบบอักษรหลัก และมีแบบอักษรของระบบปฏิบัติการเป็นตัวเลือกสำรอง โดยแบ่งลำดับความสำคัญของข้อความเป็นหัวข้อหน้า หัวข้อย่อย เนื้อหา และคำอธิบายประกอบ ใช้ขนาดและน้ำหนักของตัวอักษรเพื่อแยกข้อความแต่ละระดับ โดยหัวข้อมีน้ำหนักมากกว่าเนื้อหาปกติ ส่วนข้อความประกอบใช้รูปแบบรองเพื่อไม่ให้แข่งขันกับข้อมูลหลัก

ป้ายกำกับของช่องกรอกข้อมูลและปุ่มดำเนินการใช้ข้อความที่สื่อถึงหน้าที่ เช่น Username or email, Password, Create user และ Apply filters เพื่อให้ผู้ใช้เข้าใจสิ่งที่ต้องกรอกหรือผลของการกดปุ่ม เมนูหลักใช้ขนาด `0.875rem` และน้ำหนัก 600 ตามรูปแบบที่กำหนดในส่วนจัดวางหน้าจอ

> หมายเหตุสำหรับผู้เขียน: ฟอนต์บนเว็บเป็นคนละส่วนกับฟอนต์ที่ใช้จัดรูปเล่มปริญญานิพนธ์ ปัจจุบันหน้าเว็บใช้ข้อความภาษาอังกฤษเป็นหลักและยังไม่ได้กำหนดฟอนต์ภาษาไทยเฉพาะ จึงไม่ควรเขียนว่าใช้ Sarabun หรือ Angsana New บนเว็บ Roboto โหลดผ่าน Google Fonts และมีฟอนต์สำรอง ไม่ได้ยืนยันว่าฝังฟอนต์ไว้เพื่อใช้งานออฟไลน์

### 3.7.3 แนวทางการใช้สัญลักษณ์ในส่วนติดต่อผู้ใช้งาน

ระบบใช้สัญลักษณ์จากชุด Material UI Icons ร่วมกับข้อความของเมนูและปุ่ม เพื่อช่วยให้ผู้ใช้งานจดจำหน้าที่ขององค์ประกอบ และใช้สัญลักษณ์ที่มีความหมายสอดคล้องกับงาน เช่น รูปอุปกรณ์เครือข่ายสำหรับหน้า Devices และรูปประวัติสำหรับหน้า Audit history

| สัญลักษณ์ที่ใช้ในโค้ด | เมนูหรือการดำเนินการ | ความหมาย |
|---|---|---|
| `SpaceDashboardOutlined` | Dashboard | หน้าหลักหรือภาพรวม |
| `RouterOutlined` | Devices | รายการอุปกรณ์เครือข่าย |
| `AccountTreeOutlined` | Topology | แผนผังและความสัมพันธ์ของอุปกรณ์ |
| `PeopleOutlined` | Users | การจัดการบัญชีผู้ใช้งาน |
| `HistoryOutlined` | Audit history | ประวัติเหตุการณ์ |
| `Search` / `TravelExplore` | ค้นหาหรือ Network Discovery | การค้นหาข้อมูลหรืออุปกรณ์ |
| `Add` / `Refresh` / `Sensors` | เพิ่มข้อมูล / โหลดข้อมูลใหม่ / ตรวจสถานะ | แยกประเภทของการดำเนินการ |

ปุ่มที่แสดงเฉพาะสัญลักษณ์ควรมีคำอธิบายหรือป้ายกำกับที่สื่อถึงหน้าที่ ส่วนสถานะระหว่างดำเนินการใช้สัญลักษณ์กำลังโหลดร่วมกับข้อความ เพื่อแจ้งให้ผู้ใช้งานทราบว่าระบบยังประมวลผลอยู่

## 3.8 ผลการออกแบบส่วนติดต่อผู้ใช้งาน

ผลการออกแบบส่วนติดต่อผู้ใช้งานของระบบ MyNetMate แสดงการจัดวางหน้าจอและการเชื่อมโยงระหว่างความสามารถในส่วน Network Management โดยใช้ตารางสำหรับข้อมูลหลายรายการ แบบฟอร์มสำหรับการรับข้อมูล และแผนผังสำหรับแสดงความสัมพันธ์ระหว่างอุปกรณ์ ทั้งนี้ ภาพที่นำเสนอควรระบุให้ชัดเจนว่าเป็นภาพหน้าจอจากระบบปัจจุบันหรือภาพแบบร่างของส่วนที่อยู่ระหว่างพัฒนา

### 3.8.1 ลำดับการใช้งานเว็บแอปพลิเคชัน (Application Flow)

ผู้ใช้งานเริ่มต้นจากหน้าเข้าสู่ระบบ เมื่อระบบตรวจสอบข้อมูลสำเร็จจะแสดงหน้าหลัก จากนั้นผู้ใช้เลือกหน้า Devices หรือ Topology ผ่านเมนูหลักได้ ส่วน Admin สามารถเลือกหน้า Users และ Audit history เพิ่มเติม การนำเสนอ Flow ในหัวข้อนี้มุ่งแสดงการเปลี่ยนหน้าจอ ไม่จำเป็นต้องแสดงการเรียก API หรือการทำงานภายในฐานข้อมูลซ้ำกับ Sequence Diagram

ลำดับการใช้งานหลักที่ควรแสดงในภาพ ได้แก่

1. **เข้าสู่ระบบ:** Login → ตรวจสอบข้อมูล → หน้าหลัก Dashboard หากข้อมูลไม่ถูกต้องให้อยู่หน้า Login พร้อมข้อความแจ้งข้อผิดพลาด
2. **เรียกดูอุปกรณ์:** Dashboard หรือเมนู Devices → ตารางอุปกรณ์ → เลือกอุปกรณ์ → แผงรายละเอียด หรือเลือก View Topology
3. **เพิ่มอุปกรณ์และค้นหาเครือข่าย:** Devices → แบบฟอร์ม Add Device หรือ Network Discovery → กรอกข้อมูล → แสดงผลการดำเนินการ โดยเส้นทาง Discovery ปัจจุบันไปแสดงการค้นหาในหน้า Topology
4. **เรียกดูแผนผัง:** เมนู Topology หรือ View Topology จาก Devices → แสดงแผนผังจากข้อมูลที่จัดเก็บไว้ → เลือกอุปกรณ์เพื่อดูรายละเอียด การเปิดดูข้อมูลเดิมไม่ใช่การเริ่ม Discovery ใหม่
5. **จัดการผู้ใช้งาน:** Admin → Users → รายการบัญชี → เพิ่มบัญชีหรือแก้ไขบทบาทและสถานะ → ยืนยันและแสดงผล ไม่รวมการลบบัญชีผู้ใช้
6. **ดูประวัติเหตุการณ์:** Admin → Audit history → เลือกตัวกรอง → ดูรายการหรือรายละเอียดเหตุการณ์ → โหลดรายการเพิ่มเติม เป็นการอ่านอย่างเดียว

> หมายเหตุสำหรับผู้เขียน: เส้นทางข้างต้นเป็นการรวมหน้าจอ ไม่ใช่คำยืนยันว่าการตรวจสิทธิ์ของ API ในทุก Feature เสร็จแล้ว ตามนโยบายสิทธิ์ Viewer อ่านข้อมูล ส่วน Admin และ Operator จัดการอุปกรณ์ได้ แต่ยังต้องตรวจการแสดงปุ่มตามบทบาทและการบังคับสิทธิ์ฝั่ง Backend ของ Devices/Discovery/Topology ก่อนรับรองความครบถ้วน

### 3.8.2 การอธิบายหน้าส่วนติดต่อผู้ใช้งาน

หัวข้อนี้ควรนำเสนอภาพหน้าจอพร้อมคำอธิบายสั้น ๆ ว่าหน้าจอนั้นใช้ทำอะไร มีองค์ประกอบสำคัญอะไร และผู้ใช้ดำเนินการต่ออย่างไร โดยไม่จำเป็นต้องแยกทุก Use Case ออกเป็นหน้าใหม่ เพราะบางความสามารถอยู่ในหน้าต่างแบบฟอร์มหรือแผงรายละเอียดของหน้า Devices

1. **หน้าเข้าสู่ระบบ (Login)** แสดงช่องกรอกชื่อผู้ใช้หรืออีเมล ช่องรหัสผ่าน และปุ่ม Sign in เมื่ออยู่ระหว่างส่งคำขอจะแสดงสถานะกำลังดำเนินการ ส่วนกรณีผิดพลาดจะแสดงข้อความแจ้งให้ผู้ใช้ทราบ หน้าเข้าสู่ระบบใช้บัญชีที่ Admin จัดเตรียมให้และไม่มีการสมัครบัญชีด้วยตนเอง

2. **หน้าหลัก (Dashboard)** เป็นหน้าเริ่มต้นหลังเข้าสู่ระบบและใช้เป็นจุดเชื่อมต่อไปยัง Devices และ Topology โดยแนวทางออกแบบกำหนดให้แสดงข้อมูลสรุปของเครือข่าย อย่างไรก็ตาม โค้ดปัจจุบันแสดง Dashboard is Empty จึงต้องระบุสถานะนี้เมื่อใช้ภาพจริง หากนำเสนอข้อมูลสรุปที่ยังไม่พัฒนา ให้ใช้ภาพแบบร่างแยกต่างหาก

3. **หน้ารายการอุปกรณ์ (Device Inventory)** แสดงข้อมูลอุปกรณ์ในรูปแบบตาราง พร้อมช่องค้นหา ตัวกรอง และปุ่มดำเนินการ เช่น Add Device, Network Discovery, View Topology และ Check Status ช่วยให้ผู้ใช้เริ่มต้นดูข้อมูลหรือดำเนินการกับอุปกรณ์จากพื้นที่เดียวกัน โดยสิทธิ์การดำเนินการเป็นไปตามบทบาทที่กำหนดและต้องตรวจการบังคับใช้ก่อนสรุปผล

4. **แผงรายละเอียดอุปกรณ์ (Device Details)** แสดงเมื่อผู้ใช้เลือกอุปกรณ์จากรายการ โดยแยกข้อมูลภาพรวมและข้อมูล Interface ออกเป็นแท็บ เพื่อให้อ่านข้อมูลของอุปกรณ์รายตัวได้โดยไม่ต้องแสดงรายละเอียดทั้งหมดในตารางหลัก

5. **หน้าต่างเพิ่มอุปกรณ์ (Add Device)** รับข้อมูล Management IP, Credential Profile ID, Environment, Role ของอุปกรณ์ และ Notes ก่อนส่งข้อมูลให้ระบบดำเนินการ โดย Role ในแบบฟอร์มนี้หมายถึงบทบาทของอุปกรณ์ในเครือข่าย ไม่ใช่บทบาท Admin, Operator หรือ Viewer ของผู้ใช้

6. **หน้าต่างค้นหาอุปกรณ์เครือข่าย (Network Discovery)** รับ Seed IP และ Credential Profile สำหรับเริ่มค้นหา จากนั้นแสดงการดำเนินการค้นหาในหน้า Topology การทดสอบและภาพประกอบต้องใช้เครือข่ายทดสอบที่ได้รับอนุญาต ไม่ใช้เครือข่ายมหาวิทยาลัยหรือข้อมูลลับจริง

7. **หน้าแผนผังเครือข่าย (Topology)** แสดงอุปกรณ์และเส้นเชื่อมจากข้อมูลเครือข่าย ช่วยให้ผู้ใช้เห็นความสัมพันธ์ที่อ่านจากตารางได้ยาก ผู้ใช้เลือกอุปกรณ์เพื่อดูรายละเอียดได้ คำอธิบายใต้ภาพควรแยกการดูแผนผังจากฐานข้อมูลกับการแสดงผลระหว่าง Discovery

8. **หน้าจัดการผู้ใช้งาน (User Management)** สำหรับ Admin แสดงรายการบัญชี บทบาท และสถานะ พร้อมตัวกรองสถานะบัญชีและการแบ่งหน้า มีแบบฟอร์มสร้างบัญชีและแก้ไขบทบาทหรือสถานะบัญชี โดยการเปลี่ยนแปลงที่กระทบสิทธิ์มีขั้นตอนยืนยันก่อนบันทึก และไม่มีปุ่มลบผู้ใช้ในขอบเขตปัจจุบัน

9. **หน้าประวัติเหตุการณ์ (Audit History)** สำหรับ Admin แสดงเวลา เหตุการณ์ ผู้กระทำ ทรัพยากร และผลลัพธ์ พร้อมตัวกรองและปุ่มดูรายละเอียด สามารถโหลดรายการเพิ่มเติมได้ แต่ไม่มีการแก้ไขหรือลบประวัติผ่านหน้านี้ ประวัติหมายถึงเหตุการณ์ที่ระบบกำหนดให้บันทึก ไม่ใช่ทุกการคลิกของผู้ใช้งาน

## ภาพที่ควรเตรียมก่อนนำลงเล่ม

| ภาพ | สิ่งที่ควรให้เห็น | ข้อควรระบุ |
|---|---|---|
| Application Flow | การเชื่อมหน้าจอและทางเลือกเฉพาะ Admin | ไม่ต้องวาดรายละเอียด API ซ้ำ |
| Login | แบบฟอร์มและข้อความผิดพลาด | ใช้บัญชีทดสอบ ไม่เปิดเผยรหัสผ่าน |
| Dashboard | หน้าปัจจุบัน หรือ Mockup ของข้อมูลสรุป | ต้องแยก Empty Page กับแบบร่าง |
| Devices และ Device Details | ตาราง ตัวกรอง และแผงรายละเอียด | ใช้ข้อมูลอุปกรณ์ตัวอย่าง |
| Add Device และ Discovery | แบบฟอร์มและการเลือก Credential Profile | ไม่แสดงรหัสผ่านหรือ SNMP Community จริง |
| Topology | อุปกรณ์และเส้นเชื่อม | ระบุว่าเป็นข้อมูลจาก Lab หรือ Mockup |
| User Management | รายการบัญชีและแบบฟอร์มแก้ไข | ใช้ผู้ใช้ทดสอบ ไม่แสดงข้อมูลส่วนบุคคลจริง |
| Audit History | ตัวกรอง รายการ และรายละเอียดเหตุการณ์ | ใช้ข้อมูลทดสอบและแสดงว่าอ่านอย่างเดียว |

ยังไม่กำหนดเลขรูปในร่างนี้ เพื่อไม่ชนเลขรูปของเพื่อนและส่วน ER ให้กำหนดลำดับหลังรวมภาพทั้งบท ส่วน Check Status กับการเปลี่ยน Management State ต้องตกลงความหมายกับทีมก่อนเลือกภาพ ไม่ใช้ภาพตรวจ SNMP แทนภาพเปลี่ยนสถานะด้วยมือ
