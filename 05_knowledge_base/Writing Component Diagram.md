
## วิธีเขียน Component Diagram

Component Diagram คือแผนภาพที่บอกว่า **"ระบบประกอบด้วยชิ้นส่วนอะไร และชิ้นส่วนเหล่านั้นคุยกันอย่างไร"** ครับ

---

## 📐 องค์ประกอบ 4 อย่างที่ต้องมี

### 1. Component (กล่อง)
คือชิ้นส่วนที่ทำหน้าที่อะไรบางอย่างได้ด้วยตัวเอง

```
┌─────────────────┐
│   <<component>> │
│   Device API    │
└─────────────────┘
```

**หลักการตั้งชื่อ:** ชื่อต้องบอกว่า **"มันทำอะไร"** ไม่ใช่ว่า "มันคืออะไร"
- ❌ `Python`  ← บอกแค่ว่าใช้ภาษาอะไร
- ✅ `Config Generator` ← บอกว่าทำอะไร

---

### 2. Interface (พอร์ต/ช่องทางรับส่ง)
คือ **"ช่องทาง"** ที่ Component อื่นจะเข้ามาคุยด้วยได้

มี 2 แบบ:
```
   Provided Interface        Required Interface
   (สิ่งที่ Component ให้)    (สิ่งที่ Component ต้องการ)
        ─○─                        ─(─
```

ตัวอย่างในโลก Web:
- `POST /api/devices` = Provided Interface ของ Backend
- เรียก `Gemini API` = Required Interface ของ Backend

---

### 3. Dependency / Connection (ลูกศร)
คือเส้นที่บอกว่า **"ใครพึ่งพาใคร"**

```
[Component A] ──────→ [Component B]
```
ลูกศรชี้ไปหา **"สิ่งที่ต้องการ"** เสมอ  
อ่านว่า: "A ต้องการ B"

---

### 4. Subsystem / Package (กรอบใหญ่)
คือกรอบที่ครอบกล่องที่อยู่ใน Layer เดียวกัน

```
┌─────────────────────────────┐
│        <<subsystem>>        │
│           Backend           │
│  ┌──────────┐ ┌──────────┐  │
│  │ Auth API │ │Config API│  │
│  └──────────┘ └──────────┘  │
└─────────────────────────────┘
```

---

## 🪜 ขั้นตอนการเขียนทีละขั้น

### ขั้นที่ 1: ระบุ Boundary (ขอบเขต)
วาดกรอบใหญ่ก่อนเลย แบ่งเป็น 2 โซน:
```
┌─────────────────────────────────────┐   ┌──────────────┐
│           ระบบของเรา (In Scope)     │   │  ภายนอก      │
│                                     │   │ (External)   │
└─────────────────────────────────────┘   └──────────────┘
```

---

### ขั้นที่ 2: วาง Subsystem ตาม Layer
วางกล่องใหญ่ตาม Layer ที่คุณคิดไว้ก่อนหน้า (จากบนลงล่าง):
```
┌──────────────┐
│   Frontend   │
└──────────────┘
       ↓
┌──────────────┐
│   Backend    │
└──────────────┘
       ↓
┌──────────────┐
│   Database   │
└──────────────┘
```

---

### ขั้นที่ 3: ระเบิด Component ย่อยในแต่ละ Subsystem
ไล่ดู **Feature P1** แต่ละอัน แล้วถามว่า มันต้องการกล่องย่อยอะไรใน Layer ไหน?

ตัวอย่าง: Feature **"Login + JWT"** ต้องการ:
- Frontend: `Login Page Component`
- Backend: `Auth API`, `JWT Middleware`
- Database: `users table`

---

### ขั้นที่ 4: วาดลูกศร Dependency
เริ่มจาก User (ซ้ายหรือบนสุด) แล้วลากลูกศรตาม Flow ที่ข้อมูลวิ่ง:

```
[User] → [Login Page] → [Auth API] → [JWT Middleware] → [users table]
```

ข้อควรระวัง:
- ลูกศรชี้ทิศทางเดียว = ฝ่ายหนึ่งเรียกใช้อีกฝ่ายข้างเดียว
- ลูกศรชี้สองทิศ = คุยกันไปมา (ระวังใช้เกินจำเป็น)

---

### ขั้นที่ 5: ใส่ Label บนลูกศร
บอกว่าส่งอะไรไป / ใช้ Protocol อะไร:

```
[Frontend] ──HTTP/REST──→ [Backend API]
[Backend]  ──SQL Query──→ [PostgreSQL]
[Backend]  ──SSH/Netmiko→ [Cisco Device]
[Backend]  ──HTTPS──────→ [Gemini API]
```

## 🛠️ เครื่องมือที่ใช้เขียน

| เครื่องมือ                 | ข้อดี                              | เหมาะกับ            |
| -------------------------- | ---------------------------------- | ------------------- |
| **draw.io** (diagrams.net) | ฟรี, ใช้ง่าย, มี Template          | ทำงานจริง           |
| **Mermaid**                | เขียนเป็น Code, ใส่ใน Markdown ได้ | ใส่ใน GitHub/เอกสาร |
| **Lucidchart**             | สวย, ทำงานร่วมกันได้               | Presentation        |
| **กระดาษ + ปากกา**         | เร็วสุด ไม่ต้องง้อ Software        | ร่างไอเดียครั้งแรก  |

---

## ⚠️ ข้อผิดพลาดที่มักเกิดขึ้น

| ผิดพลาด | วิธีแก้ |
|---|---|
| กล่องเยอะเกินไปจนอ่านไม่ออก | 1 Diagram = 1 มุมมอง ถ้าเยอะให้แตก Diagram |
| ลูกศรไม่มี Label | ทุกเส้นต้องบอกว่า "ส่งอะไร / ใช้อะไร" |
| ลืมวาด External System | Gemini API, Router/Switch ต้องอยู่ในภาพด้วย |
| ชื่อ Component ไม่ชัด | ตั้งชื่อว่า "ทำอะไร" ไม่ใช่ "คืออะไร" |

---

## 💡 สูตรจำง่าย

```
Component Diagram ที่ดี ตอบได้ 3 คำถาม:

1. "ระบบมีกี่ส่วน?"        → ดูจากจำนวนกล่อง
2. "แต่ละส่วนทำอะไร?"      → ดูจากชื่อกล่อง
3. "ส่วนไหนคุยกับส่วนไหน?" → ดูจากลูกศร + Label
```

ลองเริ่มด้วยกระดาษก่อนได้เลยครับ ร่างคร่าวๆ แล้วมาถ่ายรูปให้ดูได้เลย!
