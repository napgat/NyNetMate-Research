การขยับมาสู่กลุ่มที่ 2 **Network Discovery (การค้นหาและสร้างแผนผังเครือข่าย)** ถือเป็นก้าวสำคัญที่เปลี่ยนจากการ "ตั้งค่า" (Configuration) มาเป็นการ "ทำความเข้าใจ" (Observability/Data Collection) สถานะปัจจุบันของเครือข่าย

อ้างอิงจากโครงสร้างของหนังสือ _Network Programmability and Automation_ เนื้อหาในส่วนนี้จะถูกจัดอยู่ในหัวข้อ **Data Collection and Enrichment** (บทที่ 2) และการใช้งาน **Network APIs** (บทที่ 10)

เพื่อนำไปใช้ในการพัฒนาโปรเจกต์ของคุณ นี่คือคอนเซปต์และเครื่องมือที่คุณต้องเจาะลึกครับ:

### คอนเซปต์หลักที่ต้องศึกษา (Core Concepts for Network Discovery)

**1. โปรโตคอลที่ใช้ค้นหาความสัมพันธ์ (Discovery Protocols)** แม้ OSPF, ARP และ MAC Address จะสำคัญมากในการบอกเส้นทางและตำแหน่งอุปกรณ์ปลายทาง แต่ในโลกของ Network Automation การวาดแผนผัง (Topology) ว่าสวิตช์ตัวไหนต่อกับเราเตอร์ตัวไหน พอร์ตอะไร มักจะพึ่งพาโปรโตคอลเหล่านี้เป็นแกนหลัก:

- **LLDP (Link Layer Discovery Protocol) / CDP (Cisco Discovery Protocol):** การดึงตาราง Neighbor ของโปรโตคอลเหล่านี้คือวิธีที่ตรงไปตรงมาที่สุดในการสร้าง Topology Map แบบอัตโนมัติ
    
**2. การเปลี่ยนผ่านจาก SNMP สู่ Modern APIs**

- **ข้อจำกัดของ SNMP:** หนังสือระบุชัดเจนว่าแม้ SNMP จะมีมานานกว่า 25 ปี แต่ออกแบบมาเพื่อดึงค่า (Polling) ทีละตัวแปรผ่าน MIBs ซึ่งช้าและจัดการโครงสร้างข้อมูลได้ยาก
    
- **การมาถึงของ Modern APIs:** การดึงข้อมูล ARP หรือ OSPF Neighbor ในปัจจุบัน ควรหันไปใช้ **RESTCONF** หรือ **NETCONF** เนื่องจากระบบจะส่งคืนค่ากลับมาเป็นโครงสร้างข้อมูลมาตรฐาน (JSON หรือ XML) ที่โปรแกรมเมอร์สามารถนำไปวนลูป (Loop) เพื่อสร้างกราฟหรือแผนผังต่อได้ทันที
    
**3. การเสริมเติมข้อมูล (Data Enrichment)** ข้อมูลดิบที่ได้จากอุปกรณ์ (เช่น ได้ MAC Address มา) อาจยังไม่มีประโยชน์สูงสุด คอนเซปต์ของการทำ Enrichment คือการนำข้อมูลนั้นไปเทียบกับฐานข้อมูลอื่น เช่น เอา MAC Address ไปเทียบกับฐานข้อมูล (Source of Truth) ว่าเป็นอุปกรณ์ยี่ห้ออะไร หรือของแผนกไหน ก่อนนำไปแสดงผลบน Dashboard

### เครื่องมือและไลบรารีที่ต้องใช้ (Tools & Libraries)

ในการเขียนสคริปต์เพื่อประมวลผลข้อมูลเหล่านี้ หนังสือได้จัดเตรียมเครื่องมือตามสถาปัตยกรรมดังนี้:
เครื่องมือทั้ง 4 ตัวนี้ถูกสร้างขึ้นมาเพื่อแก้ปัญหา "วิธีสื่อสาร" และ "วิธีจัดการข้อมูล" กับอุปกรณ์เครือข่ายที่มีความทันสมัยแตกต่างกัน ดังนี้ครับ

**1. Python `requests` Library (สำหรับการใช้ RESTCONF API)**

- **หน้าที่:** เป็นไลบรารี HTTP Client ที่ทรงพลังและใช้งานง่ายที่สุดใน Python ใช้สำหรับยิงคำขอ (HTTP GET) ไปยังอุปกรณ์เครือข่าย
- **เปรียบเทียบให้เห็นภาพ:** ทำหน้าที่เหมือน **"เว็บเบราว์เซอร์"** สำหรับโค้ด Python
- **การทำงาน:** โดยปกติเมื่อคุณพิมพ์ URL ในหน้าเว็บ เบราว์เซอร์จะยิงคำขอไปที่เซิร์ฟเวอร์เพื่อขอโหลดหน้าเว็บ ไลบรารี `requests` ก็ทำแบบเดียวกัน แต่ใช้ส่งคำขอ (HTTP Requests) ไปยังช่องทาง API ของอุปกรณ์เครือข่าย (เช่น RESTCONF)
- **ผลลัพธ์:** ข้อมูลที่อุปกรณ์ส่งกลับมามักจะอยู่ในรูปแบบ **JSON** ซึ่งเป็นโครงสร้างข้อมูลมาตรฐานที่นำไปเขียนโปรแกรมเพื่อวาดแผนผัง (Topology) ต่อได้ทันที
- **การประยุกต์ใช้:** คุณสามารถใช้ `requests` ยิงไปที่ Endpoint ของ RESTCONF เพื่อขอข้อมูล ARP Table หรือ OSPF Database ระบบของอุปกรณ์จะคืนค่าข้อมูลกลับมาเป็นรูปแบบ **JSON** ทันที ทำให้คุณแกะตัวแปรไปวาดแผนผังได้ง่ายมาก
    

**2. Python `ncclient` Library (สำหรับการใช้ NETCONF API)**
- **หน้าที่:** ไลบรารีเฉพาะทางสำหรับเชื่อมต่อผ่านโปรโตคอล NETCONF (วิ่งบน SSH)
- **เปรียบเทียบให้เห็นภาพ:** เป็น **"ช่องทางสื่อสารเฉพาะทาง"** สำหรับวิศวกรเครือข่าย
- **การทำงาน:** แทนที่จะสื่อสารผ่าน HTTP แบบ `requests` ตัว `ncclient` จะทำการเชื่อมต่อเข้าอุปกรณ์ผ่านโปรโตคอลความปลอดภัย SSH แต่ออกแบบมาเพื่อพูดคุยด้วยภาษามาตรฐานที่เรียกว่า **NETCONF** โดยเฉพาะ (รับส่งคำสั่งในรูปแบบ RPC - Remote Procedure Call)
- **การประยุกต์ใช้:** ส่งคำสั่ง RPC (Remote Procedure Call) เพื่อขอข้อมูลสถานะเครือข่าย โดยผลลัพธ์ที่ได้จะอยู่ในรูปแบบโครงสร้างข้อมูล **XML**
- -**ผลลัพธ์:** ข้อมูลที่ระบบส่งกลับมาจะถูกจัดโครงสร้างในรูปแบบ **XML** (หน้าตาคล้าย HTML ที่มีแท็กเปิด-ปิด)
    

**3. TextFSM หรือ Genie Parsers (สำหรับอุปกรณ์เก่าที่ไม่มี API)**
- **หน้าที่:** อุปกรณ์รุ่นเก่าหรืออุปกรณ์ระดับ Access บางรุ่นอาจยังไม่มี RESTCONF ให้ใช้ คุณจำเป็นต้องกลับไปใช้ `Netmiko` สั่งรันคำสั่ง `show ip arp`, `show mac address-table`, หรือ `show lldp neighbors`
-  **เปรียบเทียบให้เห็นภาพ:** ทำหน้าที่เหมือน **"ตะแกรงร่อนข้อมูล"**
-  **การทำงาน:** พัฒนาโดย Google ใช้สำหรับอุปกรณ์รุ่นเก่าที่ไม่มี API ให้ใช้ เมื่อคุณยิงคำสั่ง CLI (เช่น `show ip arp`) ผลลัพธ์ที่ได้จะเป็นข้อความดิบ (Raw text) ยาวๆ ที่คอมพิวเตอร์นำไปประมวลผลต่อยาก TextFSM จะให้คุณสร้าง "เทมเพลตกฎเกณฑ์ (Regular Expression)" เพื่อบอกระบบว่าคำไหนคือ IP และคำไหนคือ MAC Address
- **ผลลัพธ์:** ระบบจะสกัดเฉพาะตัวแปรที่ต้องการออกมาจากข้อความดิบ แล้วแปลงให้อยู่ในรูปแบบ **Python Dictionary หรือตาราง**
- **การประยุกต์ใช้:** ผลลัพธ์ที่ได้จาก Netmiko จะเป็นข้อความดิบ (Raw text) คุณต้องใช้ Parser อย่าง TextFSM หรือ Genie (พัฒนาโดย Cisco) มาครอบอีกชั้น เพื่อเปลี่ยนข้อความเหล่านั้นให้กลายเป็น Dictionary ใน Python ถึงจะนำไปประมวลผลสร้างแผนผังต่อได้

### 4. Genie Parsers
- **เปรียบเทียบให้เห็นภาพ:** คือ TextFSM **"แบบสำเร็จรูป"**
- **การทำงาน:** พัฒนาโดย Cisco (เป็นส่วนหนึ่งของระบบ pyATS) ทำหน้าที่แปลงข้อความจาก CLI เป็นโครงสร้างข้อมูลเหมือน TextFSM
- **จุดเด่น:** ข้อเสียของ TextFSM คือคุณต้องมานั่งเขียนเทมเพลตเพื่อแยกคำเอง แต่ Genie มีคลังเทมเพลตสำเร็จรูปสำหรับคำสั่ง `show` แทบทุกคำสั่งของหลายระบบปฏิบัติการ (เช่น `show ip interface brief`, `show lldp neighbors`) มาให้พร้อมใช้งานทันที ช่วยประหยัดเวลาในการเขียนโค้ดคัดแยกข้อมูลได้อย่างมาก


การเลือกใช้เครื่องมือสำหรับกระบวนการค้นหาและสร้างแผนผังเครือข่าย (Network Discovery) จะพิจารณาจาก **ความสามารถของอุปกรณ์ปลายทาง (Device Capabilities)** เป็นเกณฑ์หลัก เนื่องจากในระบบเครือข่ายที่มีผู้ผลิตหลากหลาย (Multi-Vendor) อุปกรณ์แต่ละรุ่นจะรองรับช่องทางการเชื่อมต่อและรูปแบบข้อมูลที่แตกต่างกัน

## เกณฑ์การเลือกใช้เครื่องมือ

การเลือกเครื่องมือจะถูกแบ่งออกเป็น 2 แนวทางหลักตามสถาปัตยกรรมของอุปกรณ์:

### 1. อุปกรณ์รุ่นใหม่ (API-Driven)

หากอุปกรณ์เครือข่ายรองรับการสื่อสารผ่านโปรโตคอลสมัยใหม่ ไม่ควรใช้การส่งคำสั่ง CLI แต่เปลี่ยนมาใช้ API แทน:

- **เลือกใช้ Python `requests`:** เมื่ออุปกรณ์เปิดใช้งาน **RESTCONF** (เน้นรับส่งข้อมูลในรูปแบบ JSON ซึ่งประมวลผลต่อได้ง่ายที่สุด)
    
- **เลือกใช้ Python `ncclient`:** เมื่ออุปกรณ์เปิดใช้งาน **NETCONF** (ใช้เมื่อระบบต้องการความปลอดภัยในระดับ SSH และดึงข้อมูลโครงสร้างตาม YANG Model ในรูปแบบ XML)
    

### 2. อุปกรณ์ดั้งเดิม / อุปกรณ์ที่ไม่รองรับ API (CLI-Driven)

หากอุปกรณ์รองรับเพียงแค่การล็อกอินผ่าน SSH เพื่อพิมพ์คำสั่งหน้าจอ ต้องใช้การผสมผสานเครื่องมือ:

- **เลือกใช้ `Netmiko`** เพื่อทำหน้าที่เชื่อมต่อและส่งคำสั่งดึงข้อมูลดิบ (เช่น `show ip arp` หรือ `show lldp neighbors`)
    
- **เลือกใช้ `Genie Parsers`** เป็นตัวเลือกแรกในการแปลงข้อความดิบนั้นให้เป็น JSON เนื่องจากมีเทมเพลตสำเร็จรูปสำหรับคำสั่งมาตรฐานของค่ายหลักๆ อยู่แล้ว
    
- **เลือกใช้ `TextFSM`** แทนก็ต่อเมื่อคำสั่งนั้นเป็นคำสั่งเฉพาะทาง หรือเป็นอุปกรณ์ยี่ห้อที่ Genie ยังไม่มีเทมเพลตสำเร็จกุมรองรับ เพื่อเขียนกฎการตัดคำ (Regex) ขึ้นมาใช้เอง

## การนำเครื่องมือไปใช้ในแต่ละส่วนของ Network Discovery (ND Pipeline)

กระบวนการทำ Network Discovery สามารถแบ่งออกเป็น 3 ส่วนหลัก โดยเครื่องมือแต่ละตัวจะทำหน้าที่เฉพาะในแต่ละส่วนดังนี้:

### ส่วนที่ 1: การรวบรวมข้อมูลสถานะ (Data Collection)

เป็นขั้นตอนการเข้าถึงอุปกรณ์เพื่อดึงข้อมูลตารางที่จำเป็นสำหรับการหาความเชื่อมโยง (Topology) เช่น ตาราง LLDP/CDP (หาเพื่อนบ้าน), ตาราง ARP (หาคู่ IP-MAC), และตาราง OSPF Database (หาเส้นทางเชื่อมต่อเลเยอร์ 3)

- **การใช้เครื่องมือ:** * หากใช้วิธี API: ใช้ `requests` หรือ `ncclient` ยิงคำขอไปที่ Endpoint ของอุปกรณ์เพื่อรับข้อมูลที่มีโครงสร้างมาทันที
    
    - หากใช้วิธี CLI: ใช้ `Netmiko` (หรือปลั๊กอินบน `Nornir` เพื่อความรวดเร็วแบบขนาน) ยิงคำสั่ง `show` เข้าไปดึงข้อความดิบออกมา
        

### ส่วนที่ 2: การแปลงและจัดระเบียบข้อมูล (Data Parsing)

ส่วนนี้จะใช้ **เฉพาะกรณีที่ดึงข้อมูลผ่านวิธี CLI (ข้อความดิบ)** ในส่วนที่ 1 เท่านั้น หากได้ข้อมูลจาก API มาแล้วจะข้ามส่วนนี้ไปได้เลย

- **การใช้เครื่องมือ:** * นำข้อความดิบที่ได้จาก Netmiko ส่งเข้า `Genie` หรือ `TextFSM` เพื่อสกัดคำ
    
    - ผลลัพธ์ในส่วนนี้จะต้องเปลี่ยนจากข้อความบนหน้าจอคอมพิวเตอร์ ให้กลายเป็น **Python Dictionary** หรือ **JSON** ที่ระบุชัดเจนว่าพอร์ตใดเชื่อมต่ออยู่กับอุปกรณ์ใด
        

### ส่วนที่ 3: การประมวลผลและเก็บบันทึกข้อมูล (Data Storage & Enrichment)

เป็นส่วนสุดท้ายที่นำข้อมูลแบบมีโครงสร้าง (JSON) จากส่วนที่ 1 หรือส่วนที่ 2 มาวิเคราะห์หาความสัมพันธ์เชื่อมโยง (Mapping) และบันทึกลงระบบ

- **การใช้เครื่องมือ:**
    
    - ข้อมูลจะถูกส่งต่อเข้าสู่ระบบ Backend (เช่น พัฒนาด้วย `FastAPI`) เพื่อบันทึกลงฐานข้อมูลผ่าน ORM (เช่น `SQLAlchemy`)
        
    - ข้อมูลที่จัดระเบียบแล้วในส่วนนี้ สามารถนำไปป้อนเป็นบริบท (Context) ให้กับระบบ AI หรือ RAG pipeline เพื่อให้เข้าใจสถาปัตยกรรมเครือข่ายปัจจุบัน และพร้อมสำหรับการนำไปใช้วาดรูปแผนผังเครือข่ายบนหน้าจอ Dashboard (เช่น พัฒนาด้วย `React` / `Next.js`) ในขั้นต่อไป
