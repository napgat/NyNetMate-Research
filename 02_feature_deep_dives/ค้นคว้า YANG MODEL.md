## YANG Model คืออะไร?

**YANG (Yet Another Next Generation)** ไม่ใช่โปรโตคอลและไม่ใช่ไฟล์เก็บข้อมูล (เช่น XML หรือ JSON) แต่ทำงานเป็น **ภาษาสำหรับกำหนดโครงสร้างข้อมูล (Data Modeling Language)** > **เปรียบเทียบให้เห็นภาพ:** > ถ้าเปรียบเทียบกับงานพัฒนาซอฟต์แวร์ YANG ทำหน้าที่เหมือน **Database Schema** หรือ **TypeScript Interface / SQLAlchemy Model** ที่คอยประกาศว่า อุปกรณ์เครือข่ายนี้จะมี "ตาราง" หรือ "ตัวแปร" อะไรบ้าง ตัวแปรนี้เป็นตัวเลขหรือข้อความ และจำกัดค่าไว้เท่าไหร่ (เช่น อินเตอร์เฟสต้องมีชื่อเป็น String, ค่า MTU ต้องเป็น Integer ระหว่าง 64-9216)

เมื่อยี่ห้อต่างๆ (Cisco, Huawei, Juniper) นำภาษา YANG ไปเขียนอธิบายโครงสร้างอุปกรณ์ของตัวเอง คอมพิวเตอร์หรือระบบ Automation ก็จะเข้าใจสถาปัตยกรรมด้านในของอุปกรณ์ทุกค่ายได้ผ่านเอกสารพิมพ์เขียว (Blueprint) เดียวกัน

---

## สิ่งที่ต้องรู้ก่อนเริ่มศึกษา YANG Model

เพื่อให้เข้าใจ YANG ได้ง่ายขึ้นและไม่สับสน ควรมีพื้นฐาน 3 เรื่องนี้ก่อนครับ:

1. **Configuration vs Operational State (แยกสถานะอุปกรณ์):**
    
    - **Configuration (Writable):** ข้อมูลที่เราสั่งตั้งค่าเข้าไป (เช่น การสั่งเปิดพอร์ต, การตั้ง IP)
        
    - **Operational State (Read-only):** ข้อมูลสถานะจริง ณ ปัจจุบัน (เช่น พอร์ตกำลังอัป/ดาวน์, จำนวน Packet ที่วิ่งผ่าน counter) _YANG จะแยกโครงสร้างสองส่วนนี้ออกจากกันชัดเจน_
        
2. **Data Serialization (XML และ JSON):**
    
    - YANG เป็นแค่ตัวกำหนดกฎเกณฑ์ (Schema) แต่เวลาส่งข้อมูลจริงข้ามเครือข่าย ข้อมูลเหล่านั้นจะถูกแปลงเป็น **XML** (เมื่อส่งผ่าน NETCONF) หรือ **JSON** (เมื่อส่งผ่าน RESTCONF)
        
3. **โปรโตคอล NETCONF / RESTCONF:**
    
    - ให้มองว่าโปรโตคอลเหล่านี้คือ **"รถขนส่ง"** ส่วนข้อมูลที่จัดระเบียบตามโครงสร้าง YANG คือ **"สินค้า"** ที่อยู่บนรถ

## YANG Model เอาไปทำอะไร?

ในกระบวนการทำงานจริง โดยเฉพาะขั้นตอน **Network Discovery** และ **Configuration Automation** ระบบจะใช้ประโยชน์จาก YANG ในด้านเหล่านี้:

- **สร้างภาษากลางข้ามผู้ผลิต (Multi-Vendor Consistency):** ผ่านโมเดลมาตรฐานกลุ่ม **OpenConfig** หรือ **IETF** ช่วยให้คุณสามารถเขียนข้อมูลชุดเดียวกัน (เช่น โครงสร้างสั่งตั้งค่าพอร์ตเลเยอร์ 2) แล้วส่งไปทำงานได้ทั้งบน Cisco และ Huawei โดยไม่ต้องเขียนโค้ดแปลง Logic แยกค่าย
    
- **ตรวจสอบความถูกต้องก่อนส่งคอนฟิก (Data Validation):** สคริปต์หรือระบบ Backend สามารถใช้ตัว YANG Model ตรวจสอบชุดคำสั่งฝั่งคอมพิวเตอร์ก่อนส่งเข้า Router จริงได้ทันที หากใส่ค่า IP ผิดฟอร์แมต หรือใส่ตัวเลขเกินเกณฑ์ ระบบจะบล็อกและแจ้ง Error ทันที ช่วยลดโอกาสเกิดคำสั่งพัง (Typo) บนอุปกรณ์จริง
    
- **สร้าง API อัตโนมัติ (Automated API Generation):** อุปกรณ์เครือข่ายรุ่นใหม่จะอ่านไฟล์ YANG เพื่อนำไปสร้างเป็น Endpoint ของ RESTCONF (เช่น `https://router/restconf/data/ietf-interfaces:interfaces`) ให้โปรแกรมเมอร์ยิง API เข้ามาดึงข้อมูล ARP หรือ OSPF ได้โดยตรง

## แนวทางการศึกษาและเครื่องมือที่ต้องใช้

การศึกษาเรื่อง YANG ไม่แนะนำให้เปิดอ่านไฟล์โค้ดของมันตรงๆ เพราะอ่านยากมาก แต่ควรศึกษาตามลำดับขั้นตอนและใช้เครื่องมือเหล่านี้ช่วย:

### 1. แหล่งเนื้อหาที่ควรเริ่มอ่าน

- **บทที่ 8 ของหนังสือ Network Programmability and Automation:** จะเป็นส่วนที่อธิบายโครงสร้างของ YANG ไว้อย่างเป็นระบบที่สุด ตั้งแต่การทำความเข้าใจคำศัพท์พื้นฐานอย่าง `container`, `list`, `leaf` และ `leaf-list`
    
- **OpenConfig (openconfig.net):** เข้าไปศึกษาโครงสร้างโมเดลมาตรฐานที่กลุ่มผู้ให้บริการเครือข่ายระดับโลก (เช่น Google, Microsoft) ร่วมกันออกแบบขึ้นมา เพื่อดูตัวอย่างการประกาศโครงสร้างระบบเครือข่ายที่ดี
    

### 2. เครื่องมือที่ต้องนำมาฝึกใช้งาน (Essential Tool)

- **`pyang` (Python Library):** เป็นเครื่องมือหลักที่วิศวกรระบบเครือข่ายอัตโนมัติทุกคนต้องใช้ หน้าที่ของมันคือการแปลงไฟล์ YANG ที่เป็นโค้ดซับซ้อน ให้กลายเป็น **โครงสร้างต้นไม้ (Tree Structure)** ที่อ่านง่ายบนหน้าจอเทอร์มินัล
    

Plaintext

```
# ตัวอย่างโครงสร้างต้นไม้ที่ได้จากการใช้เครื่องมือ pyang
module: ietf-interfaces
  +--rw interfaces
     +--rw interface* [name]
        +--rw name         string
        +--rw description?  string
        +--rw type         identityref
        +--rw enabled?     boolean
```

_จากโครงสร้างนี้จะทำให้เราเห็นทันทีว่าเวลาจะยิง RESTCONF API (HTTP GET) เพื่อดึงข้อมูลอินเตอร์เฟสในกระบวนการ Network Discovery จะต้องเข้าถึง Key ชื่ออะไรบ้างตามลำดับชั้น_

คุณต้องการดูตัวอย่างการใช้เครื่องมือ `pyang` แปลงไฟล์ข้อมูลจริงออกมาดูโครงสร้าง หรืออยากเห็นการเปรียบเทียบว่าข้อมูลอินเตอร์เฟสตามโครงสร้าง YANG จะกลายร่างเป็น JSON ใน RESTCONF หน้าตาแบบไหนครับ?

### ความจำเป็นของ YANG Model

YANG Model **มีความจำเป็นอย่างยิ่ง** สำหรับการทำ Network Automation ในปัจจุบัน โดยเฉพาะเมื่อต้องจัดการกับอุปกรณ์รุ่นใหม่ๆ แต่สาเหตุที่มันไม่ถูกจัดเป็น 1 ใน 5 กลุ่มหลัก (แกนกลาง) เป็นเพราะ **YANG ไม่ใช่ "เครื่องมือ (Tool)" ที่ใช้รันสคริปต์ และไม่ใช่ "กระบวนการทำงาน (Process)"** YANG เป็นเพียง **"มาตรฐานโครงสร้างข้อมูล (Data Modeling Standard / Blueprint)"** ที่เป็นรากฐานซ่อนอยู่เบื้องหลังการทำงานของกลุ่มหลักเหล่านั้น เปรียบเสมือน 5 กลุ่มหลักคือ "แผนกต่างๆ ในบริษัท" ส่วน YANG Model คือ "ไวยากรณ์ภาษากลาง" ที่อุปกรณ์และเครื่องมือในบริษัทนั้นใช้สื่อสารกัน

### YANG Model ซ่อนอยู่ในส่วนใดของ 5 กลุ่มหลัก?

หากนำ YANG Model ไปทาบกับ 5 กลุ่มหลักที่คุณกำลังศึกษา มันจะแทรกซึมและเป็นกลไกขับเคลื่อนให้กับ 3 กลุ่ม ดังนี้:

**1. ซ่อนอยู่ในกลุ่มที่ 2: Network Discovery (บทบาทที่ชัดเจนที่สุด)**

- เมื่อคุณใช้ `requests` ยิง RESTCONF API หรือใช้ `ncclient` ยิง NETCONF API เพื่อดึงข้อมูลสถานะเครือข่าย รูปแบบข้อมูล (JSON หรือ XML) ที่อุปกรณ์ส่งกลับมาให้คุณ **ถูกกำหนดโครงสร้างและตั้งชื่อตัวแปรตาม YANG Model ทั้งหมด**
    
- หากคุณไม่เข้าใจสคีมาของ YANG คุณจะไม่รู้เลยว่าต้องชี้ URL (Endpoint) ไปที่ Path ใด หรือต้องเขียนโค้ด Python เข้าถึง Key/Value ตัวไหนเพื่อดึงตาราง ARP ออกมา
    

**2. ซ่อนอยู่ในกลุ่มที่ 1: Script-Driven & Multi-Vendor Automation**

- ในอดีต เครื่องมืออย่าง NAPALM ถูกสร้างขึ้นมาเพื่อทำหน้าที่เป็น "ตัวกลาง" แปลงคำสั่งให้ใช้ได้หลายค่าย แต่ในปัจจุบัน ผู้ให้บริการเครือข่ายระดับโลกได้ร่วมกันสร้างมาตรฐาน YANG ที่เรียกว่า **OpenConfig** * เป้าหมายของ OpenConfig คือการบังคับให้อุปกรณ์ทุกค่าย (Cisco, Juniper, Arista) ใช้ YANG Model หน้าตาเหมือนกัน ทำให้คุณสามารถเขียน JSON Payload ชุดเดียว และส่งผ่าน API ไปตั้งค่าอุปกรณ์ได้ทุกยี่ห้อโดยไม่ต้องพึ่งพาตัวกลางอย่าง NAPALM อีกต่อไป
    

**3. ซ่อนอยู่ในกลุ่มที่ 4: Security Automation & Policy Validation**

- การตรวจสอบค่าความปลอดภัย (เช่น กฎของ CIS) หากต้องใช้ TextFSM สกัดข้อความดิบจาก CLI จะมีความเสี่ยงที่ข้อความจะคลาดเคลื่อนสูง
    
- แต่หากดึงข้อมูลคอนฟิกผ่าน NETCONF/RESTCONF ที่อ้างอิงโครงสร้าง YANG คุณจะได้โครงสร้างข้อมูลที่เป็นระบบและชัดเจน ทำให้สามารถเขียนสคริปต์ตรวจสอบความถูกต้อง (Validate) หรือเทียบค่าเกณฑ์มาตรฐานได้แม่นยำ 100% ทันที
    

**สรุป:** YANG ไม่ใช่เครื่องมือที่จับต้องได้เหมือน Python หรือ Ansible แต่เป็นองค์ความรู้พื้นฐาน (Prerequisite) ที่คุณต้องมี เพื่อให้สามารถดึงข้อมูลจาก API ในกลุ่มที่ 2 มาใช้งานได้อย่างถูกต้องและมีประสิทธิภาพ

ต้องการดูตัวอย่างการแปลงโครงสร้างจาก YANG Tree ให้กลายเป็น JSON Payload ที่ใช้ยิงผ่าน RESTCONF API ในกระบวนการ Network Discovery หรือต้องการข้ามไปศึกษาเรื่อง AI Integration & Configuration Generation ในกลุ่มที่ 3 ต่อครับ?
