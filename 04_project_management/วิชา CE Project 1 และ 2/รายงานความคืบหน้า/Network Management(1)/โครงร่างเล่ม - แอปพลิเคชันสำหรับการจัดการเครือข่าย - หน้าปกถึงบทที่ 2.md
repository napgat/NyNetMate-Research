## แนวทางของเล่มนี้

เล่มนี้อธิบายการจัดการข้อมูลอุปกรณ์ การเก็บสถานะแบบอ่านอย่างเดียว การแสดงภาพรวมเครือข่าย และแผนผังที่ตรวจย้อนกลับไปยังหลักฐานได้ รวมถึง Authentication/RBAC และ Audit Trail ที่รองรับการใช้งานส่วน Network Management

Dashboard ในเล่มนี้สรุป Device, Reachability, Collection Status, Data Freshness และปัญหาปฏิบัติการตามขอบเขตที่พัฒนา ไม่รวม CIS Summary เป็นผลงานที่ต้องส่งของกลุ่มนี้ งาน CIS Validation, Configuration Generation, Version Control และ Deployment เป็นขอบเขตของส่วนที่ 2

การแบ่งขอบเขตในเอกสารนี้เป็นข้อเสนอสำหรับเรียบเรียงเล่มกลุ่ม 1 ไม่ใช่การแก้เอกสาร MVP ของระบบรวม รายละเอียด Dashboard เดิมบางฉบับมี Security Summary ของระบบรวม ต้องเลือกใช้เฉพาะหัวข้อ Network Management เมื่อเรียบเรียงเล่มนี้

ประกาศ Classroom วันที่ 8 กันยายน 2569 อนุญาตให้จัดรายละเอียดเนื้อหา รูป และตัวอย่างโปรแกรมแยกตามบท และให้ขอบเขตร่างโครงงาน 1 ประมาณ 30% อยู่ในดุลยพินิจอาจารย์ที่ปรึกษา ประกาศไม่ได้ยืนยันว่าการมีเพียงบทที่ 1–2 ถือว่าครบ 30% และไม่ได้กำหนดรายการหน้าส่วนนำทั้งหมด โครงต่อไปนี้จึงเป็นแผนจัดเนื้อหา ไม่ใช่แบบฟอร์มสถาบันฉบับยืนยัน

# บทที่ 1 บทนำ

## 1.1 ความเป็นมาและความสำคัญของปัญหา

**จุดประสงค์ของหัวข้อนี้:** ทำให้ผู้อ่านเข้าใจว่าผู้ดูแลเครือข่ายพบปัญหาอะไร และเหตุใดจึงต้องพัฒนาแอปพลิเคชันนี้

วางเนื้อหาเป็นประมาณ 5 ย่อหน้า:

1. **บริบทการทำงาน:** ผู้ดูแลต้องรู้ตัวตนอุปกรณ์ Interface สถานะล่าสุด และการเชื่อมต่อระหว่างอุปกรณ์ เพื่อเลือกจุดตรวจสอบปัญหาได้อย่างเหมาะสม
2. **ปัญหา Inventory:** รายละเอียดอุปกรณ์กระจัดกระจายหรือไม่เป็นปัจจุบัน ทำให้ค้นหาอุปกรณ์และเชื่อมโยงข้อมูลจากหลายแหล่งได้ยาก ยกตัวอย่างสถานการณ์ที่ทีมมีหลักฐานหรือเคยสังเกตจริง
3. **ปัญหาการตีความสถานะ:** อุปกรณ์ไม่ตอบสนอง การเก็บข้อมูลล้มเหลว และข้อมูลเก่ามีความหมายต่างกัน การใช้สถานะ Online/Offline เพียงอย่างเดียวอาจไม่เพียงพอสำหรับการตัดสินใจ
4. **ปัญหา Topology:** แผนผังที่ปรับด้วยมืออาจไม่ทันการเปลี่ยนแปลง ข้อมูลเพื่อนบ้านที่พบเพียงฝั่งเดียวหรือข้อมูลเก่าต้องแสดงข้อจำกัดของหลักฐาน
5. **แนวทางโครงงาน:** เสนอแหล่งข้อมูลอุปกรณ์กลาง การเก็บข้อมูลแบบอ่านอย่างเดียว Dashboard ที่แยกสถานะ และ Topology จากหลักฐาน โดยใช้ Cisco IOS เป็น baseline และทดสอบเฉพาะ Isolated Lab

**สิ่งที่ต้องเติม:** สถานการณ์ตัวอย่างของผู้ใช้เป้าหมาย แหล่งอ้างอิงที่รองรับปัญหา และเหตุผลที่เลือกขอบเขตเล็กสำหรับทีม ไม่อ้างว่าทุกองค์กรประสบปัญหาเดียวกันหากไม่มีหลักฐานสำรวจ

**รูปที่อาจเพิ่ม:** รูปที่ 1.1 ภาพเปรียบเทียบกระบวนการเดิมกับแนวทางที่เสนอ แสดงการรวบรวมข้อมูลและการเปิดดูหลักฐานในหน้าเดียว

## 1.2 วัตถุประสงค์ของโครงงาน

เสนอให้มี 4–5 ข้อ โดยเชื่อมกับฟังก์ชันและการทดสอบที่ทำได้จริง:

1. เพื่อพัฒนาเว็บแอปพลิเคชันสำหรับจัดเก็บและบริหารจัดการรายละเอียดอุปกรณ์เครือข่ายเป็นแหล่งข้อมูลกลาง
2. เพื่อพัฒนาแนวทางเก็บสถานะจากอุปกรณ์แบบอ่านอย่างเดียว พร้อมระบุผลการเก็บและเวลาที่ข้อมูลได้รับการตรวจสอบ
3. เพื่อแสดงภาพรวมที่แยก Reachability, Collection Status, Operational State และ Data Freshness ให้ผู้ใช้ตรวจสอบปัญหาเบื้องต้นได้
4. เพื่อแสดงแผนผังเครือข่ายจากหลักฐาน LLDP/CDP พร้อมอ้างกลับไปยังอุปกรณ์ Interface และเวลาที่เก็บข้อมูล
5. เพื่อควบคุมการเข้าถึงและบันทึกกิจกรรมสำคัญของ Network Management ตามบทบาทผู้ใช้

**สิ่งที่ต้องเติม:** ตรวจให้วัตถุประสงค์ทุกข้อมีงานเจ้าของและแผนทดสอบรองรับ หากฟังก์ชันใดยังไม่ยืนยันในขอบเขต ให้ระบุเป็นแผนหรือปรับวัตถุประสงค์ ไม่ใช้คำรับรองว่า “ถูกต้อง 100%”

## 1.3 ขอบเขตของโครงงาน

### 1.3.1 ผู้ใช้งานและสภาพแวดล้อม

- ผู้ใช้เป้าหมายคือผู้ดูแลหรือผู้ปฏิบัติงานด้านเครือข่ายในสภาพแวดล้อมทดลองที่ทีมกำหนด
- ระบบเป็นเว็บแอปพลิเคชัน เข้าถึงผ่าน Browser โดย Backend เป็นผู้ติดต่อ Collector และฐานข้อมูล
- อุปกรณ์ baseline คือ Cisco IOS; เติมรุ่นและเวอร์ชันเมื่อมี Test Sheet
- Huawei/MikroTik เป็น candidate เท่านั้น ต้องแยกผลทดสอบ simulation กับ hardware จริง

### 1.3.2 Device Inventory และ Manual Enrollment

เติมรายการรายละเอียดที่ต้องจัดเก็บ เช่น Hostname, Management Address, Vendor, Model, OS Version, Site/Group และ Interface ระบุวิธีเพิ่มอุปกรณ์ ดู/ค้นหา/แก้ไขรายการ และแนวทางอ้างอิง Credential โดยไม่เปิดเผย Secret

### 1.3.3 การเก็บข้อมูลและ Network Discovery

ระบุเป้าหมายที่อนุญาต วิธีเก็บแบบอ่านอย่างเดียว โปรโตคอลที่อุปกรณ์จริงรองรับ และผลที่เก็บได้ เช่น Interface, Route และ Neighbor Observation แยกการ Refresh อุปกรณ์ที่ลงทะเบียนออกจากการค้นหาอุปกรณ์ใหม่

ไม่ทำ Scan เครือข่ายมหาวิทยาลัย และไม่เขียนว่ารองรับโปรโตคอล/รุ่นใดครบแล้วโดยไม่มีผลทดสอบ

### 1.3.4 Dashboard & Monitoring

เติมขอบเขตข้อมูลที่แสดง ได้แก่ จำนวนอุปกรณ์ สถานะการติดต่อ ผลการเก็บข้อมูล เวลาที่เก็บสำเร็จล่าสุด สถานะความเก่า และทางลัดไปดูหลักฐาน หากยืนยัน Operational Monitoring ระยะ P2 แล้ว จึงเติม Expected State, Critical Uplink/WAN, Err-disabled และ Missing Expected Default Route ตามข้อกำหนดที่เลือก

ระบุว่าหน้าจอแสดง Snapshot ล่าสุดตามการเก็บข้อมูล ไม่ใช้คำว่า Real-time หากไม่มีการเก็บต่อเนื่อง และไม่รวม CIS/Configuration Summary เป็น deliverable ของเล่มนี้

### 1.3.5 Network Topology Visualization

เติมการแสดง Router/Switch, เส้นเชื่อมและ Interface สองฝั่ง แหล่งหลักฐาน เวลา และสถานะที่ระบบรองรับ เช่น One-sided, Corroborated, Conflict, Stale หรือ Unresolved รวมถึง Zoom/Pan และการดูรายละเอียด แยกการเปลี่ยน Layout ออกจากการเปลี่ยนเครือข่ายจริง

### 1.3.6 Authentication/RBAC และ Audit Trail

เติมบทบาท Admin/Operator/Viewer สิทธิ์ดูข้อมูล สั่ง Refresh แก้ Inventory หรือ Expected State รวมถึงกิจกรรมที่บันทึก เช่น Login, เพิ่มอุปกรณ์ และสั่งเก็บข้อมูล กำหนดว่า Password และ Token ไม่ถูกบันทึกใน Log

### 1.3.7 ระยะดำเนินงานและขอบเขตที่ไม่รวม

- แยกฐานงาน P1 ได้แก่ Auth, Inventory, Dashboard พื้นฐาน และ Audit ออกจาก Discovery, Topology และ Operational Monitoring ที่วางไว้ใน P2 ตามแผนเดิม
- บทที่ 1 อธิบายเป้าหมายของโครงงาน; บทที่ 3–4 จะรายงานว่าอะไร Planned, Prototype, Implemented และ Tested
- ไม่รวมการสร้าง Config, การตรวจ CIS, Config Version Control และ Deployment ซึ่งเป็นหัวข้อของส่วนที่ 2
- ไม่รวมการส่งคำสั่งเปลี่ยนการตั้งค่าอุปกรณ์ในขอบเขตของกลุ่ม 1, การเฝ้าตรวจแบบ Enterprise ตลอดเวลา, Cross-device Impact Simulation และ AI สร้างเส้นเชื่อม
- หากการแบ่งสองเล่มทำให้ต้องเปลี่ยน Priority เดิม ให้บันทึกเป็นข้อเสนอรอทีม/อาจารย์ยืนยันก่อนแก้ Scope กลาง

**ตารางที่ควรเพิ่ม:** ตารางที่ 1.1 ขอบเขตฟังก์ชัน เจ้าของข้อมูล ระยะพัฒนา และสิ่งที่ไม่รวม

## 1.4 วิธีการดำเนินงาน

เรียงขั้นตอนให้สอดคล้องกับงานของกลุ่ม:

1. ศึกษาปัญหาและระบุผู้ใช้เป้าหมาย
2. ทบทวนระบบที่เกี่ยวข้องและกำหนดขอบเขต MVP
3. กำหนดเจ้าของข้อมูลและ Data Contract ของ Inventory, Collection, Dashboard และ Topology
4. ออกแบบฐานข้อมูล ระบบสิทธิ์ และโครงสร้าง API
5. ออกแบบ UI และกรณี Empty/Error/Stale
6. พัฒนาโมดูลตามลำดับความสำคัญ
7. จัดเตรียมข้อมูลทดสอบและ Isolated Lab
8. ทดสอบหน่วยย่อย การเชื่อมระบบ และความถูกต้องของข้อมูลแสดงผล
9. วิเคราะห์ข้อผิดพลาด ปรับปรุงระบบ และจัดทำเอกสาร

**สิ่งที่ต้องเติม:** กำหนดผู้รับผิดชอบของสมาชิกกลุ่ม 1 ทั้งสองคนตาม Feature และช่วงเวลาที่ทำจริง ไม่ดึงรายละเอียด implementation ของเพื่อนที่ยังไม่ได้ตรวจสอบมารับรอง

**ตารางที่ควรเพิ่ม:** ตารางที่ 1.2 แผนดำเนินงานและผู้รับผิดชอบตามเดือน/สัปดาห์

## 1.5 ประโยชน์ที่คาดว่าจะได้รับ

เติมประโยชน์ที่สัมพันธ์กับวัตถุประสงค์:

- ผู้ใช้เข้าถึงรายละเอียดอุปกรณ์จากแหล่งข้อมูลกลางได้สะดวกขึ้น
- ผู้ใช้แยกปัญหาการติดต่อ การเก็บข้อมูล และสถานะปฏิบัติการได้ชัดเจนขึ้น
- ผู้ใช้ทราบอายุและข้อจำกัดของข้อมูลก่อนนำไปประกอบการตัดสินใจ
- ผู้ใช้ตรวจสอบเส้นเชื่อมและ Interface จากหลักฐานที่อ้างอิงได้
- ผู้ดูแลตรวจสอบกิจกรรมสำคัญตามผู้กระทำและเวลาได้

ใช้ถ้อยคำว่า “คาดว่าจะ” ในหัวข้อนี้ ผลการลดเวลา/ลดการแจ้งเตือนผิดพลาดต้องรายงานหลังทดลองจริง

## 1.6 โครงสร้างของปริญญานิพนธ์

เติมคำอธิบายสั้น ๆ ของแต่ละบท:

- บทที่ 1: ปัญหา วัตถุประสงค์ ขอบเขต และวิธีดำเนินงาน
- บทที่ 2: ทฤษฎี โปรโตคอล แนวคิด และระบบที่เกี่ยวข้อง
- บทที่ 3: ความต้องการ สถาปัตยกรรม ฐานข้อมูล API และการพัฒนา
- บทที่ 4: สภาพแวดล้อม กรณีทดสอบ ผลการทดลอง และการวิเคราะห์
- บทที่ 5: ผลลัพธ์ ข้อจำกัด และแนวทางพัฒนาต่อ

# บทที่ 2 ทฤษฎีและงานที่เกี่ยวข้อง

บทนี้อธิบายหลักการที่ใช้เป็นฐานการออกแบบ พร้อมอ้างอิงแหล่งต้นฉบับ รายละเอียดตารางฐานข้อมูลจริง Endpoint, Source Code และรูป UI ของ MyNetMate ให้ไว้บทที่ 3 ส่วนผลทดสอบไว้บทที่ 4

## 2.1 พื้นฐานเครือข่ายที่เกี่ยวข้อง

### 2.1.1 Router, Switch และ Interface

เติมหน้าที่ของอุปกรณ์และความหมายของ Interface ที่ระบบใช้เป็นหน่วยตรวจสอบ อธิบายความต่างระหว่าง Admin State และ Operational State ด้วยตัวอย่าง

### 2.1.2 IP Address และ Management Address

เติมหลักการระบุตัวอุปกรณ์ผ่าน Management Address และการที่หนึ่งอุปกรณ์อาจมีหลาย Interface/IP ไม่ใช้ IP เพียงค่าเดียวเป็นตัวตนถาวรโดยไม่มีนโยบายรองรับ

### 2.1.3 VLAN, Access/Trunk, Uplink และ WAN

เติมแนวคิดเฉพาะที่จำเป็นต่อการตีความสถานะ ไม่ต้องสอนคำสั่ง Config อย่างละเอียด ยกตัวอย่าง Access Port Down ที่อาจเป็นปกติ และ Uplink Down ที่ควรตรวจสอบ

### 2.1.4 Default Route

เติมความหมายและบทบาทของเส้นทางออก อธิบายว่าการไม่มี Default Route จะถือเป็นปัญหาต่อเมื่ออุปกรณ์นั้นถูกกำหนดให้คาดหวังว่าต้องมี

**ภาพที่เสนอ:** รูปที่ 2.1 ตัวอย่างเครือข่าย Lab ขนาดเล็กที่ใช้ประกอบคำศัพท์ ระบุว่าเป็นภาพสมมติ

## 2.2 Device Inventory และ Source of Truth

### 2.2.1 ตัวตนอุปกรณ์และข้อมูลส่วนกลาง

เติมแนวคิด Device ID, Interface ID, Hostname, Vendor/Platform และความสัมพันธ์ Device–Interface–Address รวมถึงเหตุผลที่โมดูลอื่นควรใช้อ้างอิงแทนสร้างตัวตนอุปกรณ์ซ้ำ

### 2.2.2 Intended/Expected State กับ Observed State

เติมความต่างระหว่างสิ่งที่ผู้ใช้คาดหวังและสิ่งที่เก็บได้จริง ข้อมูลทั้งสองควรมีเจ้าของและเวลาที่ชัดเจน ไม่แก้ Expected State ตามค่าที่ตรวจพบโดยอัตโนมัติ

### 2.2.3 Data Ownership และ Data Contract

เติมแนวคิดการแบ่งเจ้าของข้อมูล รูปแบบข้อมูลรับส่ง และการตรวจความถูกต้องของ Schema ตัวอย่างใช้ Inventory ส่ง Device/Interface ให้ Dashboard หรือ Topology โดยไม่ต้องอธิบาย Configuration ของส่วนที่ 2

**ตารางที่เสนอ:** ตารางที่ 2.1 ตัวอย่างข้อมูลตัวตนถาวรเทียบกับข้อมูลสถานะตามเวลา

## 2.3 การเก็บข้อมูลเครือข่ายแบบอ่านอย่างเดียว

### 2.3.1 Reachability Check

เติมหลักการตรวจการตอบสนอง Timeout และข้อจำกัดของ ICMP ระบุว่าการไม่ตอบ ICMP เพียงอย่างเดียวอาจไม่เพียงพอให้สรุปว่าอุปกรณ์ดับ

### 2.3.2 SNMP

เติมบทบาท Manager/Agent, MIB/OID และแนวคิดการอ่านค่าที่ใช้ในโครงงาน เลือกอธิบายรุ่น SNMP ตามที่ Lab ใช้จริง และระบุข้อจำกัดด้านการปกป้อง Credential

### 2.3.3 SSH และการแปลงผลคำสั่ง

เติมการอ่านข้อมูลด้วยคำสั่งที่อนุญาต การแปลง Raw Output เป็นข้อมูลกลาง และเหตุผลที่ต้องแยก Collector/Parser ตาม Platform ทั้งนี้ SSH เป็นช่องทางสื่อสาร ไม่ได้ทำให้คำสั่งทุกคำสั่งเป็น Read-only

### 2.3.4 LLDP และ CDP

เติมการประกาศตัวตน/พอร์ตของเพื่อนบ้าน ข้อมูล Local/Remote Interface และเหตุผลที่หลักฐานฝั่งเดียวกับสองฝั่งอาจมีน้ำหนักต่างกัน ไม่สรุปว่าพบ Neighbor แล้วเส้นเชื่อมยังใช้งานได้ในเวลาปัจจุบันโดยไม่ดูเวลา

### 2.3.5 ขอบเขตการค้นหาและการ Refresh

เติมความต่างระหว่างการค้นหาอุปกรณ์ใหม่กับการเก็บข้อมูลของอุปกรณ์เดิม ใช้ตัวอย่าง Allowlist และ Isolated Lab พร้อมแยก Partial Success, Timeout และ Parser Failure

**ภาพที่เสนอ:** รูปที่ 2.2 กระบวนการทั่วไป Device → Collector → Parser → Observation/Snapshot

## 2.4 สถานะปฏิบัติการ ความใหม่ของข้อมูล และ Expected State

### 2.4.1 การแยกสถานะสี่มิติ

อธิบาย Reachability, Collection Status, Operational State และ Data Freshness แยกความหมายกัน ให้ตัวอย่างกรณีอุปกรณ์ติดต่อได้แต่ Parser ล้มเหลว หรือยังแสดง Snapshot รอบก่อนเพราะ Refresh ล่าสุดล้มเหลว

### 2.4.2 Current Snapshot และ Last Known State

เติมเวลาเก็บสำเร็จล่าสุด เวลาพยายามเก็บล่าสุด และความต่างระหว่างข้อมูลปัจจุบันกับข้อมูลล่าสุดที่มี ห้ามนำ Last Known State ไปแสดงเหมือนเป็นผลสด

### 2.4.3 Expected State และ Criticality

เติมหลักการระบุ Role ของพอร์ตและความสำคัญก่อนสร้างข้อสรุปปัญหา แยกพอร์ตที่ผู้ใช้อนุญาตให้ Down ออกจากพอร์ตที่คาดว่าต้อง Up

### 2.4.4 การสรุปปัญหาด้วยกฎแน่นอน

เติมตัวอย่างกฎ “Critical Uplink ที่คาดว่าต้อง Up แต่ผลล่าสุดเป็น Down” และอธิบายว่าการตรวจพบเงื่อนไขผิดปกติไม่ได้แปลว่าระบบทราบสาเหตุรากของปัญหา

**ตารางที่เสนอ:** ตารางที่ 2.2 สถานการณ์ตัวอย่างและผลการตีความในแต่ละมิติ

## 2.5 Network Topology และหลักฐานเส้นเชื่อม

### 2.5.1 กราฟ Node, Edge และ Endpoint

เติมแบบจำลองอุปกรณ์เป็น Node และเส้นเชื่อมเป็น Edge พร้อม Interface Endpoint อธิบาย Parallel Links ซึ่งคู่ Device เดียวอาจเชื่อมผ่านหลายพอร์ต

### 2.5.2 การจับคู่หลักฐาน LLDP/CDP

เติมหลักการจับคู่ Local/Remote Identity และ Port ID อธิบาย One-sided, Corroborated, Conflict และ Unresolved ในฐานะสถานะของหลักฐานที่โครงงานเสนอ ไม่อ้างว่าเป็นการจัดระดับตามมาตรฐาน LLDP โดยตรง

### 2.5.3 Freshness และการเปลี่ยนแปลงเส้นเชื่อม

เติมเหตุผลที่ไม่ควรลบ Link ทันทีเมื่อเก็บข้อมูลล้มเหลวรอบเดียว และอธิบายการแยกหลักฐานที่สังเกตได้ออกจาก Current Link ที่ใช้แสดงผล

### 2.5.4 การจัดวางและการโต้ตอบ

เติมหลักการ Auto Layout, Zoom/Pan และการเลือก Node ให้เน้นว่าตำแหน่งบนจอเป็นข้อมูล Layout การลาก Node ไม่ได้เปลี่ยนการเชื่อมต่อจริง รายละเอียดการใช้ Dagre/Isometric ในระบบให้ไว้บทที่ 3

**ภาพที่เสนอ:** รูปที่ 2.3 ตัวอย่างหลักฐานฝั่งเดียว สองฝั่ง และข้อมูลขัดแย้งบนเครือข่ายสมมติ

## 2.6 Dashboard สำหรับการตัดสินใจของผู้ดูแลเครือข่าย

### 2.6.1 คำถามที่ Dashboard ต้องตอบ

เติมว่าผู้ใช้ต้องรู้ “อุปกรณ์ใดผิดปกติ”, “ผลที่เห็นมาจากเมื่อไร” และ “ควรเปิดหลักฐานอะไรต่อ” แล้วเชื่อมคำถามกับตัวสรุปและหน้ารายละเอียด

### 2.6.2 Overview และ Drill-down

เติมแนวคิดภาพรวม → รายการปัญหา → Device/Interface/Route Detail ใช้กรณีตัวอย่าง Critical Uplink แทนการแสดงกราฟจำนวนมากโดยไม่มีการกระทำต่อ

### 2.6.3 Empty, Error, Unknown และ Stale

เติมความหมายของสถานะหน้าจอและการแสดงเวลา ต้องแยก “ไม่มีปัญหา” ออกจาก “ยังไม่มีข้อมูล” และใช้ข้อความ/สัญลักษณ์ร่วมกับสี

**ตารางที่เสนอ:** ตารางที่ 2.3 คำถามผู้ใช้ → ตัวสรุป → ข้อมูลต้นทาง → การเปิดดูรายละเอียด

## 2.7 การควบคุมการเข้าถึงและการตรวจสอบย้อนหลัง

### 2.7.1 Authentication กับ Authorization

เติมความต่างระหว่างยืนยันตัวตนและตรวจสิทธิ์ รวมถึงบทบาท Admin, Operator, Viewer ตามนโยบายที่กลุ่มเลือกใช้

### 2.7.2 Server-side Session และ Password Hashing

เติมหลักการ Token แบบสุ่ม การเก็บ Hash, Cookie, Session Expiration/Revocation และ Password Hashing พร้อมอ้างอิงด้านความปลอดภัย อธิบาย CSRF และ Rate Limiting เท่าที่จำเป็นต่อระบบ

### 2.7.3 Audit Trail และการปกปิดข้อมูลลับ

เติม Actor, Action, Resource, Time, Result และเหตุผลที่ต้องคัดกรอง Password/Token/Credential ก่อนบันทึก จำกัดตัวอย่างเหตุการณ์ไว้ที่ Network Management

หัวข้อนี้เป็นความปลอดภัยของเว็บแอปพลิเคชันและข้อมูลผู้ใช้ ไม่ใช่การตรวจ CIS ของ Configuration

## 2.8 สถาปัตยกรรมและเทคโนโลยีที่เกี่ยวข้อง

### 2.8.1 Web Application และ API

เติม Client–Server, HTTP/JSON และการแบ่ง Frontend/Backend อธิบายหน้าที่ของ React, FastAPI และ Schema Validation โดยยึด Manifest ของระบบจริง

### 2.8.2 ฐานข้อมูลเชิงสัมพันธ์

เติม Primary Key, Foreign Key, Transaction และ Migration ที่เกี่ยวข้องกับความสัมพันธ์ของอุปกรณ์และข้อมูลตามเวลา อธิบายบทบาท PostgreSQL, SQLAlchemy และ Alembic ในฐานะเทคโนโลยีเป้าหมาย/ที่พบใน Manifest ตามหลักฐาน

### 2.8.3 การจัดการ State และข้อมูลจาก API

เติมความต่างระหว่าง UI State และ Server Data อธิบายบทบาท Router, React Query และ Jotai ตามที่ติดตั้งจริง รายละเอียดการนำมาใช้กับหน้า Topology ไว้บทที่ 3

ไม่จำเป็นต้องใส่เวอร์ชันทุกไลบรารีในบททฤษฎี ให้บันทึกเวอร์ชันที่ใช้ทดลองในบทที่ 3 หรือ 4 และหลีกเลี่ยงการเขียนบทนี้เป็นคู่มือติดตั้งซอฟต์แวร์

## 2.9 ระบบและงานที่เกี่ยวข้อง

### 2.9.1 NetBox

เติมเป้าหมายด้าน Source of Truth/Inventory ที่ตรวจจากเอกสารทางการ เปรียบเทียบแนวทางแยกข้อมูลที่คาดหวังกับข้อมูลที่สังเกตจริง ตรวจ Edition/Plugin ที่นำมาเทียบก่อนระบุข้อจำกัด

### 2.9.2 LibreNMS

เติม Discovery, Monitoring และ Network Map ตามเอกสารทางการ ชี้ว่าการใช้ SNMP/LLDP/CDP หรือมี Dashboard ไม่ใช่ความสามารถใหม่ของ MyNetMate

### 2.9.3 Cisco Catalyst Center

เติม Inventory, Topology และ Assurance ตามรุ่นเอกสารที่ตรวจสอบ ใช้เป็นตัวอย่างแนวทางระบบองค์กร โดยไม่อ้างว่า MyNetMate รองรับเทียบเท่า

### 2.9.4 การเปรียบเทียบและแนวทางที่เลือก

ทำตารางเปรียบเทียบด้านเป้าหมายผู้ใช้ Inventory, Operational State, Topology Evidence, Freshness และขอบเขต Lab ระบุ “ไม่พบข้อมูลในเอกสารที่ตรวจ” เมื่อยังยืนยันไม่ได้ แทนการตัดสินว่าเครื่องมือไม่มีฟีเจอร์นั้น

เสนอคุณค่าของโครงงานในฐานะการออกแบบและประเมินระบบขนาดเล็กที่แยกสถานะและตรวจย้อนกลับไปยังหลักฐานได้ ไม่อ้างว่าเป็นระบบแรกหรือเหนือกว่าเครื่องมือทั้งหมด

**ตารางที่เสนอ:** ตารางที่ 2.4 การเปรียบเทียบระบบที่เกี่ยวข้องโดยมีแหล่งอ้างอิงแต่ละแถว

### จุดเชื่อมกับการทดลองในบทที่ 4

เลือกเกณฑ์ที่มีข้อมูลและ Lab รองรับ เช่น ความถูกต้องของการตีความสถานะใน Test Cases หรือความถูกต้องของ Endpoint ใน Topology เทียบกับสายเชื่อมจริง ประเด็นการลด False Alert ด้วย Expected State เป็นสมมติฐานที่จะทดสอบเมื่อพัฒนาฟังก์ชันแล้ว ไม่ใช่ผลที่สรุปล่วงหน้า

## แหล่งภายนอกเริ่มต้นสำหรับบทที่ 2

- SNMP Architecture: [RFC 3411 — RFC Editor](https://www.rfc-editor.org/info/rfc3411/). ใช้เป็นแหล่งหลักด้าน Architecture และตรวจ RFC ที่เกี่ยวข้องกับประเด็นที่จะอธิบายเพิ่มเติม

- Session: [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- Audit/Logging: [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)
- Source of Truth: [NetBox Introduction](https://netboxlabs.com/docs/netbox/v3.7/introduction/) — หน้านี้เป็นเอกสาร v3.7; ตรวจรุ่นที่ใช้เปรียบเทียบและข้อมูลปัจจุบันก่อนสรุปข้อจำกัด
- Discovery: [LibreNMS Auto-discovery](https://docs.librenms.org/Extensions/Auto-Discovery/)
- Topology ตัวอย่างระบบองค์กร: [Cisco Catalyst Center Topology API](https://developer.cisco.com/docs/catalyst-center/topology/)

ต้องเติมแหล่งเฉพาะเรื่องที่ยังไม่มี เช่น Cisco CDP/Interface/Route ของ Platform ที่ทดลอง, Password Hashing/RBAC และหลักการ Dashboard โดยเลือกเอกสารต้นฉบับ ตำรา หรือบทความวิชาการที่อ่านจริง ไม่ใช่สร้างรายการอ้างอิงจากชื่อเรื่องเพียงอย่างเดียว
