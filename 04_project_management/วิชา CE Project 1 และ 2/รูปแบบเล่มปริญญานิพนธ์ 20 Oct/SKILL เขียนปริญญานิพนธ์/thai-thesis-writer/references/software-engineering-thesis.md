### กลุ่มและผู้รับผิดชอบ

- ใช้ชื่อหัวข้อ สมาชิก หลักสูตร และการแบ่งงานตามกลุ่มที่ยืนยันกับรายวิชา ไม่คัดผู้จัดทำทุกคนของทีมพัฒนาใส่ทุกเล่มโดยอัตโนมัติ
- เอกสาร 01 ระบุกลุ่ม 3–4 คนในหลักสูตรเดียวกัน แต่ [ประกาศ 13 ส.ค. 69](<../../../../รายงานความคืบหน้า/ประกาศใน Classroom วันที่ 13 สิงหา 69_แบ่งกลุ่ม.md>) ให้รายละเอียดเฉพาะ 4D/3DT: กลุ่ม 4 คนแบ่งเป็น 2 กลุ่ม กลุ่มละ 2 คน แยกหัวข้อและสอบ; กลุ่ม 2 คนทำได้ยกเว้นกลุ่มเศษสุดท้ายต้อง 3 คน ส่วนหลักสูตรอื่นทำ 1 คนได้ตามประกาศ ใช้เงื่อนไขที่ตรงกับกลุ่มจริง ไม่เอาจำนวน 3–4 เป็นกฎตายตัว
- หัวหน้ากลุ่มรับผิดชอบสร้างกลุ่ม/ร้องขอหัวข้อและอัปโหลด สมาชิกตอบรับคำเชิญ อาจารย์สร้างและตอบรับหัวข้อ กลุ่มที่ระบบสร้างตามเงื่อนไขไม่ได้ให้ประสานผู้ประสานงานตามประกาศ การลบกลุ่มที่ได้หัวข้อแล้วต้องให้อาจารย์แจ้งตามต้นทาง
- อาจารย์ที่ปรึกษากำกับและพิจารณาเล่ม; เอกสาร 01 ระบุเบื้องต้นรับได้ 2 กลุ่มต่ออาจารย์ กรณีอื่นผ่านผู้ประสานงาน/กรรมการหลักสูตร กรรมการสอบพิจารณาเนื้อหาและอนุมัติการเปลี่ยนหัวข้อร่วมกับที่ปรึกษา ผู้ประสานงานตรวจรูปแบบและกำหนดการ ประธานสอบรวบรวมคะแนน ส่วนกรรมการตรวจผลงานประเมินการสาธิต Project 2

### CE Cloud: ข้อบังคับกับคะแนนเพิ่มพิเศษ

| ประเภท | เกณฑ์จากต้นทาง | วิธีนับความพร้อม |
|---|---|---|
| **ขั้นตอนพื้นฐาน Project 2** | เอกสาร 03 ระบุ Deploy ในเซิร์ฟเวอร์ภาควิชา (CE Cloud) | อยู่ในรายการบังคับของขั้นตอน Project 2 ไม่ย้ายไปเป็นงานสมัครใจเพียงเพราะมีโบนัส CE Cloud |
| **เงื่อนไขพิจารณาโบนัส CE Cloud** | เอกสาร 06 กำหนดเข้าถึงจากภายนอก มี URL/Endpoint และคู่มือเบื้องต้น ให้บริการสู่สาธารณะได้ มี Authentication/Data Protection พื้นฐาน เสถียรไม่มีข้อผิดพลาดกระทบการใช้ปกติ และผ่านที่ปรึกษา/ผู้ดูแล Cloud | ตรวจหลักฐานแต่ละข้อแยกจากการ Deploy สำเร็จ การมีระบบบน Cloud อย่างเดียวไม่รับรองว่าได้โบนัส |
| **เงื่อนไขพิจารณาโบนัสแสดงผลงาน** | ผ่านกรรมการคัดเลือก ยินดีร่วม และอยู่แสดงตลอดเวลาที่กำหนด | แยกจากการสาธิตผลงานที่เป็นขั้นตอนรายวิชา |

โบนัส CE Cloud และโบนัสแสดงผลงาน **รวมกันไม่เกิน 5 คะแนน** ไม่ใช่ 5 คะแนนต่อส่วน ไม่ใช่คะแนนที่ได้รับแน่นอน และเป็นคนละรายการกับ “คะแนนส่วนพิเศษ 10%” ในสัดส่วนคะแนนปกติ หากมีข้อยกเว้นหรือประกาศเปลี่ยนเงื่อนไข ให้บันทึกขอบเขตและหลักฐาน ไม่เพิ่มหรือลดข้อบังคับเอง

สำหรับ MyNetMate การ Deploy เว็บบน CE Cloud ไม่ใช่ SSH Push ไปยังอุปกรณ์จริง และการเข้าถึงเว็บจากภายนอกไม่ได้อนุญาตให้ Scan เครือข่ายมหาวิทยาลัย การตรวจรายการเหล่านี้ไม่ใช่คำสั่งให้อัปโหลด เปิดเผยข้อมูล หรือติดต่อผู้อื่นแทนนักศึกษา

### กำหนดการและเงื่อนไขประเมิน

- ใช้เอกสาร 04 ร่วมกับประกาศเปลี่ยนกำหนด ไม่คัดวันที่เดิมที่ถูกแทนที่แล้ว [ประกาศ 10 ต.ค. 69](<../../../../รายงานความคืบหน้า/ประกาศใน Classroom วันที่ 10 ตค 69_ปรับวันส่ง.md>) เปลี่ยน Project 1: ความคืบหน้า 4 (ร่าง 60%) เป็น 16 ต.ค. 2569 รายงาน/ไฟล์นำเสนอเป็น 13 พ.ย. 2569 และสอบเป็น 23 พ.ย. 2569 ใน snapshot นี้
- Project 1 ความคืบหน้า 1–3 ในเอกสาร 04 คือ 7 ส.ค., 28 ส.ค., 18 ก.ย. 2569; Project 2 ความคืบหน้า 1–5 คือ 4 ธ.ค., 25 ธ.ค. 2569, 15 ม.ค., 5 ก.พ., 26 ก.พ. 2570 ส่วนร่าง/ไฟล์นำเสนอ/แจ้ง kip 12 มี.ค., สอบ 5 เม.ย., สาธิต 7 เม.ย., ฉบับสมบูรณ์/เอกสาร/คู่มือ 9 เม.ย. 2570 มีเครื่องหมายอาจเปลี่ยนตาม Classroom ให้ตรวจประกาศก่อนยืนยันกำหนดส่ง ไม่สร้าง Reminder หรือส่งงานเองจากตารางนี้
- เอกสาร 06 แยกคะแนนปกติเป็นที่ปรึกษา 30%, กรรมการสอบ 50–60%, กรรมการตรวจผลงาน 0–10%, ส่วนพิเศษ 10% ซึ่งรวมรายงานความคืบหน้า/กิจกรรม/สาธิต/บรรยาย ใช้สัดส่วนที่ตรงกับการประเมินนั้น ไม่บวกขอบบนทุกช่วงหรือรับรองคะแนนจากการมีเอกสารอย่างเดียว ที่ปรึกษาไม่ให้คะแนนในส่วนกรรมการสอบ
- บันทึกความเสี่ยงส่งช้า: แจ้งหัวข้อช้าไม่เกิน 7/14 วันหัก 1/3 คะแนน; ความคืบหน้าช้าไม่ได้คะแนนครั้งนั้น; รายงาน/ร่าง/ฉบับสมบูรณ์ช้าไม่เกิน 1/3/7 วันหัก 3/5/10 คะแนน เกิน 7 วันหัก 15 ตามเอกสาร 06 ไม่คำนวณลงโทษแทนผู้สอนหรือขยายเกณฑ์กรณีที่ต้นทางไม่ได้ระบุ
- รูปแบบผิดหักรายการละ 1 คะแนน สำนวน/ประโยคผิดประโยคละ 1 ตั้งค่ากระดาษผิด 5 ฟอนต์ผิด 10; เล่มที่ที่ปรึกษาพิจารณาผ่านส่งให้ผู้ประสานงานช่วยตรวจรูปแบบได้ 1 รอบโดยไม่หักตามต้นทาง ใช้ข้อผ่อนผันรายงานความคืบหน้าเฉพาะขั้นตอนที่ประกาศระบุ
- ตรวจความพร้อมสอบและส่งจบ: ต้องส่งรายงาน/ร่าง ได้รับการพิจารณาให้ขึ้นสอบ เข้าสอบและเซ็นชื่อ เอกสาร 06 ระบุคะแนนรวมต่ำกว่า 60%, กรรมการเกินกึ่งหนึ่งให้ไม่ผ่าน หรือไม่ส่งฉบับสมบูรณ์/เอกสาร/คู่มือเป็นเงื่อนไขไม่ผ่าน การเลื่อนสอบ เหตุสุดวิสัย/เกรด I และกรณีอื่นให้ดำเนินการตามผู้ประสานงาน/กรรมการหลักสูตรและต้นทาง ไม่ตัดสินเกรดหรือยื่นคำร้องเอง

## 2. ประเภทงานและข้อกำหนดเฉพาะ SW_Dev

ส่วนนี้สรุปจาก [05_Project_Types_and_Requirements.md](../../../../05_Project_Types_and_Requirements.md) ใน Vault ตรวจเมื่อ 2026-10-22 เอกสารที่เก็บอยู่ไม่ได้ระบุวันที่ประกาศหรือรุ่น จึงไม่อ้างว่าเป็นฉบับล่าสุด หากใช้ skill นอก Vault ให้ขอไฟล์ต้นทางเมื่อจำเป็นต้องตรวจขอบเขตหรือมีข้อขัดแย้ง

รายวิชาแบ่งประเภทเป็น **HW+SW**, **SW_Dev** และ **Research** ให้บันทึกประเภทที่แจ้งรายวิชาหรืออาจารย์ยืนยัน ไม่เลือก Research หรือเพิ่มเงื่อนไข ML เพียงเพราะระบบเรียก AI API

### สิ่งที่ใช้ประเมิน SW_Dev

- ความเหมาะสมและความจำเป็นของข้อกำหนดในระดับ วศ.บ. คอมพิวเตอร์
- การออกแบบ UX/UI
- แผนภาพอธิบายการทำงานและโครงสร้างโปรแกรม เช่น Use Case, Class, Sequence หรือแบบอื่นที่เหมาะกับระบบ
- Software Architecture Diagram / System Architecture Diagram เพื่ออธิบายโครงสร้างระบบ
- ความสามารถทำงานตามข้อกำหนดและหลักฐานทดสอบ เช่น Unit, Integration หรือวิธีอื่นที่เหมาะกับข้อกำหนด ไม่ตีความว่าต้องใช้ทุกวิธีพร้อมกัน
- การ Deploy และ Integrate ให้เป็นระบบที่ทำงานตามข้อกำหนด คำว่า Deploy ในข้อนี้หมายถึงระบบซอฟต์แวร์ ไม่ใช่สิทธิ์ให้ AI สั่งอุปกรณ์เครือข่ายหรือเผยแพร่ระบบเอง

### เนื้อหาที่บังคับในรายงาน SW_Dev

เอกสารรายวิชาระบุว่าหากไม่มีหรือไม่ครบจะถูกหักคะแนน รวมไม่เกิน 5 คะแนน ข้อกำหนดต่อไปนี้จึงไม่ใช่เพียงตัวเลือกแผนภาพ ใช้ตรวจฉบับส่งตามขั้นตอนจริง ส่วนร่างความคืบหน้าให้บันทึกสิ่งที่ออกแบบแล้ว/ยังวางแผนตามขอบเขตที่ปรึกษา ไม่ตีว่าผลที่ยังไม่ทำเป็นผลสำเร็จ:

| สิ่งที่ต้องมี | วิธีตรวจเนื้อหา |
|---|---|
| ER Diagram อย่างน้อยระดับ 3NF | ระบุ Entity, Attribute, Key, ความสัมพันธ์ และเหตุผลของการ Normalize ให้ตรงกับโครงสร้างข้อมูล |
| ข้อจำกัดการใช้ ID | ต้นทางระบุ “ห้ามใช้ ID ในตารางที่ไม่ใช้ Entity พื้นฐาน” พร้อมตัวอย่างตารางผู้สอนสอนวิชาใด แยกตารางความสัมพันธ์ออกจาก Entity พื้นฐานและพิจารณาคีย์จากความสัมพันธ์ ไม่เติม surrogate ID ให้ทุกตารางโดยอัตโนมัติ |
| Use Case Diagram และ Use Case Description | แสดง Actor, ขอบเขตระบบ และการเชื่อมไปยังคำอธิบายแต่ละ Use Case เช่น เงื่อนไขก่อนเริ่ม ขั้นตอนหลัก/ทางเลือก และผลหลังทำงาน |
| Sequence Diagram อย่างน้อยระดับ Component | แสดงการโต้ตอบระหว่าง Component จริง ลำดับ Request/Response และทางผิดพลาดสำคัญ ให้ตรงกับ Architecture และ Use Case |

ข้อจำกัดเรื่อง ID เป็นถ้อยคำเฉพาะรายวิชา ไม่ใช่กฎทั่วไปว่า associative entity ทุกแบบห้ามมี surrogate key หากแยก Entity พื้นฐานกับตารางความสัมพันธ์ไม่ได้ชัด ให้แสดงแบบจำลองและเหตุผลเพื่อยืนยันเฉพาะกรณี อย่าเปลี่ยนฐานข้อมูลจริงจากการตรวจเล่มโดยอัตโนมัติ

Class Diagram, BPMN หรือแผนภาพอื่นเพิ่มได้เมื่อช่วยอธิบายงาน แต่ไม่ใช้แทนสามรายการบังคับข้างต้น และไม่บังคับทุกชนิดเพิ่มเอง

### เงื่อนไขเพิ่มเมื่อ SW_Dev เน้น ML จริง

ต้องมีที่มาของแนวทางแก้ปัญหาและควรเปรียบเทียบมากกว่าหนึ่งแนวทาง อธิบายอัลกอริทึมหรือเทคนิค ลำดับพัฒนาพร้อมการวิเคราะห์และปรับปรุง วิธีวัดประสิทธิภาพ/ประสิทธิผลที่เป็นมาตรฐาน และเหตุผลเลือกเครื่องมือ เก็บหลักฐาน Data Split, Baseline และผลตามงานที่ทำจริง ไม่แต่งผลหรือบังคับเงื่อนไขนี้กับการใช้ AI เป็นเพียงส่วนเสริม

## 3. เนื้อหาที่ต้องเชื่อมถึงกัน

| ส่วน | หลักฐานที่ควรอธิบาย |
|---|---|
| ปัญหาและวัตถุประสงค์ | ผู้ใช้เป้าหมาย ปัญหาจริง ขอบเขต และสิ่งที่วัดได้ว่าแก้สำเร็จ |
| Requirements | Functional/Non-functional Requirements มีรหัส แหล่งที่มา ลำดับความสำคัญ และเกณฑ์ยอมรับที่ตรวจได้ แยกข้อยืนยันแล้วออกจากข้อเสนอ |
| UX/UI | งานของผู้ใช้ หน้าจอ/Flow ที่รองรับ Use Case สถานะสำเร็จ/ผิดพลาด และการจำกัดสิทธิ์ตามความต้องการ |
| System Design | Architecture, Use Case/Description, Sequence, ER และสัญญา API ที่สัมพันธ์กัน ใช้ชื่อ Component/ข้อมูลให้ตรงกัน |
| Implementation | สิ่งที่พัฒนาจริง ภาษา/Dependency จาก manifest, API, ฐานข้อมูล และข้อจำกัดของรุ่นที่ใช้ ไม่คัดสถานะจากแผนมาเป็นผลสำเร็จ |
| Testing | Test Case, Input/Precondition, Expected Result, Actual Result, Pass/Fail หรือ Not Run พร้อมหลักฐานและสภาพแวดล้อมที่ทำซ้ำได้ |
| Deploy/Integration | ขั้นตอนและสภาพแวดล้อมที่ใช้จริง การเชื่อม Frontend/Backend/Database และหลักฐานการทำงานร่วมกัน ระบุหากยังเป็นแผน |
| Evaluation/Conclusion | ผลตามเกณฑ์ที่ตั้งไว้ ความคลาดเคลื่อน ข้อจำกัด และสิ่งที่ยังต้องทำ ผลสรุปต้องไม่เกินหลักฐาน |

ใช้เกณฑ์ที่เหมาะกับวัตถุประสงค์ เช่น ความถูกต้องตาม Test Case, Response Time หรือ Error Rate ไม่กำหนด Accuracy, จำนวนผู้ตอบแบบสอบถาม หรือค่าเป้าหมายขึ้นเอง หากยังไม่ตกลงเกณฑ์ให้ระบุว่ารอการยืนยัน

## 4. ตารางสืบย้อนจากความต้องการถึงผล

| วัตถุประสงค์ | Requirement / เกณฑ์ยอมรับ | Use Case / Design | Component / API / ข้อมูล | Test Case | ผลจริง / หลักฐาน | สถานะ |
|---|---|---|---|---|---|---|
| [วัตถุประสงค์จริง] | [REQ และเกณฑ์ที่ตกลง] | [รหัสหรือหัวข้อที่เกี่ยวข้อง] | [สิ่งที่รับผิดชอบจริง] | [TC] | [ผลหรือ Not Run พร้อมเหตุผล] | [Planned / Prototype / Implemented / Tested] |

ไม่ต้องผูกทุก Requirement กับทุกชนิดแผนภาพ แต่ต้องชี้ได้ว่าออกแบบและตรวจอย่างไร:

- **Planned** มีข้อกำหนดหรือแผน ยังไม่ยืนยัน implementation
- **Prototype** มีตัวอย่างบางส่วน อาจใช้ mock/sample/in-memory ต้องระบุข้อจำกัด
- **Implemented** ตรวจพบ source code และการเชื่อมต่อที่เกี่ยวข้อง ไม่ได้แปลว่าผ่านทดสอบแล้ว
- **Tested** มีผลทดสอบตามเกณฑ์และระบุรุ่น/สภาพแวดล้อม/หลักฐาน ความสำเร็จครอบคลุมเฉพาะสิ่งที่ทดสอบ

ถ้ายังไม่ได้รันทดสอบ เขียนวิธีทดสอบและ Expected Result ได้ แต่ Actual Result เป็น Not Run ไม่ใส่ Pass และไม่สรุปว่าใช้งานได้ครบ

## 5. การใช้กับ MyNetMate ใน Vault นี้

ใช้ `AGENTS.md` และ `02_feature/MyNetMate Weight Feature List (AI คิด).md` ของโปรเจกต์เป็นหลักสำหรับขอบเขตและความปลอดภัย ตรวจสถานะจริงจาก source code/manifest/ผลทดสอบก่อนเขียนผลสำเร็จ:

- P1 แสดง Login → Add Device → Config Builder → Preview → CIS Scan → Plan/Apply Modal การมี Modal ไม่ยืนยันว่า Push SSH แล้ว
- แยก P1, P2 และ CUT; ไม่เพิ่ม AI Config Generation/Review, Discovery, SSH Push หรือ ML evaluation เข้า MVP เพียงเพื่อให้เล่มดูครบ ส่วน PII Masking และ AI Guardrails Infrastructure ยังอยู่ P1 ตาม Scope ไม่ตัดออกเพราะฟีเจอร์ AI อยู่ P2
- Cisco เป็น baseline ส่วน Vendor อื่นต้องมีหลักฐานรุ่น OS/คำสั่งและผลทดสอบก่อนรับรอง
- แยก Simulation กับ Hardware จริง ทดสอบเครือข่ายเฉพาะ Isolated Lab; ไม่ใช้การเขียนเล่มเป็นเหตุให้ AI รันคำสั่งบนอุปกรณ์จริง
- ข้อมูลเครือข่ายและ Secret ต้อง Mask ก่อน external AI และ Config ต้องผ่าน CIS gate ตามกฎโครงการ ไม่แก้หรือสร้างไฟล์ใน `mynetmate/network-discovery/`
- ประกาศแบ่งกลุ่มแยกหัวข้อ (1) Network Management และ (2) Configuration Automation ให้แยกเจ้าของงานและหลักฐานของแต่ละเล่ม อธิบายระบบส่วนที่ใช้ร่วมได้โดยระบุการพึ่งพา ไม่อ้างว่าผู้จัดทำกลุ่มหนึ่งพัฒนาหรือทดสอบผลงานของอีกกลุ่มแล้ว

## 6. รอบตรวจก่อนส่ง

- ตรวจว่ารายการบังคับของประเภทงานครบ และมีเนื้อหาจริง ไม่ใช่เพียงหัวข้อว่าง
- ตรวจรายการบังคับของขั้นตอน Project 1/2 ในหัวข้อ 1 โดยแยกจากเนื้อหาเฉพาะ SW_Dev และแยกรายการโบนัสออกอีกชุด บันทึกหลักฐาน/รายการยังไม่ครบ/ข้อยกเว้นที่ยืนยัน ไม่ใช้โบนัสเป็นเงื่อนไขผ่านแทนของบังคับ
- ตรวจชื่อ Actor/Component/Entity/API ให้สอดคล้องข้ามแผนภาพกับข้อความและ implementation ที่อ้าง
- สืบย้อนวัตถุประสงค์และ Requirement ไปยังวิธีทดสอบ ผลจริง และข้อสรุป เก็บรายการยังไม่ทดสอบเป็นข้อจำกัด
- แยกข้อกำหนดจากรายวิชาออกจากคำแนะนำของ skill พร้อมชื่อไฟล์/หัวข้อ/ฉบับหรือวันที่ที่ทราบ
- การค้นข้อความช่วยตรวจรหัสและความครบเบื้องต้นได้ แต่ความถูกต้องของ 3NF, UML และความจริงของผลทดสอบต้องตรวจด้วยหลักฐาน ไม่อ้างว่าผ่านอัตโนมัติจากการพบชื่อแผนภาพหรือคำว่า Pass
