#### ช่วงเช้า — ทดสอบ Config Generation ตาม Use Case จริง (ไม่ใช่แค่ VLAN)

ใช้ตาราง Use Case ที่มีอยู่แล้ว ทดสอบทีละอัน เทียบ **AI (Gemini) vs Jinja2 Template**:

| Use Case           | Template ทดสอบแล้ว? | AI ทดสอบแล้ว? | Token ใช้ | Accuracy |
| ------------------ | ------------------- | ------------- | --------- | -------- |
| Basic device setup |                     |               |           |          |
| Interface config   |                     |               |           |          |
| VLAN + SVI         | ✅ (มีแล้ว)          |               |           |          |
| Static route       |                     |               |           |          |
| OSPF               |                     |               |           |          |
| SSH & Security     |                     |               |           |          |
| Syslog             |                     |               |           |          |
| SNMP               |                     |               |           |          |

**สิ่งที่ต้องได้จากตารางนี้:** เห็นชัดว่า Use Case ไหนควรใช้ Template ล้วน (predictable, low-risk) กับ Use Case ไหนจำเป็นต้องพึ่ง AI (เช่น กรณี config ซับซ้อนหรือ input ไม่ตายตัว) — นี่คือหลักฐานสนับสนุนสัดส่วน AI:Template ที่จะเสนออาจารย์

#### ช่วงสาย — ทดสอบ PII Masking: Presidio vs Custom Field List

ทีมมี `CRITICAL_FIELDS` และ `SENSITIVE_FIELDS` อยู่แล้ว (แบบ hardcode list) เทียบกับ Microsoft Presidio:

- ทดสอบส่ง running-config ตัวอย่างที่มี IP, password, community string เข้า Presidio → ดูว่า detect ได้ครบไหม เทียบกับ list ที่ทำเอง
- บันทึก: Presidio detect ได้ตรงบ้าง / พลาดบ้าง / False positive เท่าไหร่
- **Decision ที่ต้องได้:** ใช้ Presidio เป็น layer เสริม หรือใช้ custom list พอ (เพราะ scope แคบแค่ Cisco เดียว pattern จำกัด)

#### ช่วงบ่าย — ทดสอบ RAG แบบ with vs without (ตามที่วางแผนไว้ใน Day 2.2 เดิม)

เพราะ scope ตอนนี้แคบลงเหลือ Cisco IOS XE 17.03.04a เท่านั้น (ไม่ใช่ multi-vendor แล้ว) คำถามสำคัญคือ **RAG ยังจำเป็นไหม**:

- ทดสอบ prompt เดียวกัน (เช่น "สร้าง OSPF config") แบบไม่มี RAG เทียบกับมี RAG (ใช้ Cisco IOS Config Guide บางส่วน)
- ถ้า output ไม่ต่างกันมาก → อาจตัด RAG ออกจาก MVP ได้เลย (ลดความซับซ้อนของระบบไปอีก)
- ถ้าต่างกันชัดเจน → เก็บ RAG ไว้ แต่จำกัดแค่ document เดียว (Cisco IOS Guide) ไม่ต้องรวม MikroTik/CIS Benchmark ตามที่วางแผนไว้เดิม

#### ช่วงท้ายวัน — ปิด 2 การตัดสินใจที่ค้าง

**1) Save/Restore Strategy** — เลือกจาก 3 แบบ (Manual / Time-based / Schedule-diff) โดยพิจารณาจาก DB Schema ที่มีอยู่แล้ว (Device/Interface/VLAN/Route/Service tables) — เลือกแบบที่ implement ง่ายสุดสำหรับ MVP แล้วบันทึกเหตุผล

**2) สรุปตาราง Scope พร้อมเวลา** โดยเอาผลจากตาราง "เกินจริง vs ปัญหาจริง" มาใส่ประกอบ:

| Feature               | เวลาประมาณ (คน-สัปดาห์) | ตัดสินใจ (จาก evidence วันนี้)                        |
| --------------------- | ----------------------- | ----------------------------------------------------- |
| Vendor support        |                         | ✅ Cisco IOS XE เท่านั้น (ตัด Juniper/MikroTik/Arista) |
| Routing protocol      |                         | ✅/❌ OSPF เท่านั้น หรือ +BGP                           |
| Config Gen (Template) |                         |                                                       |
| Config Gen (AI)       |                         | สัดส่วนตามผลทดสอบเช้านี้                              |
| PII Masking           |                         | Presidio หรือ Custom list ตามผลทดสอบ                  |
| RAG                   |                         | เก็บ/ตัด ตามผลทดสอบบ่าย                               |
| Save/Restore          |                         | ตามที่ตัดสินใจ                                        |
